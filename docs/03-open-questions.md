## Q-1. スループットの合格ラインをいくつにするか【優先度: 高】

ご提示いただいた表では性能テストの合格ラインが「500ms 以内」のみで、
スループットの具体値が未定です。応答時間とスループットは
**セットで定義しないと意味をなしません**（負荷を下げれば応答時間はいくらでも下がるため）。

要件定義書では暫定的に `throughput_rps: 50` を置いていますが、確定が必要です。
決めるための観点:

- 想定するピーク時の同時利用者数と、1 人あたりのリクエスト頻度
- 本番の現行実績（ある場合はその値の 1.5〜2 倍を目標に置くのが一般的）
- 「p95 500ms を満たしながら、何 req/s まで捌ければ十分か」という形で表現する

**推奨する定義の形**: 「到達率 N req/s の一定負荷下で、p95 ≤ 500ms かつエラー率 ≤ 0.1%」。
スループットを結果として測るのではなく、**負荷条件として固定**し、
その条件下で応答時間が基準を満たすかを判定する形にすると、計測が安定します。

## Q-2. 性能計測用の専有環境を確保できるか【優先度: 高】

性能指標（M-03 / M-04 / M-05）は、他のジョブと共有された CI ランナー上では
計測値が安定せず、ゲートとして機能しません。次のいずれかが必要です。

| 選択肢 | 内容 | 影響 |
| --- | --- | --- |
| A | 専有の自ホスト型ランナー（固定スペック VM）を用意する | 推奨。追加コストは発生するが指標が信頼できる |
| B | 共有ランナーで計測し、絶対値ではなく前回比（回帰率）のみを判定する | しきい値 500ms の絶対判定は諦めることになる |
| C | 性能指標を当面見送る（Phase 3 のまま保留） | 他 5 カテゴリを先に立ち上げる |

**確保できない場合、性能指標は Phase 3 のまま保留**とし、
他の 5 カテゴリを先行して立ち上げることを推奨します。
計測できない指標を形だけ載せると、ゲート全体の信頼性を損ないます。

## Q-3. 対象リポジトリの現在のベースライン値は【優先度: 高】

しきい値（カバレッジ 75%、ミューテーション 60% 等）が現実的かどうかは、
現在地が分からないと判断できません。導入初日に全指標が不合格になる状態は、
[リスク R-2](01-requirements.md#13-リスクと対策) のとおり導入の失敗につながります。

**ご確認いただきたい値**:

- 現在のブランチカバレッジ（backend / frontend それぞれ）
- 既存コードで CC > 15 の関数がどの程度存在するか
- 現在の Critical / High 脆弱性の件数

これらが合格ラインから大きく乖離している場合、
[付録 A のラチェット方式](02-metrics-spec.md#付録-a-移行期の推奨運用ラチェット方式)での
段階導入を前提に計画を組み直します。

## Q-4. 対象リポジトリは何個か、構成はモノレポかポリレポか【優先度: 中】

要件定義書では「初期 5 / 3 年後 50」を想定値として置いています。

- Spring Boot と Vue が同一リポジトリ（モノレポ）か、別リポジトリ（ポリレポ）か
- ポリレポの場合、「フロントとバックで 1 つの判定」にまとめる必要があるか、
  それぞれ独立に判定してよいか

ポリレポで統合判定が必要な場合、複数リポジトリの Run を束ねる
「プロダクト」という上位概念をデータモデルに追加する必要があります。

## Q-5. 認証に使う IdP は何か【優先度: 中】

OIDC 対応を前提に設計していますが、具体的な IdP により実装の細部が変わります。

- Microsoft Entra ID / Google Workspace / Okta / Keycloak / GitHub OAuth など
- グループ情報（ロールのマッピング元）をどの claim で受け取れるか
- ロールを IdP のグループから自動マッピングするか、quality-gate 内で個別に付与するか

## Q-6. ミューテーションテストの CI 実行時間をどこまで許容できるか【優先度: 中】

要件定義書では既定を「変更クラスのみ（`scope: changed`）」としていますが、
それでも PIT は相応の時間を要します。

- PR の CI 全体の許容時間（例: 15 分以内）
- 変更クラス限定でも超過する場合、ミューテーションテストを
  PR ではなく main への push 後（または夜間バッチ）のみに回すか

**推奨**: PR では差分限定、main への push 後に全量を夜間実行。
PR の待ち時間を増やさずに、両方の値を得られます。

## Q-7. 通知先と通知条件の運用【優先度: 中】

- Slack のチャネルはリポジトリごとに分けるか、1 つに集約するか
- 「合格→不合格の遷移時のみ」を既定としていますが、これで妥当か
- 不合格が継続している場合の再通知（毎日 / 週次 / しない）をどうするか

通知が多すぎると無視され、少なすぎると気づかれません。
**既定は「遷移時のみ + 週次サマリ」**を推奨します。

---

## Q-8. 不合格時の是正プロセスをどう定めるか【優先度: 中】

D-4 のとおり本フェーズではマージをブロックしないため、
**不合格が放置されない運用ルール**が別途必要です。これはアプリの機能ではなく
運用の取り決めですが、これを欠くと [リスク R-7](01-requirements.md#13-リスクと対策)
のとおり「可視化しただけで何も改善しない」状態になります。

決めていただきたいこと:

- 不合格を検知してから是正までの目標期間（例: Critical 脆弱性は 3 営業日以内）
- 週次で不合格リポジトリをレビューする場（既存の定例に組み込めるか）
- Phase 3（マージブロック）へ移行する判断基準と時期の目安

## Q-9. 成果物の保持期間とストレージ【優先度: 低】

要件定義書では「Run メタデータ・指標値 2 年 / 元成果物 90 日」を既定としています。

- 監査・リリース判定の観点で、より長期の保持が必要か
- オブジェクトストレージ（MinIO 等）を新規に立てられるか、既存の S3 互換基盤があるか

## Q-10. デプロイ先と運用体制【優先度: 低】

- オンプレミスか、プライベートクラウド（AWS / Azure / GCP）か
- Docker Compose での単一ホスト運用で足りるか、Kubernetes が前提か
- 運用担当（監視・バックアップ・アップデート）はどのチームか

社内単一テナント・初期 5 リポジトリの規模であれば、
**Docker Compose による単一ホスト構成**で十分と考えています。
