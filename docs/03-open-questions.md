## Q-6. ミューテーションテストの CI 実行時間をどこまで許容できるか【優先度: 中】

要件定義書では既定を「変更クラスのみ（`scope: changed`）」としていますが、
それでも PIT は相応の時間を要します（全量では単体テストの数十倍）。

- PR の CI 全体の許容時間（例: 15 分以内）
- 変更クラス限定でも超過する場合、ミューテーションテストを
  PR ではなく main への push 後（または夜間バッチ）のみに回すか

**推奨**: PR では差分限定、main への push 後に全量を夜間実行。
PR の待ち時間を増やさずに、両方の値を得られます。

## Q-7. 通知先と通知条件の運用【優先度: 中】

- 通知先の Slack チャネル（対象は 1 リポジトリのため 1 チャネルで足ります）
- 「合格→不合格の遷移時のみ」を既定としていますが、これで妥当か
- 不合格が継続している場合の再通知（毎日 / 週次 / しない）をどうするか

通知が多すぎると無視され、少なすぎると気づかれません。
**既定は「遷移時のみ + 週次サマリ」**を推奨します。

## Q-8. 不合格時の是正プロセスをどう定めるか【優先度: 中】

D-4 のとおり本フェーズではマージをブロックしないため、
**不合格が放置されない運用ルール**が別途必要です。これはアプリの機能ではなく
運用の取り決めですが、これを欠くと [リスク R-7](01-requirements.md#13-リスクと対策)
のとおり「可視化しただけで何も改善しない」状態になります。

決めていただきたいこと:

- 不合格を検知してから是正までの目標期間（例: Critical 脆弱性は 3 営業日以内）
- 週次で不合格リポジトリをレビューする場（既存の定例に組み込めるか）
- Phase 3（マージブロック）へ移行する判断基準と時期の目安

## Q-12. GitHub Actions の無料枠をどう使い切らずに運用するか【優先度: 高】

D-11 により GitHub は**個人アカウント（Free）**、リポジトリはプライベートとなります。
この場合、**GitHub Actions の無料枠は月 2,000 分**です。
一方、本要件で追加する計測ジョブのうち PIT と k6 は実行時間が長く、
そのままでは無料枠を圧迫します。

**提案する構成**（Q-2 で確保する専有ランナーを活用する）:

| ジョブ | 実行先 | 無料枠の消費 |
| --- | --- | --- |
| ビルド、JUnit、Vitest、JaCoCo | GitHub ホストランナー | 消費する |
| Trivy / Semgrep / gitleaks / PMD / ESLint | GitHub ホストランナー | 消費する（いずれも短時間） |
| **PIT（ミューテーション）** | セルフホストランナー | **消費しない** |
| **k6（負荷試験）** | セルフホストランナー（専有） | **消費しない** |
| Playwright + axe-core | どちらでも可 | — |

セルフホストランナーでの実行時間は無料枠を消費しません。
Q-2 で確保する性能計測用の専有マシンを、GitHub のセルフホストランナーとしても
登録することで、追加コストなく重いジョブを逃がせます。

**ご確認いただきたいこと**:

- 専有マシンをセルフホストランナーとして登録してよいか
- 上記の振り分けで問題ないか（k6 は計測条件を統制する必要があるため、
  専有ランナー固定が必須です）

> セルフホストランナーをプライベートリポジトリで使う分には問題ありませんが、
> パブリックリポジトリでセルフホストランナーを使うことは
> セキュリティ上の理由から GitHub が非推奨としています。本件はプライベートのため該当しません。

## Q-13. 利用者数と、ロール構成を簡素化するか【優先度: 中】

D-10 により対象は 1 リポジトリ、D-11 により認証は個人の GitHub アカウントとなり、
当初想定（初期 5 リポジトリ / 10 ユーザー）より**かなり小規模**な構成になりました。

要件定義書では 4 ロール（Viewer / Developer / Maintainer / Admin）と、
免除の申請 → 承認フローを定義していますが、
**利用者が数名で、申請者と承認者が同一人物になる**場合、承認フローは形式的なものになります。

| 選択肢 | 内容 |
| --- | --- |
| A（現在の前提） | 4 ロール + 免除の申請/承認フローをそのまま実装する |
| B | ロールを Admin / Viewer の 2 種に簡素化し、免除は申請即承認（記録のみ）とする |
| C | Phase 1 は B で実装し、利用者が増えた時点で A へ拡張する（**推奨**） |

免除の「承認」が持つ本来の価値は、脆弱性の握りつぶしを一人で決めさせない点にあります。
利用者が 1〜2 名の段階では機能しないため、C を推奨します。
ただし**免除の記録（理由・期限・実施者）は人数に関わらず必ず残す**べきで、
これは B でも維持します。

**ご確認いただきたいこと**: 想定する利用者数と、A / B / C のいずれを採るか
