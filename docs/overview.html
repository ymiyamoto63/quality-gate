QUALITY-GATE ／ 仕様概要

1 つのアプリが「リリースしてよいか」を、
誰にでも分かる 1 画面で示す

quality-gate は、対象アプリの品質を 12 の指標で計測・判定し、リリース可 / リリース不可を、開発に携わっていない方を含め、誰にでもひと目で分かる形で示す社内向け Web アプリケーションです。

1. 主な特徴

画面はリリース判定の 1 枚だけ

最上部に結論を大きく表示し、その下に基準ごとの合否・根拠・履歴を並べる。印刷して PDF の証跡にできる。

合否は 2 値

指標は「合格 / 不合格」だけ。測れなかった指標は計測エラーとして不合格に数える（fail-closed）。

合格ラインは環境変数

QG_* で決める。判定に使った値は計測ごとに保存され、後から変えても過去の結論は変わらない。

共有アカウントでログイン

全員で 1 つのアカウントを共有。GitHub アカウントは不要。ロールも持たない。

対象リポジトリには何も置かない

計測は quality-gate 側の収集ランナーが対象を clone して行う。対象チームに保守を求めない。

マージはブロックしない

可視化に徹する。しきい値の妥当性を実績で確かめる前のブロックはゲートを形骸化させるため。

ブラウザリリース判定の画面を閲覧・印刷
要素役割
収集ランナー対象を取得して計測し、成果物を Ingest API に送る。計測方法とツールの版は collector/ に置く
quality-gate アプリSpring Boot 1 プロセス。成果物を取り込み、合格ラインで判定して保存する。テストやスキャンは実行しない

  • Vue 3 の SPA を Spring Boot に同梱し同一オリジンで配信（CORS 不要、HttpOnly セッション Cookie で認証）
  • バックエンドは GitHub API を呼ばない。比較元やタグは収集ランナーが clone した履歴から求めて送る

4. 12 の品質指標

対象は Java / Spring Boot（Maven）+ Vue 3（npm + Vitest）のモノレポ。M-01・M-02・M-09・M-10 は backend / frontend ごとに判定し、その他は Run 全体で 1 つの値にします。

IDカテゴリ指標既定の合格ライン計測ツール環境変数
M-01機能テストブランチカバレッジ75% 以上（各コンポーネント）JaCoCo / Vitest (v8)QG_BRANCH_COVERAGE_MIN
M-02機能テストミューテーションスコア60% 以上（backend のみ）PITQG_MUTATION_SCORE_MIN
M-03性能応答時間 p9550 req/s の負荷下で 500ms 以内k6QG_RESPONSE_TIME_P95_MAX_MS
M-04性能エラー率0.1% 以下k6QG_ERROR_RATE_MAX_PCT
M-05セキュリティ重大・高 脆弱性件数Critical 0・High 0Trivy (SARIF)QG_CRITICAL_/HIGH_VULNERABILITIES_MAX

  • QG_EXCLUSIONS（glob、**/ 始まりの接尾一致で書く）に一致するファイルは M-01・M-02・M-05・M-06・M-11・M-12 の計測から外す

5. 判定のルール

指標のステータス

ステータス条件リリース判定への影響
●合格 PASS合格ラインを満たす—
■不合格 FAIL合格ラインを満たさないリリース不可
◆計測エラー ERROR成果物の未提出・形式不正・メタデータ不足・計測条件を満たさないリリース不可（不合格として扱う）
—対象外 NOT_APPLICABLEツールの制約で測れない（M-02 の frontend など）影響しない（表に出さない）
 
FAIL または ERROR が 1 つ以上  → FAIL（リリース不可）
それ以外                       → PASS（リリース可）
NOT_APPLICABLE は影響しない
測っていないものを合格とみなさない（fail-closed）ことが quality-gate の根幹です。結論は「リリース可 / リリース不可 / 未計測」の 3 つで、「注意」のような中間段階は持ちません。前回からの低下など気になる点は判定理由に書き添えるだけです。

比較元・比較対象 Run

  • 比較元（M-07 の起点）: 既定ブランチは直前のコミット、他のブランチは merge-base、タグは前のタグ
  • 比較対象 Run（前回比・違反の新規/継続/解消・M-10 の起点）: 比較元コミットの判定済み Run、無ければ同じブランチの直前の判定済み Run
  • 違反は sha256(指標ID + 同定子) の fingerprint で Run をまたいで追跡する（行番号は含めない）

Run のライフサイクル

CREATED ─(成果物)→ UPLOADING ─(finalize)→ FINALIZED → PROCESSING ─┬→ EVALUATED
                                                                  └→ FAILED（処理失敗。計測し直す）

Run は「1 コミットに対する 1 回の計測・判定」で、確定後は不変。処理失敗 FAILED と判定結果の不合格 verdict = FAIL は別物です。同じコミットへの再送信は attempt を増やした新しい Run になります。

6. 画面（リリース判定）

パスは /（?ref=<タグかコミット> で指定可）。上から次の順に並べます。

  1. 結論 — リリース可 / リリース不可 / 未計測 を大きく表示
  2. 品質基準ごとの合否 — 不合格の指標には理由と主な違反（深刻な順に最大 10 件、GitHub の該当箇所へのリンク）
  3. 各指標の説明と基準の根拠 — 根拠の種類（外部基準 / 業界の目安 / チーム判断）と、満たさないと何が起きるか
  4. 判定の履歴 — 新しい順、最大 50 件。各判定を開ける
要件内容
結論の安定性同じ指定なら何度開いても結論が変わらない（判定し直さない。近くのコミットで代用しない）
出力印刷して PDF にできる（CSV 出力は持たない）
ステータス表現ラベル・記号・アイコン・色を常に同時に使い、色だけで合否を伝えない
テーマライト / ダーク / OS 追従
レスポンシブ768px 未満では指標の表をカード形式に変形（375px 幅で確認）
アクセシビリティquality-gate 自身も WCAG 2.2 AA を満たす。CI で axe-core の critical / serious 0 件を確認

他の画面はログイン（/login）と「見つからない」のみです。

7. 収集ランナー（計測の仕組み）

.github/workflows/collect.yml を手動実行（ブランチ・コミット・タグを指定）すると、3 つのジョブで計測します。

ジョブやること認証情報所要時間
fetchGitHub App の読み取り専用トークン（1 時間）で clone し、計測コミット・比較元・タグを決めるApp の秘密鍵1 分未満
measureコンテナの中でビルド・テスト・解析し、成果物を reports/ にまとめるなし数分〜20 分以上
submitRun 作成 → 成果物アップロード → 確定。処理失敗ならジョブ失敗（不合格では失敗にしない）Ingest Token1 分未満
  • 専有のセルフホストランナー 1 台で直列に実行（性能計測の条件をそろえ、社内の quality-gate に届くようにするため）
  • 計測コンテナは --cap-drop ALL・no-new-privileges・メモリ上限付きで、Docker ソケットや認証情報を見せない
  • テストが失敗しても計測は止めない。成果物が出なかった指標は ERROR になる
  • PR は計測しない。部分計測（スキップの申告）も持たない

8. バックエンドとデータベース

モジュール構成（com.qualitygate）

モジュール役割
ingest取り込み API、Ingest Token 認証、成果物の受領と保管、リポジトリ登録
pipeline正規化 → 判定の流れ（確定から呼ぶ）
adapterツール別パーサ（jacoco, lcov, pit, k6, sarif, pmd, eslint, junit, oasdiff, axe）
normalize / evaluate正規化と fingerprint 生成 / 合格ラインの適用・指標判定・Run の集約
release / queryリリース判定と履歴 / ログイン状態
domain / platform / configエンティティ等 / 設定・ArtifactStore・例外・可観測性 / Security と SPA 配信

adapter と evaluate は互いを知らない、などの依存規則を ArchUnit で検証します。指標やツール形式の追加は、アダプタと判定器の追加で完結します。

テーブル

repositories ──▶ runs ──┬──▶ artifacts
                        ├──▶ measurements
                        └──▶ findings
  • 主キーは UUIDv7、日時は timestamptz（UTC）、判定に関わる数値は numeric
  • measurements.threshold に判定時の合格ラインを、previous_value に前回値を焼き付ける
  • マイグレーションは Flyway（V001__init.sql、V002__simplify.sql）

9. API

ベースパス /api/v1、JSON（アップロードのみ multipart）。正本は実装から生成した api/openapi.yml で、フロントエンドの型もそこから生成します。エラーは RFC 9457 Problem Details に errorCode・traceId を足して返します。

メソッドパス用途認可
POST/runsRun の作成（初回はリポジトリ登録）Ingest Token
POST/runs/{runId}/artifacts成果物のアップロード（1 ファイル 50MB / Run 合計 200MB まで）Ingest Token
POST/runs/{runId}/finalize確定し、その場で判定して結果を返すIngest Token
POST/login, /logoutログイン / ログアウト公開 / ログイン
GET/meログイン中のユーザー名ログイン
GET/release?ref=リリース判定（ref 省略で最新）ログイン
GET/release/history判定の履歴（最大 50 件）ログイン
  • Ingest Token は書き込み専用で参照 API は呼べない。交換時は新旧をカンマ区切りで並べる
  • セッションは HttpOnly の JSESSIONID Cookie。状態を変える操作には CSRF トークン（X-XSRF-TOKEN）が必要
  • /actuator/health は公開、/actuator/prometheus はログインが必要

11. 非機能要件と制約

項目内容
規模対象 1 リポジトリ、Run は 1 日数件、利用者は数名〜20。PostgreSQL 1 台 + アプリ 1 プロセス（Docker Compose）
性能の目安リリース判定の表示 p95 1.0 秒、確定から判定結果の応答まで p95 60 秒
可用性quality-gate の障害が対象の開発を止めない。DB は日次バックアップ
セキュリティTLS、秘密情報は環境変数でログに出さない、アップロードのサイズ上限と形式検証、XML 外部実体参照の無効化
運用/actuator/health、Prometheus メトリクス、相関 ID（requestId / runId）付きログ
自身の品質quality-gate 自身は計測対象にせず、PR の CI（ci.yml）で単体・結合テスト、静的検査、生成物の同期、アクセシビリティ、脆弱性を確認

制約

  • 社内専用・単一テナント。共有アカウントのため、誰が見たかは記録しない
  • 計測できるのは Maven + npm / Vitest のモノレポのみ。ミューテーションテストは backend のみ
  • 自動のアクセシビリティ検査は WCAG 違反の一部しか検出できない（手動確認を併用）
