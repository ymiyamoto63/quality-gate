QUALITY-GATE ／ 仕様概要

1 つのアプリが「リリースしてよいか」を、
誰にでも分かる 1 画面で示す

quality-gate は、対象アプリの品質を 12 の指標で計測・判定し、リリース可 / リリース不可を、開発に携わっていない方を含め、誰にでもひと目で分かる形で示す社内向け Web アプリケーションです。

1. 主な特徴

画面はリリース判定の 1 枚だけ

最上部に結論を大きく表示し、その下に基準ごとの合否・根拠・履歴を並べる。印刷して PDF の証跡にできる。

合否は 2 値

指標は「合格 / 不合格」だけ。測れなかった指標は計測エラーとして不合格に数える（fail-closed）。

合格ラインは環境変数

QG_* で決める。判定に使った値は計測ごとに保存され、後から変えても過去の結論は変わらない。

共有アカウントでログイン

全員で 1 つのアカウントを共有。GitHub アカウントは不要。ロールも持たない。

対象リポジトリには何も置かない

計測は quality-gate 側の収集ランナーが対象を clone して行う。対象チームに保守を求めない。

マージはブロックしない

可視化に徹する。しきい値の妥当性を実績で確かめる前のブロックはゲートを形骸化させるため。

quality-gate アプリSpring Boot 1 プロセス。成果物を取り込み、合格ラインで判定して保存する。テストやスキャンは実行しない

  • Vue 3 の SPA を Spring Boot に同梱し同一オリジンで配信（CORS 不要、HttpOnly セッション Cookie で認証）
  • バックエンドは GitHub API を呼ばない。比較元やタグは収集ランナーが clone した履歴から求めて送る

3. 最初の測定結果までの手順

アプリを起動してから、リリース判定の画面で最初の結論を見るまでの流れです。大きく事前設定 → 測定 → 結果確認の 3 段階で、初回の準備は 1 回だけ行います。詳しい手順は docs/operations.md を参照してください。

① 事前設定アプリ・ランナー・GitHub・計測プロファイルを準備（初回のみ）
→
② 測定collect ワークフローを手動実行（数分〜）
→
③ 結果確認ジョブのログとリリース判定の画面で結論を見る

3.1 事前設定（初回のみ）

#やること場所ポイント
1.env を作り、アプリを起動するアプリを動かすマシンQG_REPOSITORY（対象の owner/name）、QG_LOGIN_PASSWORD（12 文字以上）、QG_INGEST_TOKEN は必須。合格ラインは書かなければ既定値
2セルフホストランナーを 1 台登録するランナーのマシン（Linux x64）Docker・git・curl・jq が必要。Settings → Actions → Runners で Idle になれば完了
3対象を読む GitHub App を作り、対象にインストールするGitHub対象が private のときだけ。権限は Contents: Read-only。秘密鍵をダウンロードしておく
4quality-gate リポジトリに変数とシークレットを設定するGitHub（Settings → Secrets and variables → Actions）Variables: QG_BASE_URL・QG_COLLECTOR_APP_ID／Secrets: QG_COLLECTOR_APP_PRIVATE_KEY・QG_INGEST_TOKEN（アプリと同じ値）
5計測プロファイル collector/target/profile.env を書き、main にマージするquality-gate リポジトリQG_REPOSITORY をアプリと一致させる。止める指標は DISABLED_METRICS とアプリの QG_DISABLED_METRICS の両方に書く
 
cp .env.example .env                              # QG_REPOSITORY・QG_LOGIN_PASSWORD・QG_INGEST_TOKEN を書き入れる
openssl rand -hex 32                              # Ingest Token の作り方の例
docker compose --profile full up -d --build       # DB とアプリを起動 → http://localhost:8080
対象リポジトリには何も置きません。アプリの QG_REPOSITORY と計測プロファイルの QG_REPOSITORY、アプリと GitHub の QG_INGEST_TOKEN がそれぞれ一致していることが、最初の計測を通すための要点です。

3.2 測定

  1. quality-gate リポジトリの Actions → collect → Run workflow を開く
  2. 入力を指定して実行する。最初は branch・commit とも空（既定ブランチの最新コミット）でよい。リリース判定に使うときは commit にタグ（例: v1.2.0）を入れる
  3. fetch → measure → submit の 3 ジョブが順に動く。所要時間は負荷試験が無効なら数分、有効なら約 18 分を加える。初回は計測用コンテナのビルドに数分かかる

手元で試すときは、ワークフローと同じスクリプトを直接実行できます（その場合も結果はアプリに取り込まれます）。

WORK=/tmp/qg-collector
./collector/bin/fetch.sh "$WORK"
./collector/bin/measure-isolated.sh "$WORK" "$WORK/reports"
QG_BASE_URL=http://localhost:8080 QG_INGEST_TOKEN=<アプリの QG_INGEST_TOKEN> \
  ./collector/bin/submit.sh "$WORK/reports"

3.3 結果確認

  1. submit ジョブのログで、Run を作成しました: <runId>・送信したファイル・判定: PASS（または FAIL）とリリース判定の URL を確かめる。処理失敗のときだけ submit ジョブが失敗する（判定が不合格でもジョブは成功）
  2. quality-gate の画面（/）を開き、QG_LOGIN_USERNAME（既定 quality）と QG_LOGIN_PASSWORD でログインする
  3. 最上部の結論（リリース可 / リリース不可）と、品質基準ごとの合否を見る。不合格・計測エラーの指標は理由と主な違反から原因を確かめる
  4. 必要なら「PDF として保存（印刷）」で証跡を残す。measure ジョブの成果物 collector-reports（7 日保持）で送った内容も確認できる
最初の結果でよくあること原因と対処
ジョブが始まらないセルフホストランナーが止まっている（Idle になっているか確かめる）
submit の Run 作成が 401GitHub の Secret とアプリの QG_INGEST_TOKEN が一致していない
submit の Run 作成が 400計測プロファイルとアプリの QG_REPOSITORY が一致していない
計測していない指標が計測エラーDISABLED_METRICS にだけ書き、アプリの QG_DISABLED_METRICS に書いていない
M-07 が対象外初回は比較元に OpenAPI 定義が無いため。異常ではない

最初の計測はベースラインです。合格ラインを確定する前に、対象自身のビルド（カバレッジ・テスト件数など）と結果が一致するかを確かめてください。判定し直す機能は無いため、設定を直したら計測し直します。

6. 判定のルール

指標のステータス

ステータス条件リリース判定への影響
●合格 PASS合格ラインを満たす—
■不合格 FAIL合格ラインを満たさないリリース不可
◆計測エラー ERROR成果物の未提出・形式不正・メタデータ不足・計測条件を満たさないリリース不可（不合格として扱う）
—対象外 NOT_APPLICABLEツールの制約で測れない（M-02 の frontend など）影響しない（表に出さない）
 
FAIL または ERROR が 1 つ以上  → FAIL（リリース不可）
それ以外                       → PASS（リリース可）
NOT_APPLICABLE は影響しない
測っていないものを合格とみなさない（fail-closed）ことが quality-gate の根幹です。結論は「リリース可 / リリース不可 / 未計測」の 3 つで、「注意」のような中間段階は持ちません。前回からの低下など気になる点は判定理由に書き添えるだけです。

比較元・比較対象 Run

  • 比較元（M-07 の起点）: 既定ブランチは直前のコミット、他のブランチは merge-base、タグは前のタグ
  • 比較対象 Run（前回比・違反の新規/継続/解消・M-10 の起点）: 比較元コミットの判定済み Run、無ければ同じブランチの直前の判定済み Run
  • 違反は sha256(指標ID + 同定子) の fingerprint で Run をまたいで追跡する（行番号は含めない）

Run のライフサイクル

CREATED ─(成果物)→ UPLOADING ─(finalize)→ FINALIZED → PROCESSING ─┬→ EVALUATED
                                                                  └→ FAILED（処理失敗。計測し直す）

Run は「1 コミットに対する 1 回の計測・判定」で、確定後は不変。処理失敗 FAILED と判定結果の不合格 verdict = FAIL は別物です。同じコミットへの再送信は attempt を増やした新しい Run になります。

7. 画面（リリース判定）

パスは /（?ref=<タグかコミット> で指定可）。上から次の順に並べます。

  1. 結論 — リリース可 / リリース不可 / 未計測 を大きく表示
  2. 品質基準ごとの合否 — 不合格の指標には理由と主な違反（深刻な順に最大 10 件、GitHub の該当箇所へのリンク）
  3. 各指標の説明と基準の根拠 — 根拠の種類（外部基準 / 業界の目安 / チーム判断）と、満たさないと何が起きるか
  4. 判定の履歴 — 新しい順、最大 50 件。各判定を開ける
要件内容
結論の安定性同じ指定なら何度開いても結論が変わらない（判定し直さない。近くのコミットで代用しない）
出力印刷して PDF にできる（CSV 出力は持たない）
ステータス表現ラベル・記号・アイコン・色を常に同時に使い、色だけで合否を伝えない
テーマライト / ダーク / OS 追従
レスポンシブ768px 未満では指標の表をカード形式に変形（375px 幅で確認）
アクセシビリティquality-gate 自身も WCAG 2.2 AA を満たす。CI で axe-core の critical / serious 0 件を確認

他の画面はログイン（/login）と「見つからない」のみです。

8. 収集ランナー（計測の仕組み）

.github/workflows/collect.yml を手動実行（ブランチ・コミット・タグを指定）すると、3 つのジョブで計測します。

ジョブやること認証情報所要時間
fetchGitHub App の読み取り専用トークン（1 時間）で clone し、計測コミット・比較元・タグを決めるApp の秘密鍵1 分未満
measureコンテナの中でビルド・テスト・解析し、成果物を reports/ にまとめるなし数分〜20 分以上
submitRun 作成 → 成果物アップロード → 確定。処理失敗ならジョブ失敗（不合格では失敗にしない）Ingest Token1 分未満
  • 専有のセルフホストランナー 1 台で直列に実行（性能計測の条件をそろえ、社内の quality-gate に届くようにするため）
  • 計測コンテナは --cap-drop ALL・no-new-privileges・メモリ上限付きで、Docker ソケットや認証情報を見せない
  • テストが失敗しても計測は止めない。成果物が出なかった指標は ERROR になる
  • PR は計測しない。部分計測（スキップの申告）も持たない

9. 成果物の流れ

成果物は、計測ツールが出力するレポートのファイル（JaCoCo の XML、Trivy の SARIF など）のことです。収集ランナーが作って送り、quality-gate アプリが保管して判定に使います。対象リポジトリには何も書き込みません。

  1. 1
    作成measure ジョブ

    誰が計測ツール（measure.sh が呼ぶ JaCoCo・Trivy・k6 など）

    どこにランナーのマシンの reports/（計測用コンテナにマウント）

    何を各ツールがレポートを決まったパスに書く。出なかったファイルは無いまま

  2. 2
    受け渡しmeasure → submit

    誰がGitHub Actions

    どこにActions の成果物 collector-reports（7 日で消える）

    何をreports/ をまるごと次のジョブへ渡す

  3. 3
    送信submit ジョブ

    誰がsubmit.sh

    どこにIngest API（Ingest Token で認証）

    何をRun を作り、ファイルを 1 つずつ type・component・metadata 付きで送り、最後に確定（finalize）する。無いファイルは送らない

  4. 4
    保管quality-gate アプリ

    誰が取り込み（ingest）

    どこにファイル: QG_ARTIFACT_ROOT/<runId>/<ID>_<ファイル名>
    記録: artifacts テーブル

    何をこの時点では中身を読まない。サイズ上限と必須のメタデータだけ検証して保存する

  5. 5
    判定quality-gate アプリ

    誰が判定の流れ（pipeline）

    どこにmeasurements・findings テーブル、runs.verdict

    何を確定の中で、保存したファイルを種別ごとのアダプタで読み、正規化 → 判定する。送られなかった指標は計測エラー

GitHub Actions の「成果物（artifact）」は、ジョブ間でこのファイル群を受け渡す入れ物として使うだけです（② 受け渡し）。quality-gate アプリが判定に使うのは、④ で Ingest API から受け取って保管したファイルです。

成果物ごとの対応

reports/ 内のどのファイルを、どの種別（type）で送り、どの指標の判定に使うかの一覧です。component は計測プロファイルの BACKEND_DIR / FRONTEND_DIR の末尾のディレクトリ名です。

reports/ 内のファイル作るツールtypecomponentmetadata指標送る条件
backend/jacoco.xmlJaCoCojacoco-xmlbackend—M-01BACKEND_DIR がある

  • 止めた指標（DISABLED_METRICS）の成果物は作らず、送らない
  • meta.env（計測したコミット・比較元・タグ）は成果物として送らず、Run を作る要求の中身にする。versions.env（ツールの版）と oasdiff の入力（openapi-*.yml）も送らない
  • 確定前に同じ種別・同じファイル名を送り直すと置き換わる。確定後は追加も置き換えもできず、判定済みの結論は変わらない
  • ファイルは自動では消さない。Run を削除しても、ファイルの実体は QG_ARTIFACT_ROOT に残る

11. データベース

DBMS は PostgreSQL 17。列の定義の正本は backend/src/main/resources/db/migration/ で、Flyway で適用します。V001__init.sql 1 本で作ります。現在のテーブルは次の 5 つです。

11.1 設計方針

項目方針理由
主キーuuid（UUIDv7 をアプリで採番）API に出る ID を推測しにくくしつつ、時系列順でインデックスの局所性を保つ
日時timestamptz（UTC）表示するときにタイムゾーンを適用する
列挙varchar + CHECK 制約ENUM 型は値の追加に DDL が要る
半構造データjsonb指標ごとに違う内訳を持つ。検索に使う値は列にする
数値判定に関わる値は numeric丸めで境界値（75.0% など）の判定が変わらないようにする
削除自動では消さない。消すときは Run を物理削除し、子の行は CASCADE で消える論理削除フラグは全クエリに条件が増える

11.2 論理設計（ER 図）

PK 主キーFK 外部キー｜｜ 1○＜ 0 以上破線: 複製・自己参照

関連多重度意味
リポジトリ → Run1 : 0..N1 つのリポジトリを何度も計測する。同じコミットの再計測は試行回数を増やした別の Run
Run → 成果物1 : 0..N収集ランナーが送った JaCoCo・SARIF などのファイル
Run → 指標の判定結果1 : 0..N指標 × コンポーネント × シナリオ × 計測条件ごとに 1 行
Run → 違反1 : 0..N不合格の根拠になった関数・CVE・画面の要素など
Run → 比較対象 RunN : 0..1前回比・違反の新規 / 継続 / 解消・スキップの増加を数える起点。比較対象が消えても判定済みの値は残る（前回値を焼き付けているため）
リポジトリ → 指標の判定結果1 : 0..NRun を経由せずに指標の値を時系列で引くための複製

12. API

ベースパス /api/v1、JSON（アップロードのみ multipart）。正本は実装から生成した api/openapi.yml で、フロントエンドの型もそこから生成します。エラーは RFC 9457 Problem Details に errorCode・traceId を足して返します。

メソッドパス用途認可
POST/runsRun の作成（初回はリポジトリ登録）Ingest Token
POST/runs/{runId}/artifacts成果物のアップロード（1 ファイル 50MB / Run 合計 200MB まで）Ingest Token
POST/runs/{runId}/finalize確定し、その場で判定して結果を返すIngest Token
POST/login, /logoutログイン / ログアウト公開 / ログイン
GET/meログイン中のユーザー名ログイン
GET/release?ref=リリース判定（ref 省略で最新）ログイン
GET/release/history判定の履歴（最大 50 件）ログイン
  • Ingest Token は書き込み専用で参照 API は呼べない。交換時は新旧をカンマ区切りで並べる
  • セッションは HttpOnly の JSESSIONID Cookie。状態を変える操作には CSRF トークン（X-XSRF-TOKEN）が必要
  • /actuator/health は公開、/actuator/prometheus はログインが必要

14. 非機能要件と制約

項目内容
規模対象 1 リポジトリ、Run は 1 日数件、利用者は数名〜20。PostgreSQL 1 台 + アプリ 1 プロセス（Docker Compose）
性能の目安リリース判定の表示 p95 1.0 秒、確定から判定結果の応答まで p95 60 秒
可用性quality-gate の障害が対象の開発を止めない。DB は日次バックアップ
セキュリティTLS、秘密情報は環境変数でログに出さない、アップロードのサイズ上限と形式検証、XML 外部実体参照の無効化
運用/actuator/health、Prometheus メトリクス、相関 ID（requestId / runId）付きログ
自身の品質quality-gate 自身は計測対象にせず、PR の CI（ci.yml）で単体・結合テスト、静的検査、生成物の同期、アクセシビリティ、脆弱性を確認

制約

  • 社内専用・単一テナント。共有アカウントのため、誰が見たかは記録しない
  • 計測できるのは Maven + npm / Vitest のモノレポのみ。ミューテーションテストは backend のみ
  • 自動のアクセシビリティ検査は WCAG 違反の一部しか検出できない（手動確認を併用）
