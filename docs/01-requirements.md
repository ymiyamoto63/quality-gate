## 1. 背景と目的

### 1.1 背景

ソフトウェアの品質は「テストを書いている」「脆弱性スキャンを回している」といった
*活動の有無* では語れるが、*水準* を数値で語れていないことが多い。
個々のツール（JaCoCo、Vitest、Trivy、k6、axe-core など）は導入済みでも、
結果は CI のログやジョブごとの成果物に散在し、次のような状態に陥りやすい。

- 品質の現在地がチーム内で共有されていない（各自が別のツールの別の画面を見ている）
- 「良くなっているのか悪くなっているのか」の推移が追えない
- 合格ラインが暗黙知で、人によって判断が違う
- カバレッジは見ているが、ミューテーションスコア・複雑度・アクセシビリティは誰も見ていない

### 1.2 目的

quality-gate は、指定したリポジトリについて以下を実現する。

1. **定量化** — 6 カテゴリの品質指標を、定義の揺れなく同一の基準で数値化する
2. **判定** — 明示された合格ラインに対して 合格 / 不合格 を機械的に判定する
3. **可視化** — 現在地と推移をダッシュボードで一望できるようにする
4. **早期検知** — 品質が劣化した時点で通知し、劣化を放置させない

### 1.3 ゴール（成功の定義）

| # | ゴール | 測り方 |
| --- | --- | --- |
| G-1 | 対象リポジトリの 6 カテゴリ全指標が、毎日自動で数値として記録されている | 直近 30 日の計測成功率 95% 以上 |
| G-2 | 誰でも 1 画面で「今の合否」と「30 日の推移」が分かる | ダッシュボード到達から把握まで 3 クリック以内 |
| G-3 | 品質劣化（不合格への遷移）が発生当日に関係者へ通知される | 不合格遷移の通知到達率 100% |
| G-4 | 合格ラインの定義がコードとして管理され、変更履歴が追える | 設定はすべて `.quality-gate.yml` とその版数で管理 |

### 1.4 非ゴール（このアプリがやらないこと）

- **テストやスキャンの実行そのもの** — 実行は対象リポジトリの CI が担う（3.1 参照）
- **マージのブロック** — 本フェーズでは可視化・通知に徹し、PR のマージ制御は行わない
- **品質問題の自動修正** — 検出と提示までを担当し、修正は開発者が行う
- **汎用 BI ツール化** — 品質指標に用途を限定し、任意のメトリクス投入基盤にはしない

## 2. スコープ

### 2.1 計測対象リポジトリの前提

| 項目 | 前提 |
| --- | --- |
| バックエンド | Java / Spring Boot 4 |
| フロントエンド | Vue 3 SPA（TypeScript） |
| 単体・結合テスト | JUnit 5、Testcontainers、Vitest（導入済み） |
| カバレッジ計測 | JaCoCo（導入済み）、Vitest coverage |
| リポジトリホスティング | GitHub（GitHub Actions を CI として利用） |
| リポジトリ構成 | **モノレポ**（`backend/`、`frontend/`）。対象は **1 リポジトリ** |
| GitHub アカウント種別 | 個人アカウント（GitHub Free）。Organization は使用しない |
| リポジトリの公開設定 | プライベート |

対象が単一のモノレポであるため、backend と frontend の計測結果は 1 つの Run に
まとまる。契約テスト（M-08）のように両者にまたがる指標を扱ううえで都合がよく、
複数リポジトリの Run を束ねる上位概念（「プロダクト」等）は不要である。

> **GitHub Free の制約**: プライベートリポジトリでの GitHub Actions は
> **月 2,000 分**までが無料枠となる（パブリックリポジトリおよび
> セルフホストランナーでの実行は無料枠を消費しない）。
> PIT と k6 は実行時間が長いため、性能計測用に確保する専有ランナー（C-3）を
> **セルフホストランナーとして登録し、重いジョブを既定でそちらへ寄せる**ことで
> 無料枠の範囲に収める。ランナー種別と重量ジョブの実行可否はワークフローで
> 切り替えられる（7.1.1）。

未導入のツール（ミューテーションテスト、負荷試験、脆弱性スキャン、複雑度解析、
契約テスト、アクセシビリティ検査）は、quality-gate 導入に合わせて
対象リポジトリの CI に追加する必要がある。導入手順とサンプルワークフローは
quality-gate 側が提供物として用意する（FR-03）。

### 2.2 スコープ内

- 計測結果（CI 成果物）の受け取り・保管・正規化
- 合格ライン（しきい値）の定義・管理・版管理
- 合否判定と、判定根拠（個別違反）の保持
- ダッシュボード・トレンド・詳細ドリルダウンの提供
- 通知（メール）
- 免除（Waiver）の申請・承認・期限管理
- 認証・認可、監査ログ

### 2.3 スコープ外（将来検討）

- 計測ジョブの自前実行（リポジトリを clone してビルド・テストまで行う方式）
- PR の必須チェック化によるマージブロック（enforcement モード）
- 複数組織を収容するマルチテナント / 課金
- GitHub 以外のホスティング（GitLab、Bitbucket）対応
- 手動アクセシビリティ検査結果の取り込み

> 将来拡張としてスコープ外に置いた項目も、データモデルと API は拡張可能な形で設計する（8 章）。

## 3. 全体方針

### 3.1 計測の実行方式：CI 成果物の取り込み型

```
┌──────────────────────── 対象リポジトリ (GitHub) ────────────────────────┐
│  GitHub Actions                                                          │
│   ├ JUnit + JaCoCo      → jacoco.xml                                     │
│   ├ Vitest + coverage   → lcov.info / coverage-final.json                │
│   ├ PIT (pitest)        → mutations.xml                                  │
│   ├ k6                  → summary.json                                   │
│   ├ Trivy / Semgrep ほか → SARIF                                          │
│   ├ PMD / ESLint        → SARIF / JSON                                   │
│   ├ Pact / Schemathesis → JUnit XML / pact verification JSON             │
│   └ axe-core (Playwright) → axe-results.json                             │
│                                                                          │
│   quality-gate-action（提供物）が上記をまとめて送信                       │
└──────────────────────────────┬───────────────────────────────────────────┘
                               │ HTTPS / Ingest Token
                               ▼
┌──────────────────────── quality-gate ────────────────────────────────────┐
│  取り込み (Ingest) → 正規化 (Normalize) → 評価 (Evaluate)                 │
│                    → 可視化 (Visualize) → 通知 (Notify)                   │
└──────────────────────────────────────────────────────────────────────────┘
```

この方式を採る理由:

- Testcontainers・負荷試験・ブラウザ自動操作はいずれも Docker と専用環境を要求する。
  それらの実行責務を対象リポジトリの CI に残すことで、quality-gate 側に
  Docker-in-Docker、ビルドツールチェーン、対象リポジトリの認証情報を持ち込まずに済む
- 対象リポジトリの言語・ビルド構成の差異を quality-gate が吸収しなくてよい
- quality-gate の停止が対象リポジトリの CI を止めない（疎結合）

代償として次の制約を受け入れる。これらは要件として明示的に扱う。

| 制約 | 対処 |
| --- | --- |
| 計測条件（マシンスペック等）を quality-gate が統制できない | 計測メタデータの提出を必須化し、条件が変わった Run は系列を分ける（FR-04） |
| CI 側の設定次第でレポートが提出されない | 申告のない未提出は「不合格（fail-closed）」として扱う。意図的なスキップは申告制とし、ERROR と区別する（6.4） |
| 提出値の真正性を完全には保証できない | Ingest Token をリポジトリ単位で発行し、提出元コミット SHA と突合する |

### 3.2 運用方針：可視化・通知に徹する

本フェーズでは **PR のマージをブロックしない**。理由は、合格ラインの妥当性が
実績で検証されていない段階でブロックを始めると、しきい値の一時緩和や
チェックのスキップが常態化し、ゲート自体が形骸化するため。

段階的に次の順で強度を上げる想定とする。

1. **Phase 1（本要件の範囲）** — 計測・可視化・通知のみ。合否は「情報」として提示
2. **Phase 2** — GitHub Check Run を `neutral` で出力し、PR 上でも合否が見える状態にする
3. **Phase 3（スコープ外）** — 必須チェック化し、不合格でマージ不可にする

判定ロジックと合否そのものは Phase 1 から本番同等に動かす。Phase 3 で追加されるのは
「ブロックするかどうか」の一点だけであり、そのための設定項目
（`enforcement: report-only | check-run | blocking`）は Phase 1 から持つ。

## 4. 利用者とユースケース

### 4.1 ロールと権限

対象が 1 リポジトリ・利用者が数名の規模であるため、**Phase 1 ではロールを 2 種に絞る**。

| ロール | 想定者 | 権限 |
| --- | --- | --- |
| Viewer | 参照のみの関係者（PO、QA など） | ダッシュボード・Run 詳細・トレンド・免除記録の閲覧 |
| Admin | 開発者・基盤管理者 | 全操作（リポジトリ登録、しきい値変更、免除の登録、Run の再評価、ユーザー管理、Ingest Token 管理、監査ログ閲覧、保持期間設定） |

#### 将来の拡張（利用者増加時）

利用者が増え、免除の判断を一人で完結させるべきでなくなった時点で、
次の 4 ロール構成へ拡張する。データモデルとロール判定は初めから拡張可能な形で実装し、
ロールの追加が画面と権限定義の追加のみで済むようにする。

| ロール | 権限 |
| --- | --- |
| Viewer | 閲覧のみ |
| Developer | Viewer + 免除の申請、Run の再評価 |
| Maintainer | Developer + リポジトリ登録、しきい値変更、**免除の承認** |
| Admin | Maintainer + ユーザー/ロール管理、Ingest Token 管理、監査ログ閲覧、保持期間設定 |

認証に GitHub（個人アカウント）を用いるため、**Organization のメンバーシップや Team を
ロールのマッピング元にできない**。そのため、ロールは quality-gate 内で個別に付与する
（FR-13-4）。

### 4.2 主要ユースケース

| UC | 利用者 | シナリオ |
| --- | --- | --- |
| UC-01 | Admin | リポジトリを登録し、Ingest Token を発行して CI に設定する |
| UC-02 | Admin | main への push 後、CI が計測結果を送信し、判定結果が自動生成される |
| UC-03 | Admin | 自分の PR の計測結果を Run 詳細で確認し、不合格の原因（どの関数、どの CVE、どのページ）を特定する |
| UC-04 | 全員 | 朝の定例でダッシュボードを開き、全リポジトリの合否と 30 日推移を確認する |
| UC-05 | Admin | 修正版が未提供の High 脆弱性について、理由と期限を記録して免除を登録する |
| UC-06 | 全員 | 現在有効な免除の一覧を確認し、期限切れが近いものを把握する |
| UC-07 | 全員 | 不合格に遷移した時点でメール通知を受け取り、当日中に対応する |
| UC-08 | Admin | 合格ラインを引き上げ（例: カバレッジ 75% → 80%）、その影響を過去 Run で試算する |
| UC-09 | Admin | 新規 CVE の公開により、コード変更なしで判定が変わったことを日次再評価で検知する |
| UC-10 | QA | リリース判定会議のために、特定タグ時点の品質レポートを出力する |

## 5. 機能要件

凡例: **必須** = Phase 1 で必須 / **推奨** = Phase 1 で可能なら / **Phase 2** = 次フェーズ

### 5.1 リポジトリ・設定管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-01-1 | GitHub リポジトリを識別子（`owner/repo`）で登録・一覧・無効化できる | 必須 |
| FR-01-2 | リポジトリに「バックエンド」「フロントエンド」等のコンポーネントを定義し、指標をコンポーネント単位で扱える | 必須 |
| FR-01-3 | 監視対象ブランチ（既定: `main`）と、PR 計測の対象可否を設定できる | 必須 |
| FR-01-4 | リポジトリごとに Ingest Token を発行・失効・ローテーションできる。トークンは発行時のみ平文表示し、以後はハッシュのみ保持する | 必須 |
| FR-02-1 | 合格ライン等の設定をリポジトリ内の `.quality-gate.yml` から取り込む（Configuration as Code） | 必須 |
| FR-02-2 | `.quality-gate.yml` をスキーマ検証し、不正な場合は取り込みを拒否して理由を提示する | 必須 |
| FR-02-3 | UI からも設定を編集でき、リポジトリ内ファイルと UI 設定の優先順位が明確である（既定: ファイル優先） | 推奨 |
| FR-02-4 | 設定は版として保存され、各 Run は「どの版の設定で判定されたか」を保持する（判定の再現性） | 必須 |
| FR-02-5 | 設定変更が過去 Run の判定に与える影響をシミュレーションできる（再判定のドライラン） | Phase 2 |

### 5.2 計測結果の取り込み

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-03-1 | Ingest API で Run を開始し、複数の成果物ファイルを添付し、確定（finalize）できる | 必須 |
| FR-03-2 | Run には コミット SHA、ブランチ、PR 番号、実行者、CI 実行 URL、計測日時を必須メタデータとして付与する | 必須 |
| FR-03-3 | 性能計測の成果物には 計測環境（ランナー種別、CPU/メモリ、対象環境名、データ量）を必須メタデータとして付与する | 必須 |
| FR-03-4 | GitHub Actions 用の composite action（`quality-gate-action`）と、ランナー種別を切り替えられるワークフローのサンプル（7.1.1）を提供する | 必須 |
| FR-03-5 | CLI（単一バイナリ / jar）を提供し、Actions 以外の CI からも送信できる | 推奨 |
| FR-03-6 | 同一コミット SHA に対する再送信は、既存 Run を上書きせず新しい試行として記録する | 必須 |
| FR-03-7 | 取り込み失敗（形式不正、サイズ超過、トークン不正）は理由を構造化して返し、CI 側のログで原因が分かる | 必須 |
| FR-03-8 | 1 ファイルあたり 50MB、1 Run あたり 200MB を上限とし、超過時は明示的にエラーとする | 必須 |
| FR-03-9 | Run 作成時に、CI が実行しなかった指標を `skippedMetrics`（指標 ID と理由）として申告できる | 必須 |

### 6.1 指標一覧

| ID | カテゴリ | 指標 | 合格ライン | 主な入力 |
| --- | --- | --- | --- | --- |
| M-01 | 機能テスト | ブランチカバレッジ | 75% 以上（backend / frontend 各々） | JaCoCo XML、Vitest lcov/istanbul |
| M-02 | 機能テスト | ミューテーションスコア | 60% 以上（**backend のみ**） | PIT XML |

| M-05 | 性能テスト | エラー率（副指標） | 0.1% 以下 | k6 summary JSON |

| M-07 | コード構造 | 循環的複雑度 15 超の新規関数数 | 0 件 | PMD / ESLint / lizard |

| M-10 | 使いやすさ | アクセシビリティ重大違反件数 | 0 件（impact: critical / serious） | axe-core JSON |

### 6.2 指標単位の判定ステータス

| ステータス | 意味 |
| --- | --- |
| PASS | 実測値が合格ラインを満たす |
| WARN | 合格ラインは満たすが、注意水準（既定: 合格ラインから 5% 以内、または前回比で悪化）に該当 |
| FAIL | 実測値が合格ラインを満たさない |
| SKIP | 計測していない。次のいずれか。(a) 設定で `enabled: false` としている (b) CI が**スキップを申告**した（6.5） |
| REFERENCE | 値は取得したが、計測条件が統制外のため**判定に用いない**（参考値）。性能指標を GitHub ホストランナーで計測した場合など |
| ERROR | 提出されるはずの成果物が未提出、または形式不正で値を確定できない |
| NOT_APPLICABLE | ツールの制約により、そのコンポーネントでは**測りようがない**（対象外）。M-02 の frontend（PIT は JVM 専用）など |

`SKIP` と `ERROR` の区別は本システムの根幹にあたる。
**「意図して測らなかった」と「測ったつもりが届いていない」は別物**であり、
後者を見逃すと計測の破綻に気づけない。区別の方法は 6.5 に定める。

### 6.3 Run 全体の集約ルール

```
FAIL が 1 つ以上          → Run = FAIL
ERROR が 1 つ以上          → Run = FAIL   （既定。fail-closed）
上記なし かつ WARN が 1 つ以上 → Run = PASS_WITH_WARNINGS
上記いずれもなし            → Run = PASS
SKIP / REFERENCE / NOT_APPLICABLE は集約に影響しない（ただし件数を UI に明示）
```

`ERROR → FAIL` の既定は **fail-closed**（計測できていないものを合格扱いしない）とする。
導入移行期間に限り、リポジトリ設定で `on_missing_report: warn` に緩和できるが、
緩和は期限付き（最長 90 日）とし、ダッシュボードに常時表示する。

### 6.3.1 完全計測と部分計測

`SKIP` または `REFERENCE` を 1 つ以上含む Run は **部分計測（PARTIAL）** として記録し、
全指標を判定できた Run（**完全計測**）と区別する。
`NOT_APPLICABLE` は部分計測の理由にしない。測りようのないものを積み残しに数えると、
どの Run も完全計測にならず、部分計測の警告が意味を失うためである。

部分計測の Run が PASS でも、それは「測った範囲では合格」を意味するに過ぎない。
そのため次を必須とする。

- Run 詳細に「部分計測（未計測 N 件）」を明示し、未計測の指標名と理由を併記する
- ダッシュボードには最新 Run とは別に「**最後の完全計測**」を常に表示する
- トレンドグラフ上、スキップした指標の点は 0 ではなく**欠測（線を繋がない）**として描画する

### 6.4 スキップの申告と、その濫用を防ぐ仕組み

CI 側でジョブを実行しないことを選べる以上（[7.1.1](#711-github-actions-ワークフローの構成)）、
quality-gate はそれを ERROR と区別できなければならない。一方で、CI が自由にスキップを
申告できると fail-closed の原則が骨抜きになる。両立のため次の 4 点を定める。

**1. スキップは明示的に申告する**

CI は Run 作成時に、実行しなかった指標を `skippedMetrics` として申告する（7.1）。
申告のない指標の成果物が届かなかった場合は、従来どおり `ERROR` とする。
申告なしの未提出を黙って許容してはならない。

**2. スキップを許容する指標は設定で限定する**

`.quality-gate.yml` の `execution.skippable_metrics` に列挙した指標だけがスキップ可能。
列挙されていない指標のスキップ申告は `ERROR` として扱う。
これにより「脆弱性スキャンをスキップした」といった申告は通らない。

**3. 部分計測であることを隠さない**

6.3.1 のとおり、部分計測の Run は完全計測と明確に区別して表示する。

**4. 完全計測が途絶えたら警告する**

`execution.full_measurement_interval_days`（既定 7 日）を超えて完全計測が行われない場合、
ダッシュボードに警告を表示し、通知する（FR-06-3）。
スキップが常態化して指標が事実上廃止される事態を、これで検知する。

### 6.5 設定ファイル（`.quality-gate.yml`）の例

```yaml
version: 1
enforcement: report-only          # report-only | check-run | blocking（Phase 3）
on_missing_report: fail           # fail | warn（期限付き緩和時のみ warn）

execution:
  # CI がスキップを申告できる指標。ここに無い指標のスキップ申告は ERROR とする
  skippable_metrics: [mutation_score, performance]
  # 完全計測がこの日数を超えて行われない場合に警告する
  full_measurement_interval_days: 7
  # この環境で計測された性能値は参考値（REFERENCE）とし、判定に用いない
  reference_only_environments: [github-hosted]

components:
  - name: backend
    language: java
    paths: ["backend/**"]
  - name: frontend
    language: typescript
    paths: ["frontend/**"]

exclusions:                       # 全指標共通の計測除外
  - "**/generated/**"
  - "**/*.config.ts"
  - "backend/**/dto/**"

metrics:
  branch_coverage:
    enabled: true
    threshold: 75                 # %
    scope: overall                # overall | diff
    per_component: true           # コンポーネントごとに判定
  mutation_score:
    enabled: true
    threshold: 60                 # %
    scope: changed                # all | changed（差分クラスのみ）
    components: [backend]         # PIT を用いるため Java のみ。frontend は対象外
  performance:
    enabled: true
    p95_ms: 500
    arrival_rate_rps: 50          # 負荷条件（到達率）。この負荷下で p95 / エラー率を判定する
    error_rate_pct: 0.1
    scenarios: ["login", "search", "order-create"]
  vulnerabilities:
    enabled: true
    max_critical: 0
    max_high: 0
    max_medium: null              # 判定対象外（可視化のみ）
  cyclomatic_complexity:
    enabled: true
    max_complexity: 15
    scope: new_and_modified       # 新規追加 + 変更で悪化した関数のみ
    warn_from: 11
  api_contract:
    enabled: true
    min_success_rate: 100         # %
    min_test_count: 1             # 0 件なら FAIL（空実行の検知）
    breaking_changes: 0
  accessibility:
    enabled: true
    standard: wcag22aa
    max_critical: 0               # axe impact: critical + serious
    pages: ["/", "/login", "/orders", "/orders/new", "/settings"]

notifications:
  on: transition_to_fail          # always | transition_to_fail | any_fail | never
  email: ["team-platform@example.com"]
```


#### 7.1.1 GitHub Actions ワークフローの構成

ランナー種別と、重いジョブ（PIT / k6）の実行可否を**ワークフロー側で切り替えられる**構成とする。
提供するサンプルワークフローは次の形を取る。

```yaml
# .github/workflows/quality-gate.yml
on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:
    inputs:
      runner:
        description: 実行するランナー
        type: choice
        options: [self-hosted, ubuntu-latest]
        default: self-hosted
      run_heavy_jobs:
        description: GitHub ホストランナーでも PIT / k6 を実行する
        type: boolean
        default: false

env:
  # 定期実行・PR では リポジトリ変数 QG_RUNNER を既定値として使う
  RUNNER: ${{ inputs.runner || vars.QG_RUNNER || 'self-hosted' }}
  RUN_HEAVY: ${{ inputs.run_heavy_jobs || vars.QG_RUN_HEAVY_ON_GITHUB || 'false' }}

jobs:
  # 軽量ジョブ: 常に実行する
  base:
    runs-on: ${{ needs.setup.outputs.runner }}
    # ビルド、JUnit、Vitest、JaCoCo、Trivy、Semgrep、gitleaks、PMD、ESLint、
    # 契約テスト、axe-core

  # 重量ジョブ: ランナー種別と設定で実行可否が決まる
  mutation:
    # セルフホストなら常に実行。GitHub ホストなら RUN_HEAVY が true のときだけ
    if: env.RUNNER == 'self-hosted' || env.RUN_HEAVY == 'true'
    runs-on: ${{ env.RUNNER }}
    # PIT

  performance:
    if: env.RUNNER == 'self-hosted' || env.RUN_HEAVY == 'true'
    runs-on: ${{ env.RUNNER }}
    # k6

  submit:
    needs: [base, mutation, performance]
    if: always()
    # 実行されなかったジョブに対応する指標を skippedMetrics として申告したうえで送信
```

切り替えの手段は 2 通りとする。

| 手段 | 用途 |
| --- | --- |
| リポジトリ変数（`QG_RUNNER`、`QG_RUN_HEAVY_ON_GITHUB`） | 常用の既定値。セルフホストランナーが停止している期間などに変更する |
| `workflow_dispatch` の入力 | その回限りの上書き。手動で一度だけ全量を回したい場合など |

**重要**: `submit` ジョブは `if: always()` とし、重量ジョブが実行されなかった場合でも
**必ず実行して `skippedMetrics` を申告する**こと。送信自体を行わないと、
quality-gate から見れば Run が存在せず、スキップと計測失敗の区別がつかない。

### 7.2 参照 API（UI / 外部 → quality-gate）

GitHub OAuth ログイン後のセッション（またはそこから発行したアクセストークン）で認証する REST API。
リポジトリ一覧、Run 一覧・詳細、指標時系列、Finding 一覧、Waiver 操作を提供する。
仕様は springdoc により OpenAPI として自動生成・公開し、quality-gate 自身の
契約テスト対象とする。

### 7.3 GitHub 連携

**単一の GitHub App** を登録し、ユーザーログインとリポジトリアクセスの双方をこれで賄う。
OAuth App を別に用意する必要はない（GitHub App は user-to-server 認可フローを持つ）。

| 用途 | 方式 | 権限 |
| --- | --- | --- |
| ユーザーログイン（FR-13-1） | GitHub App の user-to-server 認可フロー | ユーザー識別（`read:user`相当）のみ |
| `.quality-gate.yml` の取得 | GitHub App の Contents: Read | 読み取りのみ |
| `baseCommitSha` の解決（merge-base） | GitHub App の Contents: Read | 読み取りのみ |
| ~~PR サマリコメント（FR-11-4）~~ | —（v1.2 で不採用。D-15） | — |
| Check Run 出力（Phase 2） | GitHub App の Checks: Write | 書き込み |

GitHub App の権限は上記に限定し、コードのクローンやワークフローの起動権限は付与しない。

GitHub App の登録・インストールは**個人アカウント（GitHub Free）で追加費用なく可能**である。
App を private として登録すれば、所有アカウント自身のリポジトリにのみインストールできる。

> **認可上の注意**: Organization を使用しないため、「組織のメンバーであること」を
> ログインの条件にできない。GitHub アカウントを持つ任意のユーザーが OAuth フロー自体は
> 完了できてしまうため、**quality-gate 側の許可リスト（FR-13-4）が実質的な入口の
> アクセス制御となる**。この許可リストは省略できない。

## 8. データモデル（主要エンティティ）

| エンティティ | 説明 | 主な属性 |
| --- | --- | --- |
| `Repository` | 計測対象リポジトリ | owner, name, defaultBranch, enabled |
| `Component` | リポジトリ内の構成単位 | repositoryId, name, language, pathPatterns |
| `GateConfig` | 合格ライン等の設定。版管理される | repositoryId, version, sourceType(file/ui), rawYaml, effectiveFrom |
| `Run` | 1 回の計測・判定の単位 | repositoryId, commitSha, baseCommitSha, branch, prNumber, status, verdict, gateConfigId, measuredAt |
| `Artifact` | 取り込んだ元成果物 | runId, type, filename, sizeBytes, storageKey, sha256 |
| `Measurement` | 指標ごとの実測値と判定 | runId, componentId, metricId, value, threshold, status, previousValue |
| `Finding` | 個別違反（脆弱性 / 複雑度超過関数 / 失敗テスト / a11y 違反） | runId, metricId, fingerprint, severity, title, filePath, line, detail(JSON), waiverId |
| `Waiver` | 免除 | repositoryId, fingerprint, scope, reason, createdBy, approvedBy（将来の承認フロー用。Phase 1 では createdBy と同値）, expiresAt, status（`active` / 将来 `pending` / `rejected`） |
| `IngestToken` | リポジトリ単位の取り込みトークン | repositoryId, tokenHash, createdBy, lastUsedAt, revokedAt |
| `User` / `RoleAssignment` | 利用者と権限 | subject, email, displayName, role |
| `AuditLog` | 監査ログ（追記のみ） | actor, action, targetType, targetId, before, after, occurredAt |
| `Notification` | 通知の送信履歴 | runId, channel, status, sentAt |

**`Finding.fingerprint`** は違反を Run をまたいで同定するためのキーであり、
「新規発生 / 継続 / 解消」の判定と、免除の紐付けに用いる。
指標ごとの fingerprint 定義は [02-metrics-spec.md](02-metrics-spec.md) に記載する。

## 10. 非機能要件

### 10.1 性能

| 項目 | 目標 |
| --- | --- |
| ダッシュボード初期表示 | p95 1.0 秒以内（リポジトリ 50 件、Run 10 万件想定） |
| Run 詳細表示 | p95 1.5 秒以内 |
| トレンド API（30 日 / 1 指標） | p95 800ms 以内 |
| 成果物取り込み（finalize 後の判定完了まで） | 中央値 60 秒以内、p95 5 分以内 |
| 同時取り込み | 10 Run まで劣化なく処理 |

### 10.2 規模想定

| 項目 | 初期 | 3 年後 |
| --- | --- | --- |
| 対象リポジトリ数 | 1 | 5 |
| 1 日あたり Run 数 | 10〜30 | 100 |
| 累積 Run 数 | 1 万（1 年） | 10 万 |
| 成果物ストレージ | 10 GB | 50 GB |
| 同時利用ユーザー数 | 数名 | 20 |

初期規模は小さく、性能・可用性の要求は緩い。この規模では
**PostgreSQL 1 台 + アプリ 1 プロセスの Docker Compose 構成で十分**であり、
水平スケール、専用メッセージキュー、キャッシュ層はいずれも不要である。
データモデルと API は将来のリポジトリ追加に耐える形にしておくが、
**インフラを先回りして複雑にはしない**。

### 10.3 可用性・信頼性

- 稼働率 99.5%（社内業務時間帯基準）。計画停止は事前告知の上で業務時間外に実施
- quality-gate の障害が対象リポジトリの CI を失敗させないこと。
  送信失敗時、CI 側は警告ログを残して処理を継続する（`continue-on-error` 相当）
- 取り込み API は冪等性キー（`repository + commitSha + attempt`）により、CI のリトライで
  重複 Run を作らない
- データベースは日次バックアップ、RPO 24 時間 / RTO 4 時間

### 10.4 セキュリティ

- 通信はすべて TLS 1.2 以上
- Ingest Token・IdP クライアントシークレットは暗号化して保管し、
  平文でログ出力しない
- Ingest Token は発行時のみ平文を表示し、以後は照合可能なハッシュのみ保持する
- GitHub App の権限は 7.3 の最小限に限定する
- 取り込んだ成果物にはソースコード断片・環境情報が含まれうるため、
  閲覧権限は当該リポジトリの閲覧権限に従う
- アップロードファイルはサイズ上限・MIME 検証・XML 外部実体参照（XXE）無効化を徹底する
- 依存ライブラリの脆弱性は quality-gate 自身の CI で継続的に検査する

### 10.5 運用・可観測性

- ヘルスチェック（`/actuator/health`）、メトリクス（Micrometer → Prometheus）を提供
- 構造化ログ（JSON）に相関 ID（runId、requestId）を付与
- 主要アラート: 取り込み失敗率の上昇、判定ジョブの滞留、日次バッチの失敗、ストレージ逼迫
- データ保持: Run メタデータ・指標値 2 年 / 元成果物 90 日 / 監査ログ 2 年（いずれも設定可能）

### 10.6 アクセシビリティ

quality-gate 自身が WCAG 2.2 Level AA に適合する。具体的には、
キーボードのみで全機能を操作でき、フォーカスが常に可視で、
グラフは表形式の代替表現を併せ持ち、axe-core の critical / serious 違反が 0 件であること。

### 10.7 保守性

- quality-gate 自身を quality-gate で計測し、本要件が定める全指標に合格する（ドッグフーディング）
- 新しい指標・新しいツールフォーマットの追加が、アダプタ実装の追加のみで完結する構造とする

### 11.1 技術スタック

技術スタックは確定済み。選定理由・バージョン方針・採用しなかった選択肢を含む詳細は
**[04-tech-stack.md](04-tech-stack.md)** に定める。本節は要約のみ示す。

| レイヤ | 採用技術 | 備考 |
| --- | --- | --- |
| バックエンド | **Java 25 LTS** + Spring Boot 4 + **Maven** | 計測対象と同一構成。ドッグフーディングが成立する |
| Web 層 | Spring MVC + 仮想スレッド | 取り込みは I/O 中心。リアクティブ導入の複雑さを避ける |
| 認証・認可 | Spring Security（OAuth2 Client: GitHub） | GitHub App の user-to-server フローでログイン。セッション Cookie。許可リストと RBAC は quality-gate 内で管理 |
| 永続化 | Spring Data JPA + **PostgreSQL 17** | 時系列は通常テーブル + 適切なインデックスで足りる規模 |
| スキーマ管理 | Flyway | |
| 非同期処理 | DB ベースのジョブキュー（アウトボックス） + `@Scheduled` | 単一プロセス構成のため ShedLock は不要 |
| 成果物ストレージ | **ローカルファイルシステム**（`ArtifactStore` インタフェース経由） | この規模ではオブジェクトストレージは過剰。将来 S3 互換へ差し替え可能な形にする |
| API 仕様 | springdoc-openapi | 生成した `api/openapi.yml` をリポジトリにコミットし、契約テストと M-09 の基準にする |
| フロントエンド | Vue 3 + TypeScript + Vite + **PrimeVue** + Pinia + Vue Router | 計測対象と同一構成 |
| フロント / API 連携 | **openapi-typescript + openapi-fetch** | `openapi.yml` から型を生成。生成物の同期は CI で検証する |
| SPA の配信 | **Spring Boot に同梱（同一オリジン）** | CORS 不要。認証を HttpOnly セッション Cookie で完結できる |
| グラフ | PrimeVue `Chart`（Chart.js） | canvas は読み上げできないため、表形式の代替表現の併設を実装要件とする |
| テスト | JUnit 5 / Testcontainers / Vitest / Playwright（+ axe-core） | |
| 開発環境 | WSL2 + Docker Compose | リポジトリは WSL2 の Linux ファイルシステム側に置く |
| 配布 | Docker イメージ + Docker Compose | 社内単一テナントのため小さく始める |

### 11.2 モジュール構成（バックエンド）

```
quality-gate/
├ backend/
│  ├ ingest/        取り込み API、トークン認証、成果物保管
│  ├ adapter/       ツール別パーサ（jacoco, pit, stryker, k6, sarif, pmd, eslint, pact, axe, oasdiff）
│  ├ normalize/     正規化モデルへの変換、重複排除、fingerprint 生成
│  ├ evaluate/      しきい値適用、指標判定、Run 集約、差分（新規/解消）算出
│  ├ config/        .quality-gate.yml の取得・検証・版管理
│  ├ waiver/        免除の登録・期限管理（承認フローは将来拡張）
│  ├ notify/        メール通知
│  ├ query/         ダッシュボード・トレンド向け参照 API（読み取り最適化）
│  └ platform/      認証認可、監査ログ、スケジューラ、ArtifactStore（ストレージ抽象）
└ frontend/         Vue 3 SPA
```

設計上の要点:

- **アダプタ層の独立** — ツールの追加・差し替えが `adapter/` の追加のみで完結する。
  正規化モデルはツール中立であり、ツール固有の概念を上位層に漏らさない
- **判定の再現性** — Run は「取り込んだ実測値」と「適用した設定版」を保持するため、
  再評価はいつでも決定的に再実行できる
- **取り込みと判定の分離** — finalize は取り込み完了を返すだけとし、
  重い正規化・判定は非同期で行う。CI を待たせない

| C-1 | 計測ツールの実行は対象リポジトリの CI が行う。quality-gate はコードをクローンしない |
| C-2 | 未導入のツール（PIT、k6、Trivy / Semgrep、PMD、Pact、axe-core）は対象リポジトリ側での導入が必要 |

| C-5 | ミューテーションテストは実行時間が長いため、既定では変更クラスに限定する（M-02） |

| C-7 | 単一テナント（社内専用）構成。インターネット公開は行わない |

| C-9 | プライベートリポジトリの GitHub Actions は月 2,000 分の無料枠。重いジョブ（PIT、k6）は既定でセルフホストランナーで実行し、無料枠を消費しない構成とする。ランナー種別と重量ジョブの実行可否はワークフローで切り替えられる（7.1.1） |

| C-12 | 本フェーズではマージブロックを行わない。不合格の是正は運用ルールに依存する |
| C-13 | SPA は Spring Boot に同梱して同一オリジンで配信する。フロントエンドのみを独立してデプロイすることはしない |

## 13. リスクと対策

本章はプロダクト・運用上のリスクを扱う。
技術選定に伴うリスク（PIT の Java 25 対応、生成物の同期漏れ など）は
[04-tech-stack.md](04-tech-stack.md) 9 章に分けて記載する。

| # | リスク | 影響 | 対策 |
| --- | --- | --- | --- |
| R-1 | 性能計測値が実行環境のノイズで変動し、合否が安定しない | ゲートが信用されなくなる | 専有環境 + ウォームアップ除外 + 3 回実行の中央値採用（M-03） |
| R-2 | 既存コードの水準が低く、初日から全リポジトリが不合格になる | 導入が頓挫する | 対象リポジトリは既にベースラインが整っているため、絶対値しきい値を当初から適用する。新規リポジトリを追加する際は、登録前にベースラインを計測し、乖離があればしきい値を個別設定する |
| R-3 | PIT の実行時間で CI が長時間化する | 開発速度の低下 | 変更クラス限定（`scope: changed`）を既定とし、全量は夜間バッチで週次実行 |
| R-4 | 新規 CVE 公開により、コード変更なしで不合格に転じる | 突然の不合格に混乱 | 日次再評価（FR-12-1）と通知で予見可能にし、免除の仕組みで運用を吸収 |
| R-5 | ツールの severity 表記がばらつき「High」の定義が揺れる | 判定の信頼性低下 | CVSS スコアへの正規化マッピングを明文化し、設定として可視化（M-06） |
| R-6 | 免除が乱発され、実質的に無効なゲートになる | 形骸化 | 期限必須（最長 90 日、無期限は登録不可）、理由の必須入力、実施者の記録、免除件数のダッシュボード常時表示。承認フローがない分、**免除件数の可視性で抑止する** |
| R-7 | 可視化のみで是正されない | 品質が改善しない | 週次で不合格リポジトリをレビューする運用を定め、Phase 2/3 で強度を上げる |
| R-8 | 許可リストの設定漏れにより、意図しない GitHub ユーザーがログインできてしまう | 情報漏洩 | 既定を「拒否」とし、許可リストに存在しないユーザーは認証成功後も一律拒否する。追加操作は監査ログに記録する |
| R-9 | GitHub Actions の無料枠（月 2,000 分）を超過し、計測が止まる | 計測の途絶 | 重いジョブを既定でセルフホストランナーへ寄せる。加えて、48 時間計測が途絶えた場合にダッシュボードへ警告を出す（FR-06-2）ことで、無料枠切れに気づける |
| R-10 | 重量ジョブのスキップが常態化し、M-02 と M-03〜05 が事実上廃止される | 指標の形骸化 | スキップを申告制とし、部分計測を完全計測と区別して表示する。完全計測が 7 日途絶えたら警告・通知する（FR-06-3）。スキップ可能な指標は設定で限定する（6.4） |
| R-11 | セルフホストランナーの停止に気づかず、計測が止まる | 計測の途絶 | ランナー種別をリポジトリ変数で切り替えられるようにし、停止時は GitHub ホストへ退避できる。退避中は部分計測として可視化される |
| R-12 | frontend のミューテーションスコアを計測しないため、Vue 側のテストの実効性が検証されない | フロント側のテスト品質が見えない | frontend は M-01 ブランチカバレッジで担保し、必要に応じて Phase 4 で Stryker の導入を検討する |
| R-13 | 「新規関数」の同定がリファクタリング（移動・リネーム）で誤検知する | 開発者の不信 | git の rename 検出を用い、誤検知を免除ではなく判定ロジックの修正で潰す（M-07） |

### Phase 1 — MVP（本要件の中核）

取り込み → 判定 → 可視化の縦串を最小構成で通す。

- マルチテナント対応

## 15. 受け入れ基準

本要件の達成は次をもって確認する。

| # | 基準 |
| --- | --- |
| A-1 | 対象リポジトリの CI から成果物を送信すると、5 分以内に Run 詳細で 6 カテゴリの判定が確認できる |
| A-2 | 各指標について、合格ラインをまたぐ値を人為的に作り、PASS / FAIL が仕様どおり切り替わることを確認できる |
| A-3 | 成果物を未提出にした場合、既定設定で当該指標が ERROR となり Run 全体が FAIL になる |
| A-4 | 同一 Run を再評価すると、同じ設定版の下で同じ判定結果が再現される |
| A-5 | 免除を登録すると判定から除外され、期限超過後は自動的に再カウントされる。登録・失効が監査ログに残る |
| A-6 | 合格→不合格の遷移時に、設定したチャネルへ 5 分以内に通知が到達する |
| A-7 | quality-gate 自身を quality-gate で計測し、全指標が合格する |
| A-8 | quality-gate の主要 9 画面について、axe-core の critical / serious 違反が 0 件である |
| A-9 | 監査対象操作がすべて監査ログに記録され、Admin が検索・確認できる |
| A-10 | GitHub ホストランナーで PIT / k6 をスキップして送信した Run が、ERROR ではなく `SKIP` として記録され、部分計測と表示される |
| A-11 | `execution.skippable_metrics` に含まれない指標のスキップを申告すると `ERROR` となり、Run が FAIL になる |
| A-12 | GitHub ホストランナーで計測した性能値が `REFERENCE` として記録され、判定に影響せず、トレンド上で専有ランナーの系列と分離される |
| A-13 | 完全計測が 7 日間行われない状態で、ダッシュボードに警告が表示され通知が送られる |

## 16. 用語定義

| 用語 | 定義 |
| --- | --- |
| Run | 1 つのコミットに対する 1 回の計測・判定の単位 |
| Finding | 判定の根拠となる個別の違反（脆弱性 1 件、複雑度超過関数 1 つ、失敗した契約テスト 1 件 など） |
| fingerprint | Finding を Run をまたいで同一と見なすためのキー。新規 / 継続 / 解消の判定に用いる |
| Waiver | 個別 Finding を期限付きで判定対象から除外する仕組み（免除） |
| ゲート（Gate） | 指標としきい値の集合。合格ラインの定義そのもの |
| ベースライン | 導入時点の実測値。しきい値の妥当性確認と、新規リポジトリ追加時の判断に用いる |
| fail-closed | 計測できなかった場合に「合格」ではなく「不合格」と扱う方針 |
| ドッグフーディング | quality-gate 自身を quality-gate の計測対象とすること |
