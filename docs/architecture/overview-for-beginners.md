# はじめての人向け: quality-gate のしくみ

quality-gate が like-chatgpt をどうやって計測しているのかを、GitHub Actions やランナーに詳しくない人向けに説明します。
次の 4 つの疑問に答えることを目標にしています。

1. 2 つのリポジトリ（quality-gate と like-chatgpt）は、どういう関係なのか
2. 「ランナー」「セルフホスト」とは何で、なぜ必要なのか
3. 誰が、どの鍵（認証情報）を使って、何をしてよいことになっているのか
4. 計測の中で、実際に何を測っているのか

設定の手順そのものは [収集ランナーで計測する](../operations/collector.md) にあります。
本書は「なぜそうなっているか」を理解するための読み物です。

---

## 1. たとえ話で全体をつかむ

健康診断にたとえると、登場人物は次のようになります。

| 健康診断 | quality-gate の世界 | 説明 |
| --- | --- | --- |
| 受診者 | **like-chatgpt**（計測対象のリポジトリ） | 測られる側。**何も準備しなくてよい** |
| 健診センター | **quality-gate**（リポジトリとアプリ） | 測り方の道具と、結果を判定・記録する仕組みを持つ |
| 検査技師 | **収集ランナー**（`collect` ワークフロー） | 受診者のところへ行き、検査をして、結果を受付に届ける |
| 検査室 | **セルフホストランナー**（あなたが用意したマシン） | 実際に検査（ビルド・テスト・解析）が行われる場所 |
| 基準値表 | **合格ライン**（画面 S-06 で保存した設定） | 「カバレッジ 75% 以上」などの判定基準 |
| 受付と医師 | **quality-gate のアプリ**（Ingest API と判定処理） | 検査結果を受け取り、基準値と比べて合否を出す |
| 健診結果の画面 | **ダッシュボード・Run 詳細** | 結果を見る場所 |

大事なのは、**受診者（like-chatgpt）は何もしなくてよい**という点です。
検査技師が必要な道具を持っていき、like-chatgpt の中身を写し取って、別の部屋で検査します。
like-chatgpt そのものには一切手を加えません。

## 2. 登場するもの（用語集）

先に用語をそろえておきます。あとの章で何度も出てきます。

| 用語 | ひとことで | 補足 |
| --- | --- | --- |
| リポジトリ | GitHub 上のプロジェクトの置き場 | 本書では quality-gate と like-chatgpt の 2 つ |
| GitHub Actions | GitHub の自動実行の仕組み | 「このボタンを押したら、この手順を実行する」を定義できる |
| ワークフロー | 自動実行の手順書 | `.github/workflows/*.yml` に書く。収集ランナーは `collect.yml`（入り口）と `collect-target.yml`（1 コミットの計測） |
| ジョブ | ワークフローの中の作業のまとまり | `collect.yml` は `plan` で対象を決め、1 コミットずつ `fetch` → `measure` → `submit` を実行する |
| ステップ | ジョブの中の 1 つ 1 つの命令 | 「clone する」「テストを実行する」など |
| **ランナー** | ジョブを**実際に実行するコンピューター** | GitHub が貸してくれるもの（GitHub ホスト）と、自分で用意するもの（セルフホスト）がある |
| シークレット / 変数 | ワークフローに渡す設定値 | シークレットは暗号化され、ログでは `***` に伏せられる |
| GitHub App | GitHub に登録した「アプリの身分証」 | quality-gate はこれでログインと、like-chatgpt の読み取りを行う |
| トークン | 「この人（アプリ）は○○してよい」という証明書 | 期限や権限の範囲が決まっている |
| Ingest API | quality-gate の「計測結果の受付窓口」 | `POST /api/v1/runs/...` |
| Run | 1 回分の計測と判定の記録 | 1 つのコミットを 1 回測ると 1 つの Run ができる |
| 成果物（アーティファクト） | 計測ツールが出力するファイル | `jacoco.xml`、`pmd.xml` など |
| 指標（M-01 など） | 何を測るかの項目 | 全 10 種類。いまは 5 種類を測る |
| head / base | 測るコミット / 比べる相手のコミット | 「どれだけ悪くなったか」を知るために base と比べる |

## 3. 全体像

```
 ┌──────────────────────────── GitHub（github.com）────────────────────────────┐
 │                                                                              │
 │   ymiyamoto63/quality-gate               ymiyamoto63/like-chatgpt            │
 │   ├ アプリのソース                        ├ アプリのソース                    │
 │   ├ .github/workflows/collect.yml        └ （計測用のものは何も置かない）    │
 │   ├ collector/（計測スクリプト）                    ▲                         │

 │            │                                        │  App のトークンで       │
 │            │ ①「このジョブを実行して」               │                         │
 │            │   （ランナーが取りに来る）              │     GitHub App          │
 │            ▼                                        │  （読み取り専用で        │
 └────────────┼────────────────────────────────────────┼── like-chatgpt に ──────┘
              │                                        │   インストール済み）
              │   ランナーから GitHub へ接続して         │
              │   仕事をもらいに行く（外向きの通信だけ）  │
 ┌────────────┼─────────── セルフホストランナーのマシン ─┼────────────────────────┐
 │            ▼                                        │                         │
 │   fetch   ──────────────────────────────────────────┘                         │
 │     │  like-chatgpt を写し取る                                                │
 │     ▼                                                                         │
 │   measure    テスト・解析（JaCoCo/PIT/Vitest/PMD/oasdiff/Trivy/axe）           │
 │     │        ※ 鍵は一切渡さない                                                │
 │     ▼                                                                         │
 │   submit  ────────────────────┐ ③計測結果を送る（Ingest Token）               │
 └───────────────────────────────┼───────────────────────────────────────────────┘
                                 ▼
 ┌──────────────────────── quality-gate のアプリ ───────────────────────────────┐
 │   Ingest API（受付） → 判定（合格ラインと比較） → PostgreSQL に保存           │
 │                                                     │                        │
 │   ダッシュボード / Run 詳細  ◀── ④ブラウザで見る（GitHub でログイン）          │
 └──────────────────────────────────────────────────────────────────────────────┘
```

矢印は 4 本だけです。

| # | 誰が → どこへ | 何をする | 使う鍵 |
| --- | --- | --- | --- |
| ① | ランナー → GitHub | 「実行するジョブはありますか」と取りに行く | ランナー登録時の資格情報（ランナーが自動で管理） |
| ② | ランナー → like-chatgpt | ソースを写し取る（読むだけ） | GitHub App が発行する 1 時間だけ有効なトークン |
| ③ | ランナー → quality-gate | 計測結果を送る | like-chatgpt 用の Ingest Token |
| ④ | あなたのブラウザ → quality-gate | 結果を見る | GitHub アカウントでのログイン |

**like-chatgpt から誰かへ向かう矢印は 1 本もありません。** like-chatgpt は読まれるだけです。

## 4. 2 つのリポジトリの関係

### 4.1 役割の分担

| | quality-gate | like-chatgpt |
| --- | --- | --- |
| 立場 | 測る側（健診センター） | 測られる側（受診者） |
| 持っているもの | アプリ本体、収集ワークフロー、計測スクリプト、ツールの版、計測プロファイル、鍵 | 自分のアプリのソースだけ |
| 計測のために必要な変更 | 計測プロファイルを 1 つ置く（`collector/targets/ymiyamoto63__like-chatgpt.env`） | **なし** |
| 設定する Secrets | App の秘密鍵、like-chatgpt の Ingest Token | **なし** |

### 4.2 「どう測るか」と「何を合格とするか」は別の場所にある

| 情報 | 置き場所 | 例 |
| --- | --- | --- |
| **どう測るか**（計測プロファイル） | quality-gate リポジトリの `collector/targets/ymiyamoto63__like-chatgpt.env` | バックエンドは `backend/` にある、Java 21 を使う、契約テストは `*ControllerTest` |
| **何を合格とするか**（合格ライン） | quality-gate アプリの画面（S-06）。控えは `collector/targets/ymiyamoto63__like-chatgpt.gate.yml` | カバレッジ 75% 以上、重大な脆弱性 0 件 |
| **測るツールの版** | quality-gate リポジトリの `collector/versions.env` | JaCoCo 0.8.15、PIT 1.20.4、PMD 7.17.0 |

like-chatgpt 自身の `.quality-gate.yml` やワークフロー（以前の方式の名残）は、収集ランナーでは**使いません**。
ただし like-chatgpt 側の CI が quality-gate への送信を続けていると、同じコミットの Run が 2 つでき、
その Run は like-chatgpt の `.quality-gate.yml` で判定されます（その間は画面 S-06 で設定を編集できません）。
like-chatgpt 側の CI 用の Ingest Token を quality-gate の管理画面で失効させれば、like-chatgpt に触らずに送信を止められます
（[対象の CI からの送信を止める](../operations/collector.md#対象の-ci-からの送信を止める)）。

### 4.3 like-chatgpt のコードは書き換えるのか

書き換えません。収集ランナーは like-chatgpt を**ランナーのマシンへ写し取り（clone）、その写しの中で**計測します。
計測のために写しの中へ部品を足すことはありますが（例: Vitest のカバレッジ部品を `npm install --no-save` で入れる）、
写しは計測が終わると削除され、GitHub 上の like-chatgpt には何も書き戻しません。
そもそも、渡しているトークンが**読み取り専用**なので、書き戻そうとしても GitHub が拒否します。

## 5. ランナーとセルフホスト

### 5.1 ランナーとは

ワークフローはただの手順書です。それを**実際に実行するコンピューター**がランナーです。

ランナーには 2 種類あります。

| | GitHub ホストランナー | セルフホストランナー |
| --- | --- | --- |
| 用意する人 | GitHub | **自分**（手元の PC、社内サーバー、WSL2 など） |
| ワークフローでの書き方 | `runs-on: ubuntu-latest` | `runs-on: self-hosted` |
| 料金 | private リポジトリは月 2,000 分まで無料 | 実行時間の制限なし（マシン代・電気代は自分持ち） |
| 実行後 | 毎回まっさらな環境に戻る | 前回のファイルやキャッシュが残る |
| 届く先 | インターネット上のものだけ | **マシンから届くものすべて**（`localhost` や社内ネットワークも） |

### 5.2 なぜセルフホストにしているのか

| 理由 | 説明 |
| --- | --- |
| quality-gate に届く必要がある | 手元や社内で動かしている quality-gate（例: `http://localhost:8080`）には、GitHub ホストランナーからは届かない |
| 無料枠を使い切らない | テストや解析は時間がかかる。セルフホストなら無料枠を消費しない |
| 性能計測の条件をそろえる | 性能（M-03〜05）は、毎回同じマシンで測らないと比べられない（収集ランナーのマシンで、既定ブランチの計測のときだけ測る） |

### 5.3 ランナーは「仕事を取りに行く」

ここが一番誤解されやすいところです。
**GitHub がランナーのマシンに接続してくるのではなく、ランナーが GitHub に「仕事はありますか」と聞きに行きます。**

```
 セルフホストランナー  ──（外向きの HTTPS）──▶  GitHub
       「self-hosted 向けの仕事はある？」
                      ◀──────────────────  「collect の fetch ジョブをお願い」
```

そのため次のことが言えます。

- マシンに外部から接続できる必要はない（ファイアウォールの内側、自宅の PC でもよい）
- **ランナーが止まっていると、ジョブは誰にも取られず `Waiting for a runner to pick up this job...` のまま待ち続ける**
  （待ち続けたジョブは 24 時間で失敗扱いになる）
- ランナーは 1 台なので、ジョブは**1 つずつ順番に**処理される。
  quality-gate 自身の計測ジョブが溜まっていると、collect はその後ろに並ぶ

### 5.4 `collect` のジョブは何をしているか

`collect` ワークフローは、15 分ごとの定期実行か、Actions 画面からの手動実行で動き出します。
最初の `plan` ジョブが「今回どのコミットを測るか」を決め、1 コミットずつ `fetch` → `measure` → `submit` を実行します。

| ジョブ | やること | 使う鍵 | 所要時間の目安 |
| --- | --- | --- | --- |
| `plan` | 定期実行なら、like-chatgpt の main の先頭と、open な PR の先頭を GitHub に問い合わせ、まだ測っていないものを選ぶ。手動実行なら、指定されたものをそのまま選ぶ | App の秘密鍵 → 読み取り用トークン | 数秒 |
| `fetch` | 計測プロファイルを読み、GitHub App のトークンを発行して like-chatgpt を写し取る。測るコミットと比較相手（base）を決める | App の秘密鍵 → 読み取り用トークン | 1 分未満 |
| `measure` | 写し取ったソースでビルド・テスト・解析をして、成果物を `reports/` にまとめる | **なし** | 数分 |
| `submit` | `reports/` を quality-gate の Ingest API に送る | Ingest Token | 1 分未満 |

ジョブの間のファイルの受け渡しには、GitHub Actions の「アーティファクト」（一時置き場）を使います。
写し取ったソースは 1 日、計測結果は 7 日で自動的に消えます。

## 6. 認証と認可

### 6.1 認証と認可の違い

| 言葉 | 意味 | たとえ |
| --- | --- | --- |
| 認証（Authentication） | **あなたは誰か**を確かめる | 社員証を見せて本人だと示す |
| 認可（Authorization） | **あなたは何をしてよいか**を決める | 社員証で入れるのは自分のフロアだけ |

### 6.2 このしくみで使う 4 種類の鍵

| 鍵 | 誰が使う | どこに保管 | できること | できないこと |
| --- | --- | --- | --- | --- |
| **ログイン（GitHub App の Client ID / Secret ＋ 許可リスト）** | 人（ブラウザ） | quality-gate アプリの `.env` | quality-gate の画面を見る。ADMIN なら設定の変更も | 許可リストに無い人は、GitHub アカウントがあっても入れない |
| **GitHub App の秘密鍵 → インストールトークン** | `fetch` ジョブ | quality-gate の Secrets（`QG_COLLECTOR_APP_PRIVATE_KEY`） | like-chatgpt を**読む**（1 時間だけ） | 書き込み、ほかのリポジトリの読み取り |
| **Ingest Token**（`qg_xxxx_yyyy`） | `submit` ジョブ | quality-gate の Secrets（`QG_INGEST_TOKEN_LIKE_CHATGPT`） | like-chatgpt の Run を作り、成果物を送る | 画面の閲覧、設定の変更、**ほかのリポジトリへの送信** |
| **GITHUB_TOKEN** | 全ジョブ（GitHub が自動発行） | 自動 | quality-gate リポジトリ自身を読む（計測スクリプトを取り出すため） | like-chatgpt へのアクセス、書き込み |

### 6.3 GitHub App の「インストール」とは

GitHub App は、GitHub に登録した**アプリ用の身分証**です。quality-gate では 1 つの App を 2 つの用途に使っています。

1. **ログイン**：「この人は GitHub の○○さんです」と確かめる（認証）
2. **like-chatgpt の読み取り**：収集ランナーが like-chatgpt を clone する

2 のために、App を like-chatgpt に**インストール**しています。インストールは「このリポジトリへの立ち入り許可を出す」操作です。
許可の範囲は App の設定で決めていて、今回は **Contents（ソース）と Pull requests の読み取りだけ**です。

実際に clone するときは、秘密鍵そのものではなく、秘密鍵から発行した**インストールトークン**を使います。

```
 秘密鍵（Secrets に保管。長期間有効）
    │  actions/create-github-app-token が GitHub に「トークンをください」と頼む
    ▼
 インストールトークン（1 時間で失効。like-chatgpt だけ、読むだけ）
    │  fetch.sh が clone に使う
    ▼
 like-chatgpt の写し
```

こうしているのは、万一トークンが漏れても、被害を「1 時間以内に」「like-chatgpt を」「読むことだけ」に限るためです。
さらに、トークンは写しの `.git/config` にも保存しないようにしています。

### 6.4 Ingest Token

Ingest Token は、quality-gate が like-chatgpt 専用に発行する**送信用の鍵**です。

- 管理画面（S-08）で発行し、**発行したときに 1 回だけ**表示されます。quality-gate の DB には SHA-256 のハッシュしか残りません
- 「like-chatgpt の結果を送る」ことしかできません。別のリポジトリ名で送ろうとすると `REPOSITORY_MISMATCH` で拒否されます
- この鍵では画面の閲覧も設定の変更もできません
- 漏れたときは S-08 で失効させ、新しく発行して Secrets を入れ替えます

### 6.5 画面のログインと権限

- ログインは GitHub アカウントで行います。ただし GitHub アカウントがあれば誰でも入れるわけではありません。
  **quality-gate の許可リスト（`users` テーブル）に登録された人だけ**が入れます
- 最初にログインした人が ADMIN になります。権限は ADMIN（設定変更・トークン発行ができる）と VIEWER（見るだけ）の 2 種類です
- ログインできる人は、**登録されているすべてのリポジトリの結果を見られます**。
  GitHub で like-chatgpt を見る権限が無い人でも、quality-gate に入れれば like-chatgpt の結果が見えます

### 6.6 なぜ `measure` ジョブには鍵を渡さないのか

`measure` ジョブは like-chatgpt のテストコードを実行します。テストコードは like-chatgpt 側の人が書いたもので、
その中身が何をするかは、quality-gate 側からは保証できません。
もし同じジョブの中に鍵があれば、テストコードがその鍵を読み取れてしまいます。

そこで、鍵を使う作業（`fetch` と `submit`）と、他人のコードを動かす作業（`measure`）を別のジョブに分けています。

```
 fetch   : 鍵あり（App のトークン） ／ like-chatgpt のコードは動かさない
 measure : 鍵なし                   ／ like-chatgpt のコードを動かす
 submit  : 鍵あり（Ingest Token）   ／ like-chatgpt のコードは動かさない
```

さらに `measure` は、like-chatgpt のコードを**計測用のコンテナ（箱）の中だけで**動かします。
箱の中から見えるのは、写し取ったソースと計測結果の置き場所くらいで、ランナーのマシンのほかのファイルや Docker には触れられません。
ただし箱の中からインターネットへは出られる（ライブラリを取ってくるため）ので、
**自分たちが管理するリポジトリだけを計測対象にする**のが前提なのは変わりません。

### 6.7 鍵はどこにあり、誰が見られるか

| 鍵 | 保管場所 | 見られる人 |
| --- | --- | --- |
| App の秘密鍵、Ingest Token | quality-gate リポジトリの Actions Secrets | 誰も中身を見られない（登録した人も再表示できない）。ワークフローの中でだけ使える |
| ログイン用の Client Secret | quality-gate アプリを動かすマシンの `.env` | そのマシンに入れる人 |
| ランナーの登録情報 | ランナーのマシンの `actions-runner/` | そのマシンに入れる人 |

**quality-gate リポジトリは private にしておいてください。** ワークフローのログや成果物には、like-chatgpt のファイルパスやテスト結果が含まれます。

## 7. 1 回の計測で起きていること

Actions の画面で **collect → Run workflow** を押してから、画面に結果が出るまでの流れです。

| # | どこで | 何が起きる |
| --- | --- | --- |
| 1 | GitHub | 15 分ごとの定期実行が来るか、あなたが Run workflow を押す。`plan` ジョブが「self-hosted 向けの仕事」として列に並ぶ |
| 1' | ランナー（plan） | 測るコミットを決める。定期実行なら、まだ測っていない main と PR の先頭を選ぶ（測り終えたコミットはランナー上のファイルに記録してある） |
| 2 | ランナー | ランナーが仕事を受け取り、quality-gate リポジトリ（計測スクリプト）を取り出す |
| 3 | ランナー（fetch） | 計測プロファイル `ymiyamoto63__like-chatgpt.env` を読む |
| 4 | ランナー → GitHub | App の秘密鍵で、like-chatgpt 専用・読み取り専用・1 時間有効のトークンを発行する |
| 5 | ランナー → like-chatgpt | トークンで like-chatgpt を全履歴ごと clone する（base のコミットも必要なため） |
| 6 | ランナー（fetch） | 測るコミット（head）と比較相手（base）を決める。main なら 1 つ前のコミット、PR なら main との分岐点 |
| 7 | ランナー（measure） | Java・Node.js を用意し、ビルド・テスト・解析をする（詳しくは次章） |
| 8 | ランナー（measure） | 成果物を `reports/` にまとめ、写し取ったソースを削除する |
| 9 | ランナー → quality-gate（submit） | Ingest Token で Run を作り、成果物を 1 つずつ送り、最後に「送り終わりました」（finalize）を伝える |
| 10 | quality-gate | 成果物を読み取り、画面で保存した合格ラインと比べて判定する（数秒） |
| 11 | あなたのブラウザ | ダッシュボードや Run 詳細で結果を見る |

## 8. 中で測っているもの

### 8.1 いま測っている 7 つの指標

| 指標 | ひとことで | 測り方（ツール） | like-chatgpt の合格ライン |
| --- | --- | --- | --- |
| **M-01** ブランチカバレッジ | テストが、コードの分かれ道（if の真と偽など）をどれだけ通ったか | Java: JaCoCo ／ TypeScript: Vitest（v8） | 75% 以上（backend / frontend それぞれ） |
| **M-02** ミューテーションスコア | コードをわざと壊したとき、テストがそれを見つけられるか（main のみ） | PIT | 60% 以上（backend のみ） |
| **M-06** 脆弱性 | 使っているライブラリに、既知の危険な穴がいくつあるか | Trivy | Critical 0 件、High 0 件 |
| **M-07** 循環的複雑度 | 新しく複雑すぎる関数（分かれ道が多すぎて読みにくい関数）が増えていないか | PMD | 複雑度 15 を超える新規・悪化関数が 0 件（11〜15 は警告） |
| **M-08** API 契約テスト | API の約束（リクエストと応答の形）を確かめるテストが全部通ったか | JUnit の結果（`*ControllerTest`） | 成功率 100%、1 件以上 |
| **M-09** API の破壊的変更 | 利用者を壊すような API の変更（項目の削除など）をしていないか | oasdiff | 0 件 |
| **M-10** アクセシビリティ | 画面が支援技術（読み上げなど）やキーボードで使えるか | Playwright + axe-core | 重大な違反（critical / serious）0 件 |

### 8.2 それぞれの中身

**M-01 ブランチカバレッジ**

```java
if (age >= 20) {   // ← 分かれ道。「真」と「偽」の 2 つの枝がある
    return "adult";
} else {
    return "minor";
}
```

テストが `age = 30` しか試していなければ、2 つの枝のうち 1 つしか通っていないので 50% です。
バックエンドでは Maven のビルドに JaCoCo を**コマンドラインから差し込み**、テストを実行しながら通った枝を記録します。
like-chatgpt の `pom.xml` に JaCoCo の設定が無くても測れるのはこのためです。
フロントエンドでは Vitest にカバレッジの設定をコマンドラインから渡します。

**M-02 ミューテーションスコア**

PIT が、コードを少しだけわざと壊した版（ミューテーション）をたくさん作ります。
たとえば `age >= 20` を `age > 20` に変えたり、`return "adult"` を `return ""` に変えたりします。
壊した版ごとにテストを実行し、テストが失敗すれば「見つけられた（検出）」、通ってしまえば「見逃した（生存）」です。
検出できた割合がミューテーションスコアです。

カバレッジは「テストがそのコードを通ったか」しか見ないため、結果を確かめない（アサーションの無い）テストでも数字が上がります。
ミューテーションスコアはそうした見かけだけのテストを見抜けます。

壊した版の数だけテストを繰り返すので時間がかかります。そのため収集ランナーは **main（既定ブランチ）の計測でだけ**実行し、
PR の計測では「計測しない」と申告します（Run 詳細では SKIP と表示されます）。
PIT もコマンドラインから動かすので、like-chatgpt の `pom.xml` の設定は使いません。

**M-06 脆弱性**

`pom.xml` や `package-lock.json` から使っているライブラリと版を読み取り、
公開されている脆弱性データベースと照らし合わせます。
「このライブラリのこの版には、外部から任意のコードを実行される穴がある（Critical）」といった情報が出てきます。

**M-07 循環的複雑度**

関数の中の分かれ道（if、for、case、&& など）の多さを数値にしたものです。数値が大きいほど、読むのもテストするのも難しくなります。
収集ランナーは **head（今回）と base（比較相手）の両方**を解析して送ります。quality-gate はそれを比べて、次の 2 つを区別します。

- もともと複雑だった関数で、今回は悪化していないもの → 責めない
- 今回新しく作られた、または今回さらに複雑になった関数 → 判定の対象

以前の方式（like-chatgpt 自身の CI）は base を送っていなかったため、この区別ができていませんでした。

**M-08 API 契約テスト**

「`POST /api/chat` に正しい形で送ると、決まった形の応答が返る」ことを確かめるテストです。
like-chatgpt では `*ControllerTest` という名前のテストがこれにあたります。
単体テストまで含めると「全テストの成功率」になってしまうため、名前で絞り込んでいます（計測プロファイルの `CONTRACT_TEST_REPORTS`）。

**M-09 API の破壊的変更**

like-chatgpt は API の定義書（`api/openapi.yml`）をリポジトリに置いています。
head と base の定義書を oasdiff で比べ、「API のパスを消した」「必須の項目を増やした」など、
今の利用者を壊す変更を数えます。base に定義書が無い（API を新しく作った）ときは「対象外」になります。

**M-10 アクセシビリティ**

収集ランナーは like-chatgpt を**計測用のコンテナの中で実際に起動**します（バックエンドの jar と、ビルドした画面）。
その画面をブラウザ（Chromium）で開き、axe-core というツールで「画像に代わりの文字が無い」「文字と背景の色の差が小さすぎる」
「ボタンに名前が無い」といった問題を探します。画面はライトとダークの 2 通りで調べます。
調べる画面は計測プロファイルの `A11Y_PAGES` に書いたもので、合格ラインの `accessibility.pages` と一致している必要があります。
画面を開けなかったときは「調べた画面が足りない」として ERROR になり、合格には見えません。

### 8.3 まだ測っていないもの

| 指標 | ひとことで | まだ測らない理由 |
| --- | --- | --- |
| M-03〜05 性能 | 応答の速さ、処理量、エラー率 | 負荷をかける対象のアプリと専用の環境が要る |

これは合格ライン（画面の設定）で `enabled: false` にしています。有効のままだと「結果が届かなかった」として ERROR になります。

### 8.4 テストが失敗したら

収集ランナーは、テストが失敗しても**止まらずに最後まで測ります**。テストの失敗も大事な計測結果だからです（M-08 に表れます）。
ただし M-02 の PIT は、テストがすべて通っていないと動きません（M-02 は ERROR になります）。
一方、コンパイルができないなどでビルド自体が失敗すると、その指標の成果物が出ません。
quality-gate は「結果が届かなかった指標」を ERROR として扱い、Run 全体は FAIL になります。

## 9. 判定の結果の読み方

| 画面の表示 | 意味 |
| --- | --- |
| PASS | 合格ラインを満たした |
| WARN | 合格だが注意が要る（例: 複雑度 11〜15 の新しい関数がある） |
| FAIL | 合格ラインを満たしていない |
| ERROR | 結果が届かなかった、または読めなかった（計測の失敗。コードの品質の問題とは限らない） |
| 対象外（NOT_APPLICABLE） | 判定する材料がそもそも無い（例: 比較相手に API 定義書が無い） |

Run 全体の判定（verdict）は次のように決まります。

| Run 全体 | 条件 |
| --- | --- |
| FAIL（不合格） | 指標の中に 1 つでも FAIL か ERROR がある |
| PASS_WITH_WARNINGS（注意つき合格） | FAIL・ERROR は無いが、WARN がある |
| PASS（合格） | それ以外（対象外の指標は影響しない） |

いまは `enforcement: report-only` なので、FAIL になっても like-chatgpt の開発は何も止まりません。結果を見て判断するための情報です。

同じコミットを何度測っても、前の結果は上書きされず、新しい Run（attempt 2、3…）として残ります。
収集ランナーが作った Run は、Run 詳細の CI 実行へのリンクが quality-gate リポジトリの collect ワークフローを指します。
like-chatgpt 自身の CI が作った Run は like-chatgpt のワークフローを指すので、そこで見分けられます
（API で取得した Run のデータでは `triggeredBy` が `collector` になっています）。

## 10. よくある疑問

**Q. like-chatgpt に push したら自動で測られますか？**
A. はい。push の直後ではなく、**15 分ごとの定期実行**で測られます。main の先頭と、open な PR の先頭のうち、まだ測っていないものが対象です。
混み具合によって、push から 15〜30 分ほどで結果が出ます。すぐに測りたいときは Actions の画面から手動で実行できます。
フォーク（他人のコピー）から出された PR は、他人のコードを自分のマシンで動かすことになるため測りません。

**Q. ランナーのマシンを止めるとどうなりますか？**
A. collect を実行しても、ジョブが `Waiting for a runner...` のまま進みません。24 時間待つと失敗扱いになります。
定期実行の待機は 1 つだけ残るので、ランナーを再開すると、その時点でまだ測っていない先頭コミットがまとめて測られます。
quality-gate のアプリ自体（画面）は、ランナーとは別に動いていれば使えます。

**Q. ランナーと quality-gate のアプリは同じマシンでないといけませんか？**
A. いいえ。ランナーから quality-gate の URL（`QG_BASE_URL`）に届けば、別のマシンでも構いません。
同じマシンなら `http://localhost:8080` で届きます。

**Q. like-chatgpt 以外のリポジトリも測れますか？**
A. 計測プロファイルを追加し、App をそのリポジトリにもインストールし、Ingest Token を発行すれば測れます
（[収集ランナーで計測する](../operations/collector.md)「対象を追加する」）。
収集ランナーのスクリプトは Maven と npm + Vitest の構成を前提にしています。

**Q. 計測したデータはどこに残りますか？**

| 置き場所 | 残るもの | 期間 |
| --- | --- | --- |
| GitHub Actions のアーティファクト | 写し取ったソース（`collector-source`） | 1 日 |
| GitHub Actions のアーティファクト | 計測結果（`collector-reports`） | 7 日 |
| ランナーのマシン | 計測用のコンテナのイメージと、キャッシュ（Maven・npm・PMD・Trivy の DB）の Docker ボリューム | 消すまで（ソースそのものは残さない） |
| quality-gate のアプリ | 成果物ファイル（`data/artifacts/`）と判定結果（PostgreSQL） | 保持期間の設定（管理画面 S-09）に従う |

**Q. like-chatgpt 側のワークフロー（`.github/workflows/quality-gate.yml`）は消してよいですか？**
A. 収集ランナーで M-01 / M-02 / M-06〜M-10 が問題なく測れることを確かめたら、消しても構いません。消すかどうかは like-chatgpt 側の判断です。
