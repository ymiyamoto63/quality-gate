# 収集ランナー方式

> **状態: 採用（[決定事項 D-16](../initial/03-open-questions.md)、2026-09-23）。段階 1〜4 を実装済み**。
> 手順は [収集ランナーで計測する](../operations/collector.md) を参照してください。
> 本書は方針を決めたときの検討内容と、残りの移行計画をまとめたものです。

## 1. 目的

収集ランナーの導入前は、計測対象リポジトリに次のものを置く必要がありました（like-chatgpt では PR #14 で追加）。

| 置いているもの | 役割 |
| --- | --- |
| `.quality-gate.yml` | 合格ラインと有効な指標 |
| `.github/workflows/quality-gate.yml` | 計測と送信 |
| `scripts/quality-gate-submit.sh` | Ingest API への送信 |
| `pom.xml` / `package.json` のプラグイン・依存関係 | JaCoCo、PMD、PIT、coverage-v8、Playwright + axe-core |
| `frontend/e2e/*` | アクセシビリティ検査（M-10） |

これを**対象リポジトリに一切変更を加えずに**計測できるようにするため、
計測の実行場所を対象リポジトリの CI から、quality-gate 側に置く「収集ランナー」へ移しました。

## 2. 結論

- **採用しました（D-16）。段階的に移行し、指標ごとに切り替えます。**
- 判定側（バックエンド）は今の Ingest API をそのまま使います。収集ランナーは「quality-gate が提供する CI クライアント」という位置づけで、
  **バックエンド自身はテストを実行しない**という D-1 の核は保ちます。
- 実行基盤は **quality-gate リポジトリ（private）の GitHub Actions ＋ 既存のセルフホストランナー**とします。
- 外から測りやすい指標（M-01 / M-06 / M-07 / M-08 / M-09）から移し、M-02 → M-10 → 性能の順に進めました。
  M-10 と性能は、対象アプリをランナー上で起動して測ります（外部のサービスが要る対象は、必要になった時点で拡張します）。

## 3. 前提条件の確認

[要件定義書 2.1](../initial/01-requirements.md) の前提のうち、本方式に影響するものです。

| 前提 | 本方式への影響 |
| --- | --- |
| 対象は **1 リポジトリ**、構成は Spring Boot 4 + Vue 3 のモノレポ | 対象の構成が決まっているため、ビルド方法の自動検出を作り込まずに済む。**方式の難度を大きく下げる要因** |
| 個人アカウント（GitHub Free）、Organization なし | GitHub App の追加インストールは所有者本人が行えるため、承認のやり取りは不要 |
| 対象リポジトリは **private** | clone に読み取り権限が必要（4.3）。収集ランナーの実行ログ・成果物も private に閉じる必要がある |
| private リポジトリの Actions は月 2,000 分 | 計測はセルフホストランナーで行うため枠を消費しない |
| 性能計測は専有ランナーで、他のジョブと同居させない（D-7） | 収集ジョブと性能計測が同じランナーで重ならないよう直列化が必要（4.6） |

## 4. 構成

### 4.1 全体像

```
                        （対象リポジトリには何も置かない）
 対象リポジトリ (private) ──clone（読み取りのみ）──┐
                                                   │
 quality-gate リポジトリ (private)                 │
   .github/workflows/collect.yml                   │
   collector/                                      ▼
     targets/<owner>__<name>.env   ──►  セルフホストランナー
     bin/*.sh                            1. 新しいコミットを検出（plan）
     pmd-ruleset.xml                     2. clone（fetch。base の解析のため全履歴）
     versions.env                        3. 計測（measure。ツールは quality-gate 側で版を固定）
                                         4. Ingest API へ送信（submit）
                                                   │
                                                   ▼
                                  quality-gate バックエンド（判定のしくみは変更なし）
                                   設定は targets/<owner>__<name>.gate.yml（Run ごとに送る。D-20）
```

### 4.2 実行基盤の選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A. quality-gate リポジトリの Actions**（推奨） | `collect.yml` を定期実行・手動実行し、既存のセルフホストランナーで計測する | ランナー・シークレット・ログ閲覧を既存の仕組みで賄える。追加の常駐プロセスが不要 |
| B. バックエンドのジョブとして実行 | `JobWorker` から Docker で計測コンテナを起動する | D-1 に正面から反する。バックエンドのホストに Docker ソケット（実質 root）を渡し、DB と同じ場所で対象のビルドコードを実行することになる。**不採用** |
| C. 独立した収集デーモン | ランナー機に常駐プロセスを置き、quality-gate をポーリングする | 起動タイミングの自由度は高いが、監視・再起動・ログの仕組みを自前で持つ必要がある。対象 1 件の規模には過剰 |

### 4.3 認証情報

| 用途 | 認証情報 | 置き場所 |
| --- | --- | --- |
| 対象リポジトリの clone、コミット・PR の一覧取得 | 既存の GitHub App に **Contents: Read-only / Pull requests: Read-only** を追加し、対象リポジトリにインストールする。ジョブごとに `actions/create-github-app-token` で**対象リポジトリに限定した 1 時間有効のトークン**を発行する | quality-gate の Actions Secrets（App ID と秘密鍵） |
| Ingest API への送信 | 対象リポジトリ用の Ingest Token（従来と同じ） | quality-gate の Actions Secrets（対象ごと） |

デプロイキーや個人アクセストークンは、対象ごとの管理や個人への依存が生じるため使いません。

### 4.4 計測のきっかけ

対象リポジトリにワークフローを置かないため、push や PR をきっかけに起動できません。次の 2 つで代替します。

| きっかけ | 内容 |
| --- | --- |
| 定期実行（例: 15 分ごと） | GitHub API で既定ブランチの先頭と、同一リポジトリ内のブランチから出ている open な PR の先頭コミットを取得し、未計測のものだけを計測する |
| 手動実行（`workflow_dispatch`） | リポジトリとコミット（またはブランチ）を指定して計測する |

- **計測済みかの判定**：今の Ingest API には「そのコミットの Run が既にあるか」を Ingest Token で問い合わせる手段がありません。
  段階 2 では収集ランナー側（ランナーのマシン上のファイル）に計測済みのコミットを記録しています。
  記録が消えても、各ブランチ・PR のいまの先頭を 1 回ずつ計測し直すだけで済みます。
  ランナーを複数台にするなど、記録を共有する必要が出たら問い合わせ用の API を追加します
- **遅延**：push から計測開始まで最大で定期実行の間隔ぶん遅れます。GitHub の定期実行は混雑時にさらに遅れることがあります
- 将来 GitHub App の webhook（push / pull_request）を受けて即時に起動する形にもできます。
  ただし webhook の受け口を公開する必要があるため、最初は定期実行にします

### 4.5 指標ごとの計測方法

ツールの版は quality-gate 側で固定します。対象リポジトリにプラグインの設定があっても使いません（計測条件をそろえるため）。
ただし**テストそのものは対象リポジトリのもの**を実行します。

| 指標 | 計測方法 | 難度 | 従来との違い |
| --- | --- | --- | --- |
| M-01（Java） | `mvn org.jacoco:jacoco-maven-plugin:<ver>:prepare-agent verify org.jacoco:jacoco-maven-plugin:<ver>:report` | 低 | なし |
| M-01（TS） | 作業用の clone に `npm i --no-save @vitest/coverage-v8@<ver>` を入れ、`vitest run --coverage.enabled --coverage.reporter=lcov` | 低 | なし |
| M-02 | PIT のコマンドライン版を、`mvn dependency:build-classpath` で得たクラスパスで実行する。pom を書き換えずに済む | 中 | なし |
| M-06 | `trivy fs`（版固定のコンテナ） | 低 | なし |
| M-07 | PMD のコマンドライン版と quality-gate 側のルールセットで、**head と base の両方**を解析し `scope=base` も送る | 低 | **改善**。従来は base を送っていなかったため「新規・悪化した関数」を判定できず、M-07 が FAIL にならない |
| M-08 | surefire の JUnit XML（既定で出力される）から、計測プロファイルの名前パターン（例: `*ControllerTest`）に合うものだけを送る | 低 | なし |
| M-09 | 計測プロファイルで指定した OpenAPI 定義（例: `api/openapi.yml`）を head と base で取り出し、oasdiff で比較する | 低 | なし（full clone なので base の取得が確実になる） |
| M-10 | quality-gate 側の Playwright + axe-core スクリプトで、計測プロファイルの `pages` を巡回する。画面を表示するには対象アプリの起動が必要。対象の e2e テストのように API をモックできないため、バックエンドと DB（コンテナ）を起動してデータを用意するか、共有の検証環境の URL を検査する | **高** | 検査できる画面・状態が変わる可能性がある。ログインが必要な画面の扱いも要検討 |
| M-03〜05 | quality-gate 側に k6 のシナリオを置き、起動した対象アプリに負荷をかける | 高 | **従来は無効**。収集ランナーで新たに計測する（既定ブランチのみ。[収集ランナーで計測する](../operations/collector.md) 8 章） |

**計測プロファイル**は、対象ごとに異なる計測上の情報を quality-gate 側で持つファイルです。
合格ラインではなく「どう測るか」だけを書きます（合格ラインは画面 S-06 の設定）。
段階 1 では、追加のツールなしにシェルで読めるよう `KEY=VALUE` 形式にしました（シェルとしては実行しません）。

```bash
# collector/targets/ymiyamoto63__like-chatgpt.env（抜粋）
QG_REPOSITORY=ymiyamoto63/like-chatgpt
DEFAULT_BRANCH=main
INGEST_TOKEN_SECRET=QG_INGEST_TOKEN_LIKE_CHATGPT
BACKEND_DIR=backend
JAVA_VERSION=21
CONTRACT_TEST_REPORTS=surefire-reports/TEST-*ControllerTest.xml   # M-08
OPENAPI_PATH=api/openapi.yml                                       # M-09
FRONTEND_DIR=frontend
FRONTEND_COVERAGE_INCLUDE=src/**/*.{ts,vue}
```

M-10 の設定（対象アプリの起動方法、検査する画面）は段階 4 で `A11Y_PAGES` などのキーとして追加しました（[運用手順](../operations/collector.md#6-m-10アクセシビリティ段階-4)）。

### 4.6 実行時の安全対策

収集ランナーは**対象リポジトリのビルド・テストのコードを実行します**。対象は自分のリポジトリですが、
ビルドの依存関係まで含めると信頼しきれないため、次の対策を前提にします。

| リスク | 対策 |
| --- | --- |
| 対象のテストコードが同じジョブのシークレット（App のトークン、Ingest Token）を読む | **ジョブを 3 つに分ける**。取得（App トークンを使う）→ 計測（シークレットを渡さない）→ 送信（Ingest Token を使う）。ジョブ間は Actions の成果物で受け渡す（保持期間 1 日） |
| 前回の計測の残骸や、計測中に書き換えられたファイルが次回に影響する | 作業領域はジョブの最後に必ず削除する |
| 対象のビルド・テストのコードがランナーのマシンに触れる | **計測をコンテナに隔離する**（`collector/bin/measure-isolated.sh`）。コンテナに見せるのは作業領域・`reports/`・`collector/`（読み取りのみ）・キャッシュのボリュームだけで、権限を落とし（`--cap-drop ALL`）、ランナーの利用者の UID で動かす。外向きの通信は依存関係の取得のために残す（[運用手順](../operations/collector.md#7-計測のコンテナ隔離)） |
| private のソースやテスト出力がログから漏れる | quality-gate リポジトリを private に保つ。ログにソースを出さない |
| フォークからの PR で任意のコードが実行される | 計測するのは同一リポジトリ内のブランチからの PR だけにする |
| 性能計測と同じランナーで重なり、性能値が乱れる（D-7） | ランナーを 1 台にして、ジョブを 1 つずつ実行させる（収集ワークフローも `max-parallel: 1`）。重なりが問題になるほど頻度が上がったら、収集用のランナーを別に用意する |

## 5. 従来の方式との比較（private リポジトリ前提）

| 観点 | 従来の方式（対象の CI から送る） | 収集ランナー方式 |
| --- | --- | --- |
| 対象リポジトリの変更 | 必要 | **不要** |
| 計測のタイミング | push / PR のたびに即時 | 定期実行の間隔ぶん遅れる。取りこぼしは次回の実行で拾う |
| 計測条件の統一 | ツールの版が対象ごとにずれうる | quality-gate 側で固定 |
| M-07 のベース比較 | できていない | できる |
| M-10 の検査 | 対象の e2e の仕組み（API モック）をそのまま使える | 対象アプリの起動が必要で、難度が高い |
| GitHub App の権限 | ログインのみ | **Contents / Pull requests の読み取りを追加** |
| 対象のコードが動く場所 | 対象の CI | quality-gate のセルフホストランナー |
| 保守する人 | 対象のチーム（自分の CI） | quality-gate の運用者（対象のビルド事情に追従） |

## 7. 移行計画

| 段階 | 内容 | 完了条件 |
| --- | --- | --- |
| 0 | GitHub App に読み取り権限を追加して対象にインストールする。画面（S-06）に like-chatgpt の設定を保存する | 収集ランナーから対象を clone できる |
| 1（**実装済み**） | M-01 / M-06 / M-07 / M-08 / M-09 を収集ランナーで計測する。手動実行のみ | **同じコミットに対して、従来の CI と実測値が一致する**（M-07 は base 比較の分だけ差が出るのが正しい）。手元での計測では JaCoCo・lcov・PMD・契約テストの件数が対象自身のビルドと一致した。GitHub Actions 上での確認は未実施 |
| 2（**実装済み**） | 定期実行と計測済み判定を入れる。PR の先頭コミットも計測する | 1 週間、取りこぼしなく計測できる。計測済みの記録はランナー上のファイル（`collector/bin/state.sh`）、PR は同じリポジトリのブランチからのものだけ。GitHub Actions 上での 1 週間の確認は未実施 |
| 3（**実装済み**） | M-02（PIT）を追加する。時間がかかるため既定ブランチのみに絞る（Q-6） | 実測値が一致する。手元での計測では、ミューテーションの総数（143 件）が対象自身の `mvn -P mutation test` と一致し、検出数は 98〜99 件（対象のテストが乱数を固定していないため、対象自身の方式でも実行ごとに 1 件入れ替わる）。既定ブランチの新しいコミットごとに全量を実行する（like-chatgpt で約 1 分）。重くなったら夜間に絞る |
| 4（**実装済み**） | M-10 の方式を決めて実装する（アプリの起動か、検証環境の URL か） | 検査対象の画面が `pages` と一致する。**アプリの起動**を採った（バックエンドの jar と `vite preview`）。手元での計測では `/` をライト・ダークで検査し、検査した画面が `pages` と一致した |
| 5（**実装済み**） | M-03〜05（性能）を追加する。バックエンドの jar を起動し、quality-gate 側の k6 のシナリオで負荷をかける。既定ブランチのみ | 3 回分の summary が送られ、シナリオが `performance.scenarios` と一致する。手元での短縮実行（計測 10 秒 × 2 回）では、like-chatgpt の 3 シナリオの summary が出て、quality-gate の k6 アダプタで読めた。GitHub Actions 上での確認は未実施 |
| 6 | 対象リポジトリの計測用ファイルを削除できる状態にする（削除するかどうかは対象側の判断） | 収集ランナーだけで全指標の判定が出る |

移行中も、**対象の CI と収集ランナーの両方から送れます**（Ingest API が共通のため）。
ただし両方から同じコミットの Run を作ると画面上で重複し、対象の CI の Run は対象側の `.quality-gate.yml` で判定されます。
比較が終わったら、対象の CI からの送信を止めてください。quality-gate 側で対象の CI 用の Ingest Token を失効させれば、対象リポジトリに触らずに止められます（[手順](../operations/collector.md#対象の-ci-からの送信を止める)）。
送信元は Run の `triggeredBy`（収集ランナーは `collector`）と、Run 詳細の「CI 実行」のリンク先で区別できます。
