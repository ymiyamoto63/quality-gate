## Q-6. ミューテーションテストの CI 実行時間をどこまで許容できるか【優先度: 中】

要件定義書では既定を「変更クラスのみ（`scope: changed`）」としていますが、
それでも PIT は相応の時間を要します（全量では単体テストの数十倍）。

- PR の CI 全体の許容時間（例: 15 分以内）
- 変更クラス限定でも超過する場合、ミューテーションテストを
  PR ではなく main への push 後（または夜間バッチ）のみに回すか

**推奨**: PR では差分限定、main への push 後に全量を夜間実行。
PR の待ち時間を増やさずに、両方の値を得られます。

## Q-7. 通知先と通知条件の運用【優先度: 中】

- ~~通知先の Slack チャネル~~ → 通知はメールのみと決定（D-15）。宛先はリポジトリごとに画面で設定する
- 「合格→不合格の遷移時のみ」を既定としていますが、これで妥当か（実装の既定はこれ。D-15）
- 不合格が継続している場合の再通知（毎日 / 週次 / しない）をどうするか

通知が多すぎると無視され、少なすぎると気づかれません。
**既定は「遷移時のみ + 週次サマリ」**を推奨します。

## Q-8. 不合格時の是正プロセスをどう定めるか【優先度: 中】

D-4 のとおり本フェーズではマージをブロックしないため、
**不合格が放置されない運用ルール**が別途必要です。これはアプリの機能ではなく
運用の取り決めですが、これを欠くと [リスク R-7](01-requirements.md#13-リスクと対策)
のとおり「可視化しただけで何も改善しない」状態になります。

決めていただきたいこと:

- 不合格を検知してから是正までの目標期間（例: Critical 脆弱性は 3 営業日以内）
- 週次で不合格リポジトリをレビューする場（既存の定例に組み込めるか）
- Phase 3（マージブロック）へ移行する判断基準と時期の目安

## Q-9. 成果物の保持期間とストレージ【優先度: 低】

要件定義書では「Run メタデータ・指標値 2 年 / 元成果物 90 日」を既定としています。

- 監査・リリース判定の観点で、より長期の保持が必要か
- 保存先はローカルファイルシステム（バインドマウント）で確定済み（[04](04-tech-stack.md) 5.2）。
  必要な空き容量（初期 10GB 程度）を確保できるか

保持日数は上記を既定値として、管理画面（S-09）から変更できるよう実装済み。残るのは運用上の値の決定のみ。

## Q-15. 計測を quality-gate 側の収集ランナーへ移すか【優先度: 中】

対象リポジトリに設定ファイル・ワークフロー・計測用の依存関係を置かずに計測できるよう、
計測の実行場所を quality-gate 側の「収集ランナー」へ移すことを検討している。D-1 の改訂を伴う。

検討内容・移行計画・決めるべき論点は [収集ランナー方式への変更の検討](../architecture/collector-runner.md) にまとめた。
段階 1（M-01 / M-06〜M-09 を手動実行で計測）は実装済み（[収集ランナーで計測する](../operations/collector.md)）。

**推奨**: 外から測りやすい指標（M-01 / M-06 / M-07 / M-08 / M-09）で試し、
現在の CI と実測値が一致することを確かめてから D-1 を改訂する。
