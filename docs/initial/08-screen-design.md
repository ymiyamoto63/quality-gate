## 3. ステータスの表現

本システムで最も重要な表示要素である。**色だけで合否を伝えない**（要件定義書 9 章）。

### 3.1 ステータスと視覚表現の対応

| ステータス | ラベル | 記号 | アイコン | 色（ライト / ダーク） |
| --- | --- | :---: | --- | --- |
| `PASS` | 合格 | ● | `pi-check-circle` | `#0ca30c` / `#0ca30c` |
| `WARN` | 注意 | ▲ | `pi-exclamation-triangle` | `#fab219` / `#fab219` |
| `FAIL` | 不合格 | ■ | `pi-times-circle` | `#d03b3b` / `#d03b3b` |
| `ERROR` | 計測エラー | ◆ | `pi-question-circle` | `#ec835a` / `#ec835a` |
| `SKIP` | 未計測 | ○ | `pi-minus-circle` | `#898781` / `#898781` |
| `NOT_APPLICABLE` | 対象外 | — | `pi-ban` | `#898781` / `#898781` |

**4 つの channel（ラベル・記号・アイコン・色）を常に同時に使う。**
色覚特性、モノクロ印刷、強制カラーモードのいずれでも意味が失われない。

`SKIP` と `NOT_APPLICABLE` は同じ中立色を使うため、**記号とラベルだけが両者を区別する**。
この 2 つに status 色を割り当てないのは、どちらも「良い / 悪い」を表さないためである。
未計測を黄色にすると「注意すべき悪い状態」に見え、判定していないという事実が伝わらない。

`NOT_APPLICABLE`（対象外）も同じ中立色で、ツールの制約で測りようがないことを表す
（M-02 の frontend）。`SKIP` と同じ「未計測」にすると、測り忘れの積み残しと誤読される。
値の欄にも「未計測」ではなく「—」を出す。

### 3.2 チップの構造

```html
<span class="qg-status" data-status="FAIL">
  <i class="pi pi-times-circle" aria-hidden="true"></i>
  <span class="qg-status__mark" aria-hidden="true">■</span>
  <span class="qg-status__label">不合格</span>
</span>
```

**色は点・記号・アイコンにのみ使い、文字色には使わない。**
`WARN`（`#fab219`、ライト面で 1.79:1）と `ERROR`（`#ec835a`、2.57:1）は
ライト面でのコントラストが 3:1 を下回る。ラベルは常にインクトークン
（`--text-primary`）で描き、色付きの記号を隣に置くことで識別性を担保する。

### 3.3 `FAILED`（処理失敗）と `FAIL`（不合格）の区別

この 2 つは意味がまったく違うため、**同じ赤で表示しない**。

| 対象 | 表示 |
| --- | --- |
| `verdict = FAIL`（品質が合格ラインを満たさない） | ■ 不合格（`#d03b3b`） |
| `status = FAILED`（quality-gate の処理が異常終了） | ◆ 処理失敗（`#ec835a`）+ 「判定できませんでした」と明記 |

処理失敗を不合格と同じ見た目にすると、
「品質に問題がある」のか「システムが壊れている」のかが区別できない。
前者は開発者が直すもの、後者は基盤管理者が直すものであり、動くべき人が違う。

### 3.4 カラートークン

```css
:root {
  color-scheme: light;
  --surface-1:        #fcfcfb;   /* カード・グラフ面 */
  --surface-page:     #f9f9f7;
  --text-primary:     #0b0b0b;
  --text-secondary:   #52514e;
  --text-muted:       #706f6a;   /* ライト面 4.9:1 */
  --link:             #1f5fae;   /* ライト面 6.2:1 */
  --gridline:         #e1e0d9;
  --axis:             #c3c2b7;
  --border:           rgba(11, 11, 11, 0.10);

  --status-pass:      #0ca30c;
  --status-warn:      #fab219;
  --status-error:     #ec835a;
  --status-fail:      #d03b3b;
  --status-neutral:   #898781;

  --series-1:         #2a78d6;   /* グラフの系列 1 */
  --series-2:         #eb6834;   /* グラフの系列 2 */
  --series-3:         #8a5cd6;   /* グラフの系列 3 */
}

    --text-primary:   #ffffff;
    --text-secondary: #c3c2b7;
    --text-muted:     #9b9a92;   /* ダーク面 6.2:1 */
    --link:           #7ab5f5;   /* ダーク面 8.1:1 */
    --gridline:       #2c2c2a;
    --axis:           #383835;
    --border:         rgba(255, 255, 255, 0.10);
    --series-1:       #3987e5;
    --series-2:       #d95926;
    --series-3:       #9a72f0;
  }
}

:root[data-theme="dark"] {
  color-scheme: dark;
  --surface-1:      #1a1a19;
  --surface-page:   #0d0d0d;
  --text-primary:   #ffffff;
  --text-secondary: #c3c2b7;
  --text-muted:     #9b9a92;
  --link:           #7ab5f5;
  --gridline:       #2c2c2a;
  --axis:           #383835;
  --border:         rgba(255, 255, 255, 0.10);
  --series-1:       #3987e5;
  --series-2:       #d95926;
  --series-3:       #9a72f0;
}
```

ダークの値を 2 つのスコープに書くのは、OS 設定とアプリ内のテーマ切替の
**両方を効かせる**ためである。`:not([data-theme="light"])` のガードにより、
OS がダークでも利用者が明示的にライトを選べば、そちらが勝つ。

ステータス色はライト / ダークで同じ値を使う。**判定の意味は環境で変わらない**ためであり、
4 色とも暗い面で 3:1 以上を満たしている。

#### ステータス色を文字色に使わない

ステータス色が満たしているのは**図形に必要な 3:1** であり、本文に必要な 4.5:1 ではない。
文字色に使うと、ライト面の `--status-pass`（3.3:1）もダーク面の `--status-fail`（3.6:1）も
基準を下回る。前回比の増減のように「良い / 悪い」を色で示したい箇所では、
**記号にだけ色を付け、数字はインク色のまま**にする（3.2 のチップと同じ方針）。

#### テキストとリンクの色は両モードで検証する

`--text-muted` と `--link` はモードごとに別の値を持つ。
片方だけ検査しても他方の保証にはならないため、M-10 の自動検査は
**ライトとダークの両方で実行する**（8 章）。

実際、当初の `--text-muted`（`#898781`）はライト面で 3.5:1、
リンクはブラウザ既定の `#0000EE` でダーク面が 1.9:1 しかなかった。
どちらも「ライトだけ検査していた」ために見つかっていなかった。

### 3.5 系列色の検証結果

グラフの系列色（`--series-1` 〜 `--series-3`）は検証済みである。

| モード | 判定 | 最悪ペアの CVD ΔE | 通常視 ΔE | 面とのコントラスト |
| --- | --- | --- | --- | --- |
| ライト（面 `#fcfcfb`） | 全項目 PASS | 24.7（protan） | 28.1 | 3 色とも 3:1 以上 |
| ダーク（面 `#1a1a19`） | 全項目 PASS | 26.8（protan） | 28.2 | 3 色とも 3:1 以上 |

**色を増やして系列を増やさない。** 4 色目を作ると、色覚特性下で既存の色と
見分けがつかなくなり、検証そのものが意味を失う。系列が 3 を超える場合は
グラフを分けるか、絞り込みで対象を減らす。

系列の色は**サーバが `colorIndex` として固定して返す**。画面側で「並び順の
n 番目」に色を振ると、絞り込みで系列が減ったときに生き残った系列の色が
塗り替わり、同じものが別の色で見える。

## 4. 各画面の設計

### 4.1 S-01 ダッシュボード

```
┌───────────────────────────────────────────────────────────────────┐
│ ダッシュボード                                                     │
├───────────────────────────────────────────────────────────────────┤
│ ┌───────────────────────────────────────────────────────────────┐ │
│ │ ymiyamoto63/quality-gate                    ■ 不合格           │ │
│ │ main · 2026-09-21 02:12（3 時間前）· 部分計測（未計測 4 件）   │ │
│ │                                                               │ │
│ │  機能テスト  性能テスト  セキュリティ  コード構造  契約   使勝手│ │
│ │   ● 合格     ○ 未計測    ■ 不合格      ● 合格    ● 合格 ▲注意 │ │
│ │                                                               │ │
│ │  重大 1 件 ・ 高 1 件                                          │ │
│ │                                          [詳細] [トレンド]    │ │
│ └───────────────────────────────────────────────────────────────┘ │
│                                                                   │
│ 最後の完全計測: 2026-09-14 02:11（Run を見る）                    │
└───────────────────────────────────────────────────────────────────┘
```

| 項目 | 仕様 |
| --- | --- |
| データ取得 | `GET /api/v1/dashboard` 1 回のみ |
| 自動更新 | 60 秒間隔でポーリング。タブが非表示の間は停止する |
| 最後の完全計測 | カード下部に常時表示（FR-06-3） |
| 並び順 | 不合格 → 注意 → 合格 の順。同順位は最終計測日時の新しい順 |

不合格を先頭に並べるのは、**開く目的が「問題があるか確認すること」**だからである。
名前順に並べると、毎回同じ場所を目で探すことになる。

「最後の完全計測」を常時表示するのは、部分計測が続いたときに
**合格が実態より良く見える**ことを防ぐため。カードの判定が PASS でも、
最後に全指標を測ったのが 2 週間前なら、その PASS の意味は限定的である。

前回比は**差分そのもの**（`+0.5`）で示し、矢印の色だけに頼らない。

良し悪しは `判定` 列が担う。

### 4.3 S-03 Run 詳細

```
┌───────────────────────────────────────────────────────────────────┐
│ Run a1b2c3d   ■ 不合格   部分計測（未計測 4 件）      [再評価]    │

│ コミット a1b2c3d ↗ / 収集ワークフロー ↗ / 設定 v3（.gate.yml）    │
│ 比較対象: Run 9f8e7d6（2026-09-20）                               │
├───────────────────────────────────────────────────────────────────┤
│ ▼ 機能テスト                                          ● 合格      │
│   ブランチカバレッジ(backend)  82.4%  ≥75%  +0.5  ● 合格          │
│     しきい値 75% を満たしています                                 │
│   ミューテーションスコア        —     ≥60%   —    ○ 未計測        │
│     PR の計測では PIT を実行しない（申告あり）                    │
│                                                                   │
│ ▼ セキュリティ                                        ■ 不合格    │
│   重大・高 脆弱性件数           2 件   0 件  +2   ■ 不合格        │
│     Critical 1 件、High 1 件が未解決です                          │
│                                   [違反 2 件を見る →]             │
│                                                                   │
│ ▼ 性能テスト                                          ○ 未計測    │
│ ▼ コード構造 / 契約・互換性 / 使いやすさ              ● 合格      │
├───────────────────────────────────────────────────────────────────┤
│ 違反の内訳: 新規 2 ・ 継続 5 ・ 解消 3                            │
│ 取り込んだ成果物: 8 件（[一覧]）                                   │
└───────────────────────────────────────────────────────────────────┘
```

| 項目 | 仕様 |
| --- | --- |
| カテゴリ | API の `categories` をそのまま描画する。分類ロジックを画面に持たない |
| 判定理由 | `reason` をそのまま表示。文言はサーバが持つ |
| 未計測 | スキップ理由と「申告あり / 申告なし」を併記する |
| 計測条件 | 指標名の括弧内にコンポーネント名と並べて出す（「ミューテーションスコア（backend・変更範囲）」）。変更範囲だけの値を全量の値と読み違えないため |
| 指標の限界 | M-10 の行には、判定結果によらず「自動検査で検出できるのは WCAG 違反の一部であり、重大 0 件は適合の必要条件であって十分条件ではない」と注記する（[02](02-metrics-spec.md) M-10「限界の明示」）。判定理由とは別の段落にし、情報アイコンを添える |
| 折りたたみ | 不合格・注意を含むカテゴリは初期状態で展開、それ以外は折りたたむ |
| 処理失敗時 | 判定表の代わりに `error_code` と対処方法を表示し、再実行ボタンを出す |

不合格のカテゴリだけを展開するのは、**開いた瞬間に問題が見えている**状態にするため。
全部たたむと必ず探す操作が入り、全部開くと問題が他に埋もれる。

### 4.4 S-04 Finding 一覧

```
┌───────────────────────────────────────────────────────────────────┐
│ 違反一覧 — Run a1b2c3d                                            │
│ [指標: すべて ▾] [状態: 新規 継続 解消 ▾] [深刻度: ▾]             │
├───────────────────────────────────────────────────────────────────┤
│ 新規  重大  CVE-2026-1234: example-lib の任意コード実行           │
│       backend/pom.xml · com.example:example-lib 1.2.3 → 1.2.5     │
│       CVSS 8.1 · アドバイザリ ↗ · GitHub で見る ↗                 │
│ ─────────────────────────────────────────────────────────────── │
│ 継続  高    CVE-2025-9876: another-lib の情報漏洩                 │
│       backend/pom.xml · com.example:another-lib 2.0.0 → 2.0.4     │
│ ─────────────────────────────────────────────────────────────── │
│ 解消  高    CVE-2025-1111: old-lib の RCE（今回の変更で解消）     │
└───────────────────────────────────────────────────────────────────┘
```

| 項目 | 仕様 |
| --- | --- |
| 既定フィルタ | 状態 = 新規 + 継続（解消は明示的に選んだときだけ表示） |
| 並び順 | 状態（新規 → 継続 → 解消）→ 深刻度（重大 → 高 → …） |
| 外部リンク | `sourceUrl` は新しいタブで開き、リンクに「外部サイト」を示す |
| アクセシビリティ違反 | ファイルの代わりに「画面 `/runs/:id` · 要素 `.qg-metric__threshold` · axe impact: serious」と画面と要素で位置を示す。GitHub へのリンクは出さず、ルールの解説（axe の `helpUrl`）へのリンクを出す。深刻度は critical → 重大、serious → 高 で表示する |
| テスト・破壊的変更 | ファイルの位置を持たないため GitHub へのリンクは出さない。テストはテスト名を見出しにし、失敗理由（`message`）を添える。破壊的変更は「GET /api/v1/runs: 変更の説明」を見出しにし、「oasdiff level: error」を添える |

| 要素 | 仕様 |
| --- | --- |
| 系列 | 計測環境・コンポーネントごと。色はサーバが返す `colorIndex` で決める |
| 線の太さ | 2px。マーカーは 8px 以上 |
| しきい値 | `--text-muted` の破線のヘアライン + 直接ラベル。status 色は使わない |
| 未計測 | 線をつなげず**欠測**として描く。0 を打たない |
| 不合格の点 | マーカーを大きくし、`--status-fail` のリングと値ラベルを常時表示する |
| グリッド | `--gridline` のヘアライン。主要な目盛りのみ |
| ホバー | 十字線 + ツールチップ（日時・値・判定・Run へのリンク） |
| 凡例 | 常に表示。2 系列とも直接ラベルも付ける |

しきい値線に赤を使わないのは、**点の判定色と競合する**ためである。
しきい値は「基準」であって状態ではない。基準を赤で描くと、
その近くにある合格の点まで危険に見える。

#### 実装での確定事項

**グラフはインライン SVG で描く**（[04](04-tech-stack.md) 3.1）。当初の
Chart.js（canvas）から変更した。canvas は描画内容がスクリーンリーダーから
読めず、そのための回避策が必要になる。SVG なら回避策そのものが要らない。

`[表形式で見る]` は引き続き併設する。**読み上げのためではなく**、値をそのまま
読みたい・コピーしたいという要求に応えるためである。

| 項目 | 実装 |
| --- | --- |
| 欠測 | 線分を切って描く。前後をつなぐと計測していない期間に値があったように見え、0 を打つと最悪の値に落ちたように見える |
| 孤立点 | 前後を欠測に挟まれた点は線にできないため、マーカーだけで描く |
| y 軸の範囲 | 値の幅に余白を取り、**しきい値を必ず含める**。範囲外に出ると「基準に対してどこにいるか」が読めない |
| y 軸の下端 | 割合では 0 起点にしない。75〜95% の変化が潰れる。件数では 0 を含める（0 件に意味がある） |
| 目盛り | きりのよい数で、7 本以内。「範囲を n 等分」で決めると範囲によっては 2 本しか出ない |
| 直接ラベル | 最後に値を持つ点にだけ置く。全点に数字を出すと読まれなくなる |
| ラベルの重なり | 面の色で文字を縁取る（`paint-order: stroke`）。位置で避けようとしてもデータはどこにでも来る |
| 当たり判定 | マーカー（r=4）より大きい透明円（r=12）で取る。小さい点は狙えない |
| しきい値の変更 | 期間内に変わった場合、線は現在の基準として引き、変わったことを文で示す |

### 4.8 S-08 リポジトリ管理

リポジトリの登録（owner・名前・監視対象ブランチ）と、有効 / 無効の切り替えだけを行う。

Ingest Token は環境変数 `QG_INGEST_TOKEN` の 1 つで、画面では扱わない（D-27）。

（`collector/targets/<owner>__<name>.env`）と合格ライン（`.gate.yml`）を追加する。

### 4.9 S-09 管理

| --- | --- |

### 4.11 S-11 リリース判定（UC-10。FR-08-7〜10）

リポジトリ詳細の「リリース判定」から開く。タグかコミット SHA を入れて「判定する」。指定は URL の `?ref=` に置き、同じ判定を URL で共有できる。
読み手に経営陣や開発に詳しくない人を想定し、**結論 → 指標ごとの合否 → 各指標の説明と根拠**の順に並べる。結論と表の 3 列（指標・基準・判定）だけ読めば足りるようにする。

| 領域 | 内容 |
| --- | --- |
| 結論 | 「リリース可」「リリース可（注意あり）」「リリース不可」「判定できない」を見出しで出し、理由を 1 文で添える。左端の帯の色は補助で、文言とチップの記号でも分かるようにする |
| 前提 | タグ、コミット（GitHub へのリンク）、計測日時（Run 詳細へのリンク）と完全 / 部分計測、比較元のコミット（新規の違反などを数える起点。タグの計測では前のタグ）、合格ラインの版（既定値なら「既定値」）、計測から除外したパス、同じコミットのほかの計測の件数 |
| 指標ごとの合否 | 合否に使う指標の件数の内訳と、指標・何を見るか・基準・結果・判定の表。問題のある指標を先に並べる |
| 説明と根拠 | 指標ごとに「何を見るか」「基準の根拠」「基準を満たさないと」「計測ツール」（計測に使うライブラリ・ソフトウェア）と根拠の種類（外部基準 / 業界の目安 / チーム判断）。技術的な定義は「技術的な定義」を開いたときだけ見せる |
| CSV | 「CSV をダウンロード（証跡）」。出力は監査ログに残る |
| PDF | 「PDF として保存（印刷）」。印刷では入力欄と操作部品を隠す |

説明文は開発者以外も読むため、専門用語は括弧で補い、1 文を短くする。根拠の文は既定の基準についての説明であり、
基準を変えた場合の理由は合格ラインのコミットに残る（画面にその旨を書く）。

## 5. 画面の状態

すべての画面で 4 つの状態を実装する。

| 状態 | 表示 |
| --- | --- |
| 読み込み中 | スケルトン（レイアウトと同じ形）。スピナーは使わない |
| 空 | 何が無いかと、次に取るべき操作。例: 「まだ計測結果がありません。収集ランナーで計測すると表示されます」+ 設定手順へのリンク |
| エラー | 何が起きたか + 再試行ボタン。`traceId` を小さく表示し、問い合わせ時に参照できるようにする |
| 権限なし | 「この操作には管理者権限が必要です」。操作ボタン自体を隠さず、無効化して理由を示す |

権限のないボタンを隠さず無効化するのは、**機能の存在自体は知らせる**ため。
隠すと「そういう機能が無い」と誤解され、管理者に依頼する発想が生まれない。

スケルトンを使うのは、ダッシュボードとトレンドで
**読み込み後にレイアウトが動く**のを防ぐため。スピナーからコンテンツへの
切り替わりでは高さが変わり、クリックしようとした要素が移動する。

> 実装の現状: 読み込み中はスケルトンではなく「読み込み中…」の文言を表示している。
> エラー時は画面内にメッセージと再試行ボタンを出すが、`traceId` は表示していない。

## 7. 状態管理（Pinia）

| ストア | 保持する状態 |
| --- | --- |
| `useAuthStore` | ログイン中の利用者、ロール、権限判定（`isAdmin`） |
| `useDashboardStore` | ダッシュボードのサマリ、ポーリング制御 |
| `useRunStore` | 表示中の Run 詳細 |
| `useFindingsStore` | 表示中の Run の Finding 一覧と絞り込み条件 |
| `useTrendStore` | 選択中の指標・期間・ブランチ、取得済み系列 |
| `useUiStore` | テーマ、トースト（確認ダイアログはストアではなく `AppDialog.vue`） |

| 方針 | 内容 |
| --- | --- |
| API 呼び出し | すべて `openapi-fetch` のクライアント経由。ストアが直接 `fetch` を呼ばない |
| キャッシュ | 明示的に保持しない。画面遷移のたびに取得する |
| エラー処理 | 読み込みの失敗はストアの状態（`state: 'error'`）として持ち、画面内に再試行つきで表示する。登録・更新などの操作の失敗は `useUiStore` のトーストで知らせる |
| 型 | 生成された `schema.d.ts` の型をそのまま使い、独自の再定義をしない |

キャッシュを持たないのは、**古い判定結果を表示する事故のほうが重い**ためである。
表示速度は読み取りモデル（[06](06-database-design.md) 3.11）で担保する。
キャッシュが必要になった段階で TanStack Query の導入を検討する（[04](04-tech-stack.md) 8 章）。

型を再定義しない方針は重要である。`schema.d.ts` と手書きの型が併存すると、
API が変わったときにコンパイルエラーになる箇所と、
黙って型が合わなくなる箇所が混在する。

## 8. アクセシビリティ実装要件

WCAG 2.2 Level AA 準拠（NFR 10.6）。axe-core の critical / serious 違反 0 件が受け入れ基準（A-8）。

| # | 要件 |
| --- | --- |
| A-1 | すべての機能をキーボードのみで操作できる。マウス専用の操作を作らない |
| A-2 | フォーカスが常に可視。PrimeVue の既定リングを消さない |
| A-3 | ステータスを色だけで伝えない（3.1 の 4 channel） |
| A-4 | グラフに表形式の代替表現を併設し、DOM に存在させる。グラフはインライン SVG で描き、`role="img"` と要約の `aria-label` を付ける（[04](04-tech-stack.md) 3.1） |
| A-5 | 見出しレベルを飛ばさない。各画面に `<h1>` が 1 つ |
| A-6 | フォームの入力欄に `<label>` を関連付ける。エラーは `aria-describedby` で結び、`aria-invalid` を設定 |
| A-7 | 非同期の結果（保存完了、判定更新）を `aria-live="polite"` で通知 |
| A-8 | ダイアログはフォーカストラップし、閉じたら開いた要素へフォーカスを戻す |
| A-9 | 「スキップリンク」でヘッダを飛ばして本文へ移動できる |
| A-10 | 本文のコントラスト比 4.5:1 以上、UI 部品と図形は 3:1 以上 |
| A-11 | `prefers-reduced-motion` を尊重し、アニメーションを無効化できる |
| A-12 | ページタイトル（`<title>`）を画面ごとに設定し、遷移時に更新する |

### 検査対象ページ（quality-gate 自身の CI）

初期表示だけでなく**動的な状態も対象に含める**。
モーダルを開いた状態、検証エラーが出た状態、空状態は、
初期表示とは別の違反を含むことが多い。

| # | 対象 |
| --- | --- |
| 1 | `/login` |
| 2 | `/`（ダッシュボード、データあり） |
| 3 | `/`（空状態） |
| 4 | `/repositories/:id` |
| 5 | `/runs/:id`（不合格を含む） |
| 6 | `/runs/:id/findings`（フィルタ適用後） |
| 7 | `/repositories/:id/trends` |
| 8 | `/repositories/:id/config`（検証エラー表示状態） |
| 10 | `/admin/users` |
| 11 | `/forbidden` |
| 12 | `/repositories/:id/release`（技術的な定義を開いた状態） |

現在の検査対象は 1・4〜8・10〜12 と、リポジトリ管理（`/admin/repositories`）である
（`frontend/e2e/a11y.spec.ts` と `authenticated-a11y.spec.ts` に列挙する）。2・3 は応答例の書き出しが未整備のため検査していない。

検査結果は 1 検査 1 ファイルで `reports/axe/` に書き出し、最後に配列へ束ねて
`reports/axe-results.json` にする（`frontend/e2e/axe-report.ts`）。CI の成果物として残し、違反の内容をあとから確認できるようにする。

#### 検査はライト / ダークの両モードで行う

配色トークンはモードごとに別の値であり、片方が通っても他方の保証にはならない。
Playwright の `emulateMedia({ colorScheme })` で両方を検査する。

#### ログインが要る画面の検査方法

ログインを伴う画面は、**結合テストが実物の API から書き出した応答例**
（`frontend/e2e/fixtures/`）を `page.route` で返して描画し、検査する。
手で書いた応答例を置くと、API が変わっても検査は通り続け、実際の画面だけが壊れる。
書き出しは `RunQueryApiIT` などの結合テストが行い、`api/openapi.yml` と同じく生成物として追跡する（[API の型生成](../development/api-codegen.md)）。

検査の前に、画面に内容が描かれていることを必ず確認する。
**空のページは必ず「違反 0 件」になる**ため、これを省くと検査が空振りしていても気づけない。

> 自動検査で検出できる WCAG 違反は全体の一部にとどまる。
> 「重大 0 件」は AA 適合の必要条件であって十分条件ではない（[02](02-metrics-spec.md) M-10）。
> キーボード操作とフォーカス順序の手動確認を、リリース前のチェックリストに含める。
