# 合格ライン: 要件

対象ごとに「何を合格とするか」を定め、判定と画面に使う。設計は [design.md](design.md)。

## ユースケース

| UC | 利用者 | シナリオ |
| --- | --- | --- |
| UC-05 | Admin | 合格ラインを変える（例: カバレッジ 75% → 80%）。`*.gate.yml` をプルリクエストで変更し、マージ後の計測から反映される |
| UC-04 | 全員 | 設定の画面（S-06）で、直近の Run に送られた合格ラインと検証結果を確認する |

## 機能要件

| ID | 要件 |
| --- | --- |
| GATE-1 | 合格ラインはファイルで管理する（`collector/targets/<owner>__<name>.gate.yml`）。収集ランナーが Run ごとに送り、その内容で判定する |
| GATE-2 | 合格ラインをスキーマ検証し、不正なら判定せず、行番号とキー名つきで理由を示す。未知のキーも不正とする |
| GATE-3 | 判定に使った合格ラインを成果物として Run と同じ期間保持し、送った quality-gate リポジトリのコミットを記録する（判定の再現性）。版の履歴は Git で見る |
| GATE-4 | 指標ごとに有効・無効を切り替えられる。無効にした指標は計測も判定もしない |
| GATE-5 | PR の計測で申告してよいスキップ（`execution.skippable_metrics`）を合格ラインで決める |

## 受け入れ基準

- 各指標について、合格ラインをまたぐ値で PASS / FAIL が仕様どおり切り替わる
- 未知のキー・重複したキー・範囲外の値を書いた合格ラインで計測すると、Run が処理失敗（`CONFIG_VALIDATION_FAILED`）になり、設定の画面で該当行の直下に理由が出る
- 合格ラインを変えても、過去の Run の再評価は当時送られた合格ラインで行われる
