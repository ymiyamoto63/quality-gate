# リリース判定: 設計

要件は [requirements.md](requirements.md)。

## 1. API

| メソッド | パス | 応答 |
| --- | --- | --- |
| GET | `/api/v1/release?ref=` | `ReleaseReportResponse`。`ref` を省くと最新の判定済みの計測 |
| GET | `/api/v1/release/history` | `ReleaseHistoryResponse`（最大 50 件） |

対象は `QG_REPOSITORY` の 1 つだけのため、パスにリポジトリを含めない。

## 2. 指定の解決（`ReleaseRefResolver`）

- 16 進数 7〜40 桁はコミット SHA とみなし、計測済みのコミットから前方一致で探す（複数に一致すれば 400）。一致しなければ結論は「未計測」
- それ以外はタグ名とみなし、収集ランナーが計測時に送ったタグ（`runs.tags`）から探す。無ければ 404（タグを付ける前に計測したコミットはタグで引けない。DD-10）
- ブランチ名は受け付けない。ブランチの先頭は時間とともに動くため、証跡にならない

## 3. 結論

| 結論 | 条件 |
| --- | --- |
| `RELEASABLE`（リリース可） | 判定済みの Run の verdict が `PASS` |
| `NOT_RELEASABLE`（リリース不可） | verdict が `FAIL`（不合格か計測エラーの指標がある） |
| `NOT_MEASURED`（未計測） | そのコミットの判定済みの Run が無い（計測していない、または処理失敗だけ） |

- 使う Run は、そのコミットの最新の判定済みの attempt。判定し直さない（見るたびに結論が変わると証跡にならない）
- 理由の文言（`decisionReason`）はサーバが組み立て、画面はそのまま出す
- 対象外（`NOT_APPLICABLE`）の指標は合否に使わないため、応答に含めない

## 4. 指標の行

| 項目 | 内容 |
| --- | --- |
| 並び | 不合格・計測エラーを先に、その中は指標 ID の順 |
| 合格ライン | 判定に使った `measurements.threshold` を「≥ 75%」「≤ 0 件」「前回から +0 件以内」（M-10）のような文字列にする |
| 主な違反 | 合格でない行だけ。解消済みを除いた違反を、同じ指標（とコンポーネント）で絞り、深刻な順に最大 10 件。`findingCount` に総数を返す。ファイルと行があれば GitHub の該当箇所の URL を付ける |
| 説明 | 結果に現れた指標ごとに `MetricGuide`（何を見るか・根拠の種類と理由・満たさないと何が起きるか・技術的な定義・計測ツール） |

## 5. 画面（`/`）

上から次の順に並べる。

1. 結論（大きな見出し。色だけに頼らず、記号とアイコンと文言で示す）、理由、「品質基準 N 項目のうち M 項目が合格」、分野ごとの合否、タグ・コミット・計測日時（計測のログへのリンク）・比較元
   - 分野ごとの合否は 6 カテゴリ（機能テスト・性能テスト・セキュリティ・コード構造・契約・互換性・使いやすさ）を決まった順に並べる。1 項目でも不合格なら不合格、次に計測エラー、それ以外は合格。判定した項目が無い分野も「未計測」として残し、計測していない分野に気付けるようにする。行の `category` を画面で集計するだけで、API は変えない
2. 品質基準ごとの合否（判定・指標・何を見るか・合格ライン・結果。合格でない行には理由と、開ける「主な違反」。合格の行の理由は出さない）
3. 各指標の説明と基準の根拠
4. 判定の履歴（印刷には含めない）

- 指定は `?ref=` に置き、URL で同じ判定を共有できる
- 「PDF として保存（印刷）」はブラウザの印刷を使う。ヘッダ・入力欄・履歴は印刷しない
- アクセシビリティは [アーキテクチャ](../../architecture.md#77-アクセシビリティ) に従い、リリース不可の状態（主な違反を開いた状態）で自動検査する
