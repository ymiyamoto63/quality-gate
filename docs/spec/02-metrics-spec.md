# quality-gate 指標・判定仕様

[要件定義書](01-requirements.md) 6 章の詳細。各指標について
**定義 / 計算式 / 入力フォーマット / しきい値 / 境界条件 / fingerprint** を定める。

この文書の目的は、**同じリポジトリを誰がいつ計測しても同じ数値になる**ことを保証することにある。
指標の定義が曖昧だと、数値は出ても比較できず、ゲートとして機能しない。

---

## 0. 共通事項

### 0.1 判定ステータス

| ステータス | 条件 |
| --- | --- |
| PASS | 実測値が合格ラインを満たす |
| WARN | 合格ラインは満たすが注意水準に該当（指標ごとに定義） |
| FAIL | 実測値が合格ラインを満たさない |
| SKIP | 計測対象外。`enabled: false` による設定上の除外、または収集ランナーからのスキップ申告 |
| ERROR | 提出されるはずの成果物が未提出 / 形式不正 / 必須メタデータ欠落で値を確定できない |
| NOT_APPLICABLE | ツールの制約で、そのコンポーネントでは測りようがない（M-02 の frontend など）。集約にも部分計測にも影響しない |

`ERROR` は既定で Run 全体を FAIL にする（fail-closed）。

### 0.2 計測の対象範囲（exclusions）

合格ライン（`*.gate.yml`）の `exclusions` に列挙した glob パターンに一致するファイルは、
**全指標で共通に**計測対象から除外する。除外は設定版として記録され、
Run 詳細で「除外パターン N 件により M ファイルを除外」と明示する。

除外の濫用を防ぐため、除外により対象外となったファイル数と割合をダッシュボードに表示し、
除外率が 20% を超えた場合は警告を出す。

#### パターンはツールが報告するパスの形に合わせる

除外パターンの照合対象は、**成果物に書かれているパスそのもの**である。
ツールによって形が違うため、リポジトリ相対で書くと一致しない。

| ツール | 報告されるパスの形 | 例 |
| --- | --- | --- |
| JaCoCo | パッケージ相対 | `com/qualitygate/evaluate/Big.java` |
| PIT | パッケージ相対（`mutatedClass` のパッケージ + `sourceFile` から組み立て、JaCoCo と揃える） | `com/qualitygate/evaluate/Big.java` |
| lcov（Vitest） | コンポーネント相対 | `src/api/schema.d.ts` |
| SARIF | リポジトリ相対 | `backend/pom.xml` |
| PMD | 絶対パス（quality-gate 側で `src/` 以降に正規化） | `src/main/java/com/qualitygate/Big.java` |
| axe-core | 画面の URL（ファイルではない） | `http://localhost:5173/runs/0190…` |

axe-core の違反はファイルではなく画面の要素を指すため、`exclusions` は M-09 に適用しない。
検査する画面は `accessibility.pages` と、どの画面を検査するかという E2E テスト側で決める。

そのため `backend/**/generated/**` のようなリポジトリ相対のパターンは
JaCoCo のレポートに一致しない。**`**/` を先頭に付けた接尾一致で書く**こと
（`**/generated/**`）。

暗黙に `**/` を補うことはしない。書いたパターンより広い範囲が黙って除外されると、
除外率の警告をすり抜けて計測対象が縮む。一致しなかった場合は
「除外 0 件」として Run 詳細に現れるため、書き間違いはそこで気づける。

#### 名寄せ用のパスと表示用のパスは分ける

上表の「正規化後の形」は**名寄せ（fingerprint）と除外の照合に使う**パスである。
PMD の場合はモジュール相対（`src/main/java/...`）であり、base 側と head 側で
チェックアウト先が違っても同じ関数が同じ identity になるようにするための形である。

一方、Finding の `filePath` と `sourceUrl` は**リポジトリ相対**でなければならない。
モノレポではモジュール相対のままリンクを組み立てると 404 になる。

そのため PMD アダプタは、アップロード時に宣言されたコンポーネント名が
PMD の出した絶対パスに実際に `/<component>/<モジュール相対>` の形で
現れている場合にだけ接頭辞を付ける。推測で付けると、逆に壊れたリンクを作る。
コンポーネント宣言のない単一モジュール構成では、モジュール相対パスが
そのままリポジトリ相対パスである。

### 0.3 「差分」「新規」の基準

差分を扱う指標（M-07 の新規関数、M-08 の破壊的変更、M-02 を変更範囲で実行する場合）では、
比較基準を次のとおり定める。

| ケース | 比較基準（`baseCommitSha`） |
| --- | --- |
| PR の Run | PR のヘッドコミットと、ベースブランチとの **merge-base** |
| タグの Run（リリース判定。[03](03-design-decisions.md) DD-17） | **前のタグ**のコミット。前のタグが無ければ直前のコミット |
| ブランチへの push の Run | そのブランチの直前の Run のコミット SHA。初回は既定ブランチとの merge-base |

`baseCommitSha` は収集ランナーが算出して Ingest API に渡す。
収集ランナーは clone した履歴から上表のとおり算出する（既定ブランチでは直前のコミット、PR ではマージ先との merge-base、
タグでは前のタグ。実行時に比較元のコミットかタグを指定することもできる）。

比較対象 Run（前回比・違反の新規 / 継続 / 解消・M-11 の増加の起点）は、比較元コミットで判定済みの Run があればそれ、
無ければ同じブランチで直前に計測した Run とする。計測は手動で順不同になるため（DD-7）、
「直前に計測した Run」がリリースのタグより新しいコミットのこともあり、比較元コミットを優先する（DD-17）。
未指定の場合（最初のコミットなど）は比較元なしで判定する。

### 0.4 fingerprint

Finding を Run をまたいで同一と見なすキー。
**行番号を含めない**ことが原則（無関係な編集による行ずれで「新規」と誤判定しないため）。

| 指標 | fingerprint の構成 |
| --- | --- |
| M-06 脆弱性 | `sha256(metricId + パッケージ名 + 脆弱性ID)`（バージョンは含めない。更新で解消したことを追跡するため別途 version を保持） |
| M-07 複雑度 | `sha256(metricId + ファイルパス + 完全修飾関数名 + パラメータ型リスト)` |
| M-08 破壊的変更 | `sha256(metricId + 変更 ID + メソッド + パス + 説明文)`（M-08「詳細仕様」） |
| M-10 / M-11 テスト | `テストクラス名#テスト名`（M-10「違反」） |
| M-09 a11y | `sha256(metricId + ページパス + ルールID + 要素の CSS セレクタ)`。ページパスは ID を `:id` に置き換えたもの（M-09「詳細仕様」） |

ファイル移動・リネームにより fingerprint が変化する場合、git の rename 検出結果を用いて
移動前の fingerprint との対応表を Run に保持し、「新規発生」と誤って扱わない。
fingerprint にファイルパスを含むのは M-07 だけなので、対象は M-07。

- 移動の対応表（新しいパス → 移動前のパス）は、収集ランナーが clone した履歴から求めて成果物 `git-renames` として送り
  （`collector/bin/renames.sh`）、判定のときにそれを読む（DD-10）。
  比較元コミット（M-07 の比較元）と比較対象 Run のコミット（違反の新規 / 継続）の両方からの移動を使う。
  - 比較元からの移動は `git diff -M`（git の rename 検出。類似度 50% 以上）の結果をそのまま使う
  - 比較対象 Run は判定のときに決まるため、収集ランナーは計測するコミットから first-parent を 1,000 コミットたどり、
    コミットごとの移動（`git log -M`）を送る。判定では比較対象 Run のコミットより後の移動を古い順につなげる。
    履歴に無いコミット（1,000 コミットより前、別のブランチ）からの移動は取りこぼす（取りこぼした移動は新規として扱う）
- 対応表は Run に保持し、再評価では求め直さない。`git-renames` の無い Run では移動を追跡しない（判定は続ける）
- 移動した関数の違反は、移動後の fingerprint で保存する。比較対象に移動前の fingerprint で残っていれば
  「継続」とし、移動前の違反を「解消」にしない

SARIF 2.1.0 を静的解析系の第一形式とする。SARIF で出せるツールは SARIF で提出する。
これによりアダプタ実装が 1 本に集約でき、ツールの差し替えコストが下がる。
ただし `sarif` は M-06 にだけ使う。複雑度を報告するツール（PMD / ESLint など）の SARIF は、
M-06 の件数に混入させないため読み飛ばす。

上の形式はすべてアダプタを実装済みである。形式ごとの読み方の要点:

| `type` | 読み方 |
| --- | --- |
| `eslint-json` | `eslint -f json` の出力のうち `complexity` ルールの報告だけを読む。全関数の CC を得るため、ルールは上限 0（`["error", 0]`）で動かす。関数名の無い関数はファイル内の出現順で区別する。収集ランナーは対象の ESLint の設定を使わず、quality-gate 側で版を固定した設定（`collector/complexity`）で head と base の両方を解析する |
| `test-junit-xml` | Surefire / Failsafe の `TEST-*.xml` と Vitest の junit reporter の出力。`<testcase>` を 1 件ずつ数え直す（M-10「テストの数え方」） |

## M-01 ブランチカバレッジ

### 定義

分岐網羅率。条件分岐の各真偽経路のうち、テストで実行されたものの割合。

```
ブランチカバレッジ (%) = 実行された分岐数 / 全分岐数 × 100
```

行カバレッジではなく**ブランチカバレッジ**を採用する理由は、
行カバレッジは `if` 文を通過しただけで満たされてしまい、
分岐の片側しかテストしていないコードを検出できないため。

### 入力と抽出方法

**Java（JaCoCo）** — `jacoco.xml` の `<counter type="BRANCH" missed="M" covered="C"/>`

```
分岐カバレッジ = C / (C + M) × 100
```

集計はレポートのルート `<report>` 直下の BRANCH counter を用いる。
`exclusions` 適用時は、除外対象クラスの counter を差し引いてから再計算する。

**TypeScript / Vue（Vitest）** — `lcov.info` の `BRF`（found）/ `BRH`（hit）。

> Vitest の coverage provider は `v8` と `istanbul` で分岐の数え方が異なる。
> 同一リポジトリ内で provider を統一すること。provider は計測メタデータとして提出し、
> 変更された場合はトレンド上で系列を分ける。

### しきい値と集計単位

| 項目 | 値 |
| --- | --- |
| 合格ライン | 75% 以上 |
| 集計単位 | コンポーネント単位（backend / frontend を**別々に**判定） |
| WARN 水準 | 75% 以上 80% 未満（`warn_below`。省略すると合格ライン + 5）、または前回比で 1 ポイント以上の低下 |

**コンポーネントを合算しない**理由は、片方の高いカバレッジがもう片方の低さを隠すため。
全体値を出す場合は **分岐数による加重平均**で算出し、単純平均は用いない。

### 判定の方式

判定は全体値（コンポーネントごと）の絶対値で行う。対象リポジトリは既にベースラインが整っているため、
段階的なしきい値の引き上げ（ラチェット方式）は採用しない。

なお、新規に追加されるリポジトリでベースラインが大きく乖離している場合は、
そのリポジトリに限り `threshold` を個別設定し、達成可能な水準から開始する
（達成不可能なしきい値は無視され、ゲート全体の信頼性を損なうため）。

### 境界条件

| 条件 | 扱い |
| --- | --- |
| 分岐が 0 個（分岐のないコンポーネント） | 100% ではなく `N/A` とし、判定は PASS。UI に「分岐なし」と明示 |
| レポート未提出 | ERROR |
| 差分に変更行が 0 行（ドキュメントのみの変更など） | `N/A` / PASS |
| テストが 0 件実行された | ERROR（空実行の検知。カバレッジ 0% ではなく計測失敗として扱う） |

## M-02 ミューテーションスコア

### 定義

ソースコードに人工的な変更（ミューテーション）を加え、テストがそれを検出（kill）できた割合。
**カバレッジが「テストがコードを通ったか」を測るのに対し、ミューテーションスコアは
「テストが不具合を検出できるか」を測る**。カバレッジの水増し（アサーションのないテスト）を
見破れる点で、機能テストの実効性を測る指標として重要。

### 計算式（ツール間で統一）

```
ミューテーションスコア (%) = (Killed + Timeout) / (Killed + Timeout + Survived + NoCoverage) × 100
```

- 分母から除外するもの: `CompileError`、`RuntimeError`、`Ignored`（ツールの都合による非実行）
- **`NoCoverage`（カバーされていないミューテーション）は分母に含める**。
  除外すると、未テスト箇所が多いほどスコアが高く出る逆転が起きるため

> PIT は独自の「Mutation Coverage」を出力するが、集計対象の扱いが上記と異なるため、
> quality-gate は**ツールの出力値をそのまま使わず、`mutations.xml` の各 status を
> 数え直して上記の式で再計算する**。

### 対象範囲：backend（Java）のみ

ミューテーションテストには **PIT（pitest）を用いる**。PIT は JVM 言語専用であるため、
**本指標の対象は backend（Java / Spring Boot）に限られる**。

frontend（Vue 3 / TypeScript）のミューテーションスコアは計測しない。
フロントエンドのテストの実効性は M-01 ブランチカバレッジで担保し、
必要が生じた場合に Stryker Mutator の導入を将来検討する（スコープ外）。

この結果、ダッシュボードおよびレポートにおいて M-02 は backend コンポーネントにのみ
表示され、frontend では `対象外` と表示する。**`SKIP` や `N/A` ではなく
「ツール制約による対象外」であることを明示する**こと。未計測と混同させないためである。

### 入力

**PIT**: `mutations.xml` の各 `<mutation status="...">` を集計する。

| PIT の status | 上式での扱い |
| --- | --- |
| `KILLED` | Killed |
| `TIMED_OUT` | Timeout |
| `SURVIVED` | Survived |
| `NO_COVERAGE` | NoCoverage |
| `MEMORY_ERROR` / `RUN_ERROR` | 分母から除外 |
| `NON_VIABLE` | 分母から除外（生成されたミューテーションがコンパイル不能） |

### ランナーの影響

PIT の結果はマシン性能に概ね依存しないため、どのランナーで実行しても**同じ基準で判定する**。

ただし 1 点だけ注意がある。遅いランナーでは `TIMED_OUT` となるミューテーションが増え、
計算式上これは `Killed` 側に加算されるため、**スコアが実態より高く出る**。
そのため `Timeout` の比率が全体の 10% を超えた場合は WARN を付与し、
ランナー性能による過大評価の疑いを明示する。

### しきい値と実行範囲

| 項目 | 値 |
| --- | --- |
| 合格ライン | 60% 以上 |
| 対象コンポーネント | backend のみ |
| 集計単位 | コンポーネント単位 |
| WARN 水準 | 60% 以上 65% 未満、または前回比で 2 ポイント以上の低下 |
| 実行範囲 | 収集ランナーは PR 以外の計測で全量（`all`）を実行し、PR では実行しない（DD-17）。変更範囲（`changed`）の値も受け付ける |

ミューテーションテストは実行時間が長い（全量では単体テストの数十倍）。
そのため収集ランナーは PR の計測では実行しない。

**実行範囲は計測メタデータとして必ず提出する**こと。変更範囲限定の値と全量の値は
比較不能であるため、トレンド上で別系列として扱う。

### 境界条件

| 条件 | 扱い |
| --- | --- |
| 生成されたミューテーションが 0 個 | `N/A` / PASS（変更がロジックを含まない場合） |
| 変更ファイルが 0 件（変更範囲で実行した場合） | `N/A` / PASS |
| `NON_VIABLE` + `RUN_ERROR` が全体の 10% を超える | ERROR（ミューテーション生成が正常に機能していない疑い） |
| `TIMED_OUT` が全体の 10% を超える | WARN（遅いランナーによるスコアの過大評価の疑い） |
| スキップが申告された | `SKIP`（ERROR にはしない。6.4 の申告制に従う） |
| frontend コンポーネント | `対象外`（ツール制約。ERROR にはしない） |
| backend のレポート未提出 | ERROR |

### 詳細仕様

上の定義を実装に落とす際に決めた事項。

**実行範囲は取り込み時に必須とする。** PIT の成果物（`pit-xml`）は、アップロード時の
`metadata` に `{"mutationScope": "changed"}` または `{"mutationScope": "all"}` を付ける。
無ければ `422 MUTATION_SCOPE_MISSING`、値が選択肢に無ければ `400 VALIDATION_FAILED` で拒否する。
判定時ではなく取り込み時に拒否するのは、収集ランナーのログに残して送信側で直せるようにするためである。
範囲の分からない値は、後から正しい系列に振り分けられない。

**実行範囲は計測条件（`variant`）として値に添える。** 前回比は同じ実行範囲の値とだけ取る
（比較対象 Run の値が別の範囲なら前回値なし）。トレンドも範囲ごとに別の系列にし、
「backend（変更範囲）」「backend（全量）」のように描く。範囲の分からない計測エラーは
新しい系列を作らず、同じコンポーネントの既存の系列の欠測として描く。

実行範囲は設定では決めない（成果物のメタデータで申告する）。

**status の対応で表に無いもの**:

| PIT の status | 扱い |
| --- | --- |
| `MEMORY_ERROR` | `RUN_ERROR` と同じく分母から除外し、失敗件数に数える |
| `STARTED` / `NOT_STARTED` / 未知の値 | 解析が完了しなかったものとして「未完了」に数え、失敗件数に含める。黙って捨てると分母から消えて気づけない |

「全体の 10% を超える」の判定に使う失敗件数は `NON_VIABLE` + `RUN_ERROR` + `MEMORY_ERROR` + 未完了、
分母はミューテーションの総数（除外後）とする。ちょうど 10% は超えないものとして扱う（`TIMED_OUT` も同じ）。
失敗が 10% を超えた場合は ERROR とし、**値を持たせない**。生き残ったはずの mutation が
失敗側に紛れている可能性があり、数字を信じる根拠が無いためである（内訳は `detail` に残す）。

**複数の成果物は件数で合算する。** Maven のマルチモジュールのように、同じコンポーネントに
`mutations.xml` が複数届いた場合は status ごとの件数を足してから式を当てる。割合どうしを
平均すると、母数の違うモジュールが同じ重みで混ざる。実行範囲の違う成果物が同じ
コンポーネントに混在した場合は、どちらでもない値になるため ERROR とする。

**判定の優先順位**は、ミューテーション 0 個（値なしの PASS）→ 失敗 10% 超（ERROR）→
しきい値未満（FAIL）→ 注意水準未満 → `TIMED_OUT` 10% 超 → 前回比 2 ポイント以上の低下（以上 WARN）
→ PASS とする。上で決まったものは下を見ない。

**対象外（`NOT_APPLICABLE`）の出し方。** 設定の `mutation_score.components` で対象を
限定している場合に限り、次の行を出す。

| 状況 | 扱い |
| --- | --- |
| この Run で他の指標を計測したコンポーネントが対象に含まれない（frontend の M-01 はあるが M-02 は対象外） | そのコンポーネントの M-02 を `NOT_APPLICABLE` として並べる |
| 対象外のコンポーネントから PIT の成果物が届いた | 判定に用いず `NOT_APPLICABLE` とする。対象を絞った設定に反して合否を左右させない |
| 対象のコンポーネントの成果物が無い | そのコンポーネントを ERROR とする（fail-closed） |
| コンポーネント宣言の無い成果物がある | 全体の値として判定し、上の欠落確認は行わない（どのコンポーネントの値か知る手がかりが無い） |

リポジトリの構成（`components`）を別に持たず「この Run に現れたコンポーネント」を使うのは、
実際に計測しているものだけを並べるためである。`NOT_APPLICABLE` は合否にも部分計測にも
影響せず、トレンドにも系列を作らない。

**違反（Finding）は作らない。** 生き残った mutation を違反として保存すると、実行範囲の違う
Run が続いたときに「解消」「新規」が範囲の切り替えだけで入れ替わる。個々の mutation は
PIT の HTML レポートで確認する。

## M-03 / M-04 / M-05 性能（応答時間 p95 / スループット / エラー率）

### 定義

| ID | 指標 | 定義 |
| --- | --- | --- |
| M-03 | 応答時間 p95 | 計測区間内の全 HTTP リクエストの応答時間の 95 パーセンタイル値（ms） |
| M-04 | スループット | 計測区間内の成功リクエスト数 ÷ 計測秒数（req/s） |
| M-05 | エラー率 | 計測区間内の失敗リクエスト数 ÷ 全リクエスト数 × 100 |

応答時間はクライアント（負荷生成側）が観測した値とし、
接続確立からレスポンスボディ受信完了までを含む。サーバ内部の処理時間ではない。
静的アセットの配信は対象に含めず、**API リクエストのみ**を対象とする。

### 計測条件（統制項目）

性能値は計測条件に強く依存するため、以下を **必須の統制項目**とし、
条件が異なる Run はトレンド上で別系列として扱う。

| 項目 | 規定 |
| --- | --- |
| 負荷モデル | `constant-arrival-rate`（到達率一定）。VU 数固定ではなく到達率を固定する |
| ウォームアップ | 60 秒。**集計から除外する**（JIT コンパイル、コネクションプール、キャッシュの温まりを排除） |
| 計測時間 | 300 秒（ウォームアップ後） |
| 実行環境 | 専有の自ホスト型ランナー。他ジョブと同居させない |
| データ量 | 本番相当のシードデータ（プロファイル名を `datasetProfile` として提出） |
| 実行回数 | 3 回実行し、**中央値**を採用する（外れ値の影響を抑える） |
| 対象シナリオ | 合格ライン（`*.gate.yml`）の `scenarios` に列挙した主要業務シナリオ |

これらは Ingest API の `environment` メタデータ（要件定義書 7.1 「Ingest API」）として提出する。
欠落した場合は ERROR とする。

### 実行環境（重要）

上記の統制項目のうち「実行環境」は、性能指標にとって決定的である。
計算資源を共有するランナー（GitHub ホストランナーなど）は実行ごとに性能が変動するため、
**絶対値しきい値（p95 500ms）による判定に耐えない**。性能は専有のセルフホストランナーで動く
収集ランナーだけが計測する（DD-11）。

計測環境の名前（`environment.name`）ごとにトレンドの系列を分け、別の環境の値と同じ線で結ばない。
混ぜると、環境差による変動がアプリケーションの性能変化に見えてしまうためである。

### しきい値

| 指標 | 合格ライン | WARN 水準 |
| --- | --- | --- |
| M-03 応答時間 p95 | 500ms 以内（**全体、かつ各シナリオ単位の双方**） | 400ms 超 500ms 以内 |
| M-04 スループット | 到達率 50 req/s を**負荷条件として固定**し、その条件下で判定（下記参照） | 実測到達率が設定値の 95% 未満 |
| M-05 エラー率 | 0.1% 以下 | 0.05% 超 0.1% 以下 |

全体 p95 だけを見ると、リクエスト数の多い軽量エンドポイントが重いエンドポイントの遅さを
薄めてしまう。そのため**シナリオ単位でも p95 を判定する**。

#### スループットの扱い

スループットは「達成した値を測る指標」ではなく、**応答時間を測るための負荷条件**として扱う。

```
負荷条件: 到達率 50 req/s（constant-arrival-rate）で 300 秒間
合格条件: その条件下で p95 ≤ 500ms かつ エラー率 ≤ 0.1%
```

負荷を結果変数にすると、負荷が低いほど応答時間が良く見えるため、
「p95 500ms 以内」が単独では意味を持たなくなる。到達率を固定することで、
応答時間の比較可能性が担保される。

実測の到達率が設定値を大きく下回る場合（アプリが捌けずキューが詰まっている場合）は
WARN を付与する。この状態では p95 が実態より楽観的に出るためである。

到達率 50 req/s は初期値である。導入初回の計測で現行の実力値を確認し、
ピーク時の想定負荷を踏まえて必要なら見直す（設定値の変更は 合格ライン（`*.gate.yml`）の
更新のみで完結し、変更履歴は設定版として保持される）。

### 境界条件

| 条件 | 扱い |
| --- | --- |
| `environment` メタデータの欠落 | ERROR |
| スキップが申告された | `SKIP`（ERROR にはしない） |
| 3 回実行のうち 1 回でも異常終了 | ERROR（部分的な結果で判定しない） |
| 3 回の p95 の変動係数が 20% を超える | WARN を付与（計測環境が不安定である旨を明示） |
| エラー率が 5% を超える | 性能値を判定に用いず ERROR（負荷試験自体が成立していない） |
| 計測環境の構成が前回から変化 | 判定は行うが、トレンドは新系列として描画し、比較値を表示しない |

### 詳細仕様

**1 ファイル = 1 回の実行。** 収集ランナーは k6 の summary（`k6 run --summary-export` の出力、または
`handleSummary` で `JSON.stringify(data)` したもの）を 3 回分、それぞれ `k6-summary` 型で送る。
quality-gate は同じコンポーネント・同じ計測環境に届いた値を「同条件の繰り返し」とみなし、
**値ごとの中央値**で判定する（p95 / スループット / エラー率をそれぞれ中央値にする）。

**計測環境の名前（`environment.name`）は取り込み時に必須とする。** 無ければ
`422 PERFORMANCE_METADATA_MISSING`。名前は計測条件（`variant`）として値に添え、
前回比は同じ環境の値とだけ取り、トレンドも環境ごとに別系列にする。名前が変われば比較値は出ない。
これが「計測環境の構成が前回から変化」の扱いになる（構成を変えたら環境名も変える運用とする）。

**ウォームアップの除外は k6 側のタグで行う。** 計測区間のリクエストに `phase: measure` のタグを付け、
`http_req_duration{phase:measure}` などにしきい値を定義して部分指標を出力させる。
アダプタはこの部分指標があれば全体の指標より優先する。
シナリオ単位の p95 は `http_req_duration{scenario:<名前>}` から読む。

**値の定義:**

| 指標 | 値 | 単位 |
| --- | --- | --- |
| M-03 | 計測区間の `http_req_duration` の `p(95)` | ms |
| M-04 | `http_reqs.rate × 成功件数 / 全件数`（成功したリクエストのスループット） | req/s |
| M-05 | `http_req_failed` の `passes`（失敗 = 真の件数）÷ 全件数 × 100 | % |

**判定の優先順位**（上で決まったものは下を見ない）:

1. エラー率（中央値）が 5% 超 → 3 指標とも ERROR（値は持たせない）
2. M-03: 設定の `scenarios` のうち summary に無いシナリオがある → ERROR
3. しきい値による判定
   - M-03: 全体またはいずれかのシナリオが `p95_ms` 超で FAIL。3 回の変動係数が 20% 超、
     または全体・シナリオが注意水準（`p95_ms` の 80%）超で WARN
   - M-04: FAIL は出さない。到達率の 95% 未満で WARN
   - M-05: `error_rate_pct` 超で FAIL、その半分超で WARN
5. 上で PASS になっても、実行回数が 3 回未満なら WARN（中央値の根拠が弱い）

**異常終了。** 実行が異常終了した回の成果物は metadata に `"aborted": true` を付けて送る。
その Run の性能指標は ERROR になる（部分的な結果で判定しない）。
リクエスト 0 件の summary も同じく読まない。

## M-06 重大・高 脆弱性件数

### 定義

深刻度 Critical または High と判定された、未解決の脆弱性の件数。

### 対象スコープ

| 種別 | 対象 | ツール例 |
| --- | --- | --- |
| SCA（依存ライブラリ） | Maven / Gradle 依存、npm 依存 | Trivy、OWASP Dependency-Check、OSV-Scanner |
| SAST（ソースコード） | Java、TypeScript / Vue | Semgrep、SpotBugs + FindSecBugs |
| コンテナイメージ | ビルド成果物のイメージ | Trivy |
| シークレット混入 | リポジトリ全体 | gitleaks |

> SARIF のメタデータで走査した対象（`scanners`）を申告した場合、シークレットは M-06 ではなく
> **M-12** で、ライセンスは **M-13** で数える（[M-12 / M-13](#m-12-シークレット検出件数--m-13-ライセンス違反件数)）。
> 申告の無い SARIF では、シークレットも M-06 として数える。

### 深刻度の正規化

ツールごとに severity の表記と基準が異なるため、**CVSS スコアを正とする正規化**を行う。

| 正規化後 | CVSS v3.1 / v4 Base Score |
| --- | --- |
| Critical | 9.0 – 10.0 |
| High | 7.0 – 8.9 |
| Medium | 4.0 – 6.9 |
| Low | 0.1 – 3.9 |

CVSS スコアが提供されない検出（SAST やシークレット混入など）については、
ツール固有 severity からのマッピング表を設定として保持する。
マッピング表は UI で閲覧でき、変更は監査ログに記録される。

| 例: ツール固有 | 正規化後 |
| --- | --- |
| Semgrep `ERROR` + `security` カテゴリ | High |
| Semgrep `WARNING` | Medium |
| gitleaks の検出（すべて） | Critical（有効なシークレットの混入は常に重大として扱う） |

### 重複排除

複数ツールが同一の脆弱性を報告するため、以下のキーで重複排除する。

- SCA: `(パッケージ名, 脆弱性ID)` — CVE ID / GHSA ID が異なる表記でも、
  エイリアス関係（GHSA ↔ CVE）が判明しているものは同一と見なす
- SAST: `(ルールID, ファイルパス, 正規化したコードスニペットのハッシュ)`

### しきい値

| 項目 | 値 |
| --- | --- |
| 合格ライン | Critical 0 件 かつ High 0 件 |
| WARN 水準 | Medium が前回比で増加した場合 |
| Medium / Low | 判定対象外（可視化のみ） |

### 判定から外したいとき

修正版が未提供の脆弱性などで判定から外す必要があるときは、
合格ライン（`*.gate.yml`）の変更（しきい値や `exclusions`）として扱い、理由をコミットに残す。

### 境界条件

| 条件 | 扱い |
| --- | --- |
| スキャン成果物が未提出 | ERROR |
| スキャン対象が 0 件（依存が解決できていない） | ERROR（脆弱性 0 件ではなくスキャン失敗として扱う） |
| CVSS スコアもツール severity も欠落 | Medium として扱い、UI に「深刻度不明」と明示 |
| コード変更なしで新規 CVE により不合格に転じた | FAIL とする（計測し直したときに判定が変わる） |

## M-07 循環的複雑度 15 超の新規関数数

### 定義

McCabe 循環的複雑度（Cyclomatic Complexity, CC）が **15 を超える「新規関数」** の数。

CC はコード中の線形独立な経路数であり、テストで網羅すべき経路数の下限に相当する。
CC が高い関数はテストが困難で、欠陥が混入しやすい。

### 「新規関数」の定義（重要）

既存のレガシーコードを一括で不合格にしないため、対象を次の 2 種に限定する。

| 区分 | 条件 |
| --- | --- |
| (a) 新規追加 | `baseCommitSha` 時点に存在せず、対象コミットで新たに追加された関数で、CC > 15 |
| (b) 変更による悪化 | `baseCommitSha` 時点にも存在するが、本変更で本体が変更され、かつ **CC がベース時点より増加し、その結果 15 を超えた**もの |

**対象外**: ベース時点ですでに CC > 15 であり、本変更で CC が増加していない関数
（変更していても、複雑度を悪化させていないなら通す）。
これらは「既存の技術的負債」として別枠で可視化し、削減状況をトレンド表示する。

### 関数の同定

| 言語 | 同定キー |
| --- | --- |
| Java | `ファイルパス + パッケージ + クラス名 + メソッド名 + パラメータ型リスト` |
| TypeScript / Vue | `ファイルパス + （名前空間があれば含む）関数名 + パラメータ数` |

匿名関数・アロー関数は、宣言位置（親スコープの関数名 + 出現順）で同定する。

ファイルの移動・リネームは git の rename 検出結果（類似度 50% 以上）を用いて追跡し、
移動のみで「新規追加」と誤判定しない（0.4。比較元の CC を移動前の fingerprint でも引く）。

### 入力

| 言語 | ツール | 備考 |
| --- | --- | --- |
| Java | PMD `CyclomaticComplexity`（`reportLevel: 1`） | reportLevel を 1 にすることで、閾値超過だけでなく**全関数の CC 値**を取得する。ベース比較に必要 |
| TypeScript | ESLint `complexity`（`{ "max": 0 }` + JSON 出力） | 同様に全関数の CC を取得する |
| Vue SFC | ESLint + `vue-eslint-parser` | `<script setup>` ブロックを解析対象に含める |

> ツールによって CC の算出アルゴリズムに差がある（`&&` / `||` を数えるか、
> `switch` の各 `case` を数えるか等）。**同一リポジトリでは同一ツールを使い続ける**こと。
> ツールを変更した場合はトレンド上で系列を分ける。

M-07 として読めるのは PMD の XML（`pmd-xml`）と ESLint の JSON（`eslint-json`）である。
ESLint は SARIF ではなく JSON（`eslint -f json`）で送る（`sarif` の複雑度は M-06 に混ぜないため読み飛ばす）。

**収集ランナーのフロントエンド。** 収集ランナーは backend（PMD）に加えて frontend も ESLint で解析する。
対象リポジトリの ESLint の設定とプラグインは使わず、quality-gate 側で版を固定した設定
（`collector/complexity`。ESLint・typescript-eslint・vue-eslint-parser）で、`complexity` 以外のルールを
動かさずに解析する。対象の設定の変更で CC の算出が変わり、トレンドに段差が出るのを避けるためである
（PMD のルールセットを quality-gate 側に持つのと同じ考え方）。`.js` / `.ts` / `.vue` を対象とし、
テスト（`*.spec.ts` / `*.test.ts`）と型定義（`*.d.ts`）は計測プロファイルの既定で除外する。
比較元コミットも同じ設定で解析し、`scope: base` で送る。ESLint が出す絶対パスは、作業ツリーの場所を
外して `/<frontend のディレクトリ>/src/...` にそろえてから送る（head と base で置き場所が違っても、
同じ関数として比較されるようにするため）。M-07 は backend と frontend を合算して 1 つの値で判定する。

### ベース側の CC 取得

(b) の判定にはベースコミット時点の CC 値が必要となる。取得方法は 2 通り。

1. **推奨** — 収集ランナーが base / head の両方で解析を実行し、2 つの成果物を提出する
   （`artifacts.type: pmd-xml` に `scope: base` / `scope: head` を付与）
2. quality-gate が保持する過去 Run の複雑度データを流用する
   （ベースコミットで M-07 を判定済みの Run が存在する場合のみ。存在しなければ 1 の提出が必須）。
   過去 Run には `warn_from` 以上の関数だけが保存されているため、そこに無い関数は
   ベースで `warn_from` 未満だったとみなす（`warn_from` ≤ `max_complexity` のとき判定は変わらない）。
   base スコープの解析結果が提出されていればそちらを優先する。Run 詳細の `baseSource` に
   `artifact` / `past-run` のどちらを使ったかを出す

いずれも得られない場合、(b) の判定は行わず (a) のみを判定し、
Run 詳細に「ベース比較不可のため新規追加分のみ判定」と明示する。

### しきい値

| 項目 | 値 |
| --- | --- |
| 合格ライン | 0 件 |
| WARN 水準 | CC 11 – 15 の新規関数が存在する場合（`warn_from: 11`） |
| 判定対象外 | ベース時点で CC > 15 かつ本変更で増加していない関数 |

### 出力

違反した関数について、次を Run 詳細に表示する。

- ファイルパス、関数の完全修飾名、行番号
- CC 値、ベース時点の CC 値（あれば）、増加量
- GitHub の該当行への直リンク

### 境界条件

| 条件 | 扱い |
| --- | --- |
| 解析成果物が未提出 | ERROR |
| `baseCommitSha` が解決できない | (a) のみ判定し、Run 詳細に注記 |
| 自動生成コード | `exclusions` により除外（除外されていなければ判定対象） |

## M-08 破壊的変更件数

### M-08 破壊的変更（互換性）

`oasdiff` により、ベースコミットの OpenAPI 定義と対象コミットの OpenAPI 定義を比較し、
後方互換性を壊す変更を検出する。

| 破壊的変更の例 | 扱い |
| --- | --- |
| エンドポイントの削除 | 破壊的 |
| 必須リクエストパラメータの追加 | 破壊的 |
| レスポンスフィールドの削除 / 型変更 | 破壊的 |
| enum 値の削除 | 破壊的 |
| オプショナルなフィールドの追加 | 非破壊的 |

| 項目 | 値 |
| --- | --- |
| 合格ライン | 破壊的変更 0 件 |
| 意図的な破壊的変更 | API バージョニング（`/v1` → `/v2`）で対応する。やむを得ない場合は合格ライン（`breaking_changes`）を変え、理由をコミットに残す |

### 境界条件

| 条件 | 扱い |
| --- | --- |
| `oasdiff-json` 未提出 | ERROR |
| ベースの OpenAPI 定義が存在しない（新規 API） | M-08 は `N/A` / PASS |

### 詳細仕様

上の定義を実装に落とす際に決めた事項。

**M-08 の成果物。** `oasdiff-json` は `oasdiff breaking <base> <head> --format json` の出力
（変更の配列）とする。`[]` と `null` は 0 件として読む。**空のファイルは 0 件とみなさず ERROR にする。**
oasdiff が動かなかったことと、変更が無かったことを取り違えないためである。

oasdiff の `level` を次のように扱う。`level` は数値でも文字列でも受け付け、分類できないものは
破壊的に倒す（fail-closed）。

| level | 意味 | 扱い |
| --- | --- | --- |
| 3 / `error` | 破壊的 | 件数（値）に数え、違反（`HIGH`）にする |
| 2 / `warning` | 破壊的になりうる | WARN の根拠にし、違反（`MEDIUM`）にする |
| 1 / `info` | 非破壊的（`changelog` の出力） | 件数だけ残し、違反にしない |

fingerprint は `sha256(metricId + 変更 ID + メソッド + パス + 説明文)` とする。同じ操作に同じ種類の変更が
複数ある場合（応答のプロパティを 2 つ消した等）、対象の名前は説明文にしか現れないためである。

**新規 API。** 比較元のコミットに OpenAPI 定義が無い場合、収集ランナーは成果物のメタデータに
`{"baseSpecMissing": true}` を付けて送る。すべての `oasdiff-json` がそう申告し、破壊的変更も
報告されていなければ M-08 は `NOT_APPLICABLE`（対象外）とする。境界条件の表の「`N/A` / PASS」を
対象外で表したもので、合否・部分計測のどちらにも影響しない。

**M-08 の判定の優先順位**は、新規 API（対象外）→ 破壊的変更が `breaking_changes` 超（FAIL）→
破壊的になりうる変更が 1 件以上（WARN）→ PASS とする。

## M-09 アクセシビリティ違反

### 定義

WCAG 2.2 Level AA を基準として自動検出された違反のうち、
**重大（critical / serious）** に分類されるものの件数。

### 入力とツール

`@axe-core/playwright` を用い、Playwright の E2E テスト内で対象ページを検査する。
出力は axe results JSON。

### 重大度の定義

axe-core の `impact` を次のとおり分類する。

| axe impact | quality-gate 分類 | 判定 |
| --- | --- | --- |
| `critical` | 重大 | 判定対象（0 件が合格ライン） |
| `serious` | 重大 | 判定対象（0 件が合格ライン） |
| `moderate` | 軽微 | WARN として可視化 |
| `minor` | 軽微 | 可視化のみ |

`critical` のみを「重大」とする解釈もあるが、`serious` にはキーボード操作不能や
コントラスト不足といった**実際に利用を妨げる**違反が含まれるため、両者を判定対象とする。

### 検査対象ページ

合格ライン（`*.gate.yml`）の `accessibility.pages` に列挙したページを対象とする。
最低限、次のカテゴリのページを含めることを推奨する。

- 入口（ログイン、トップ）
- 一覧（テーブル、フィルタ、ページネーションを含む画面）
- 詳細
- フォーム（入力・バリデーションエラー表示状態の双方）
- エラー画面（404 / 500）

**動的な状態も検査対象に含める**こと。モーダルを開いた状態、
バリデーションエラーが表示された状態、ローディング中の状態は
初期表示とは別の違反を含むことが多い。

### しきい値

| 項目 | 値 |
| --- | --- |
| 合格ライン | critical + serious = 0 件 |
| WARN 水準 | moderate が 1 件以上、または前回比で増加 |
| 集計 | ページ × ルール × 要素 で 1 件とカウント |

### 限界の明示

自動検査で検出できる WCAG 違反は全体の一部にとどまる。
「重大 0 件」は WCAG 2.2 AA 適合の**必要条件であって十分条件ではない**。
この旨を Run 詳細画面に常時注記し、過信を防ぐ。

手動チェック（キーボード操作、スクリーンリーダー、フォーカス順序、
実利用者による検証）の結果を取り込む機能は将来検討する（スコープ外）。

### 境界条件

| 条件 | 扱い |
| --- | --- |
| 成果物未提出 | ERROR |
| 検査ページ数が設定より少ない | ERROR（一部ページの検査失敗を成功と誤認しない） |
| 検査ページ数 0 | ERROR |
| ページの読み込み失敗 | 当該ページを ERROR とし、Run 全体も ERROR |

### 詳細仕様

上の定義を実装に落とす際に決めた事項。

**成果物の形。** `axe-json` は `@axe-core/playwright` の `analyze()` の戻り値そのもの
（1 画面分のオブジェクト）か、その配列（複数画面分）とする。`url` と `violations` 配列の
無いものは形式不正として ERROR にする。Playwright のテストレポート（JSON reporter の出力）を
取り違えて送った場合もここで弾く。同じ Run に複数の `axe-json` を送ってもよく、検査した画面は
すべての成果物を合わせて数える。

**検査した画面のパス。** 結果の `url` からパスを取り出し、次のように正規化する。

- クエリとフラグメントは捨てる。同じ画面が表示条件の違いで別の画面に分かれるうえ、
  URL に載ったトークンを違反の詳細として保存しかねないためである
- ハッシュ方式のルーター（`/#/orders/42`）では、`/` で始まるフラグメントを画面のパスとして使う
- ID らしい区切り（数字のみ、UUID、24 桁以上の 16 進、ULID）を `:id` に置き換える。
  置き換えないと、検査のたびに違うデータで描いた同じ画面が別の画面になり、違反が毎回
  「新規」に見える。設定の `pages`（`/runs/:id`）とも照合できない

設定の `pages` との照合は区切りごとに行い、`:` で始まる区切りは任意の 1 区切りに一致する
（`/repositories/:repositoryId/trends` は `/repositories/:id/trends` に一致する）。
`pages` を省略した場合は、1 画面以上を検査していることだけを確かめる。

**読み込みの失敗。** `url` のスキームが `http` / `https` / `file` 以外
（`chrome-error://chromewebdata/` など）の結果は、読み込みに失敗した画面とみなす。
その結果の違反はエラー画面に対するものであり、数えない。ログイン切れで `/login` に
移った場合は失敗とは見分けられないが、本来の画面が検査されていないことが `pages` との
照合で ERROR になる。

**違反の数え方。** axe は 1 つのルールに該当した要素を `nodes` にまとめて返すため、
要素ごとに 1 件とする（ページ × ルール × 要素）。ライト / ダークの両モードで同じ画面を
検査して同じ違反が出た場合は、fingerprint が同じになり 1 件に数える。
impact は要素ごとの値を優先し、無ければルールの値を使う。どちらも無い違反は
**重大（serious）側に倒す**。分類できなかったというだけで判定から外さない（fail-closed）。

| axe impact | 保存する深刻度 |
| --- | --- |
| `critical` | `CRITICAL` |
| `serious` / 不明 | `HIGH` |
| `moderate` | `MEDIUM` |
| `minor` | `LOW` |

ダッシュボードの「重大 N 件・高 N 件」は脆弱性（M-06）の件数であり、M-09 の違反は含めない。

**基準（`standard`）に含まれないルールは判定に使わない。** 違反したルールのタグに
基準のタグ（`wcag22aa` なら `wcag2a` / `wcag2aa` / `wcag21a` / `wcag21aa` / `wcag22aa`）が
1 つも無ければ、WCAG のその基準の違反ではない（`best-practice` や AAA のルール）。
件数は `outOfStandard` として残し、違反一覧にも出すが、合否と WARN には使わない。
`standard` に書けるのは `wcag2a` / `wcag2aa` / `wcag21a` / `wcag21aa` / `wcag22aa` で、
それ以外は設定の検証で拒否する。

**検査ルールの絞り込みを確かめる。** 結果の `toolOptions` から次を読み、
いずれかに当たれば WARN とする。検出漏れがあり得る状態で合格を出さないためである。

- `runOnly` をタグで指定しているが、基準のタグの一部が含まれていない
- `rules` で無効にしたルールがある（`color-contrast` を切って通す、を見逃さない）
- `runOnly` でルールを個別に指定している（どの基準を満たすか判断できない）

`runOnly` の指定が無ければ全ルールが動いており、基準は満たしている。

**判定の優先順位**は、読み込み失敗 → 検査した画面が無い → `pages` の画面が欠けている
（以上 ERROR、値なし）→ 基準内の critical + serious が `max_critical` 超（FAIL）→
検査ルールの絞り込み → 基準内の moderate が 1 件以上 → 重大な違反が前回より増加（以上 WARN）
→ PASS とする。上で決まったものは下を見ない。

axe が判断を保留した要素（`incomplete`、色のコントラストを背景画像のため計算できない等）は
違反に数えず、件数を `needsReview` として残す。手動確認の手がかりにする。

## M-10 テスト成功率 / M-11 スキップされたテスト数

要件定義の後に追加した指標（カテゴリは「機能テスト」）。M-01 / M-02 はテストが**何を通し、何を検証しているか**を
測るが、テストが**通っているか**は測らない。失敗したテストがあってもカバレッジは出るため、
失敗とスキップを別の指標で見る。

### M-10 定義

```
テスト成功率 (%) = 成功したテスト数 / 実行されたテスト数 × 100
```

対象はすべてのテスト（単体テスト・結合テスト。backend の Surefire / Failsafe と frontend の Vitest）。
スキップは実行していないため分母に入れず、再実行で成功したテスト（Surefire の `flakyFailure` / `flakyError`）は
成功に数える。合否は丸めた割合ではなく件数で比べる（`成功 × 100 ≥ 合格ライン × 実行`）。表示する値は切り捨てで丸め、
失敗があるのに `100%` と表示しない。

**テストの数え方。** `<testsuite>` の `tests` / `failures` 属性は使わず、`<testcase>` を 1 件ずつ数え直す。
属性の数え方（スキップを含むか、再実行をどう数えるか）がツールごとに揃わないためである。
1 件の結果は子要素で決め、重い順に採る。

| 子要素 | 結果 | 成功率での扱い | 違反の深刻度 |
| --- | --- | --- | --- |
| `error` | エラー | 実行・不成功 | `HIGH` |
| `failure` | 失敗 | 実行・不成功 | `HIGH` |
| `skipped` | スキップ | 実行に数えない | `INFO` |
| `flakyFailure` / `flakyError` | 再実行で成功 | 実行・成功 | `LOW` |
| なし | 成功 | 実行・成功 | （違反にしない） |

Surefire は再実行しても失敗し続けたテストに `failure` と `rerunFailure` の両方を付けるため、
`rerunFailure` だけでは判断しない。


**コンポーネントごとに判定する**（M-01 と同じ）。単体テストはコンポーネントに閉じており、合算すると
件数の多い側が少ない側の失敗を薄める。
同じコンポーネントのレポートはファイル単位で届くため、件数で合算する。

### M-11 定義

```
スキップされたテスト数 = <skipped/> が付いたテストの件数（コンポーネントごと）
```

スキップ（`@Disabled` / `it.skip` など）は失敗にならないため M-10 では見えない。落ちるテストを黙らせる
手段として使われると、成功率 100% のまま検証が減っていく。そこで**比較対象 Run からの増加**を判定する。
既存のスキップを一括で不合格にしないのは M-07 と同じ考え方による。

### しきい値

合格ライン（`*.gate.yml`）の `metrics.test_results` で設定する。**既定で有効**。

| 項目 | キー | 既定値 |
| --- | --- | --- |
| M-10 の合格ライン | `min_success_rate` | 100%（= 失敗 0 件、エラー 0 件） |
| M-10 の最小実行件数 | `min_test_count` | 1 件以上。0 件は ERROR（0 は指定できない） |
| M-11 の件数の上限 | `max_skipped` | 無し（件数そのものは問わない） |
| M-11 の増加の上限 | `max_skipped_increase` | 0 件（比較対象 Run から 1 件でも増えれば FAIL） |

M-10 の判定の優先順位（上で決まったものは下を見ない）:

1. 実行件数が `min_test_count` 未満 → ERROR
2. 成功率が合格ライン未満 → FAIL
3. 失敗したテストがある（合格ラインを 100% 未満に緩めた場合）、再実行で成功したテストがある → WARN
4. それ以外 → PASS

スキップは M-11 で判定するため、M-10 では WARN にしない（同じスキップで 2 つの指標が黄色くなると、
どちらを直せばよいかが読めない）。

M-11 の判定の優先順位:

1. 件数が `max_skipped` を超えた → FAIL
2. 比較対象 Run の M-11 の値からの増加が `max_skipped_increase` を超えた → FAIL
3. それ以外 → PASS（比較対象が無ければ増加は判定せず、件数だけを記録する）

### 違反

| 指標 | 違反として残すもの | 深刻度 |
| --- | --- | --- |
| M-10 | 失敗（`failed`）・エラー（`errored`）・再実行で成功（`flaky`）したテスト | HIGH / HIGH / LOW |
| M-11 | スキップ（`skipped`）されたテスト | INFO |

fingerprint は `テストクラス名#テスト名`。行番号もファイルパスも持たない。
増えたスキップは違反一覧で「新規」として見分けられる。判定は件数で行う。

### 境界条件

| 条件 | 扱い |
| --- | --- |
| `test-junit-xml` 未提出 | M-10 / M-11 とも ERROR |
| あるコンポーネントの実行件数 0 件 | そのコンポーネントの M-10 は ERROR（M-11 は件数で判定する） |
| 比較対象 Run に同じコンポーネントの M-11 が無い | 増加は判定しない（PASS） |

### 成果物

収集ランナーは backend の `target/surefire-reports/TEST-*.xml` と `target/failsafe-reports/TEST-*.xml`
（計測プロファイルの `TEST_REPORTS` で変えられる）と、Vitest を junit reporter つきで動かした結果を
`test-junit-xml` で送る。

## M-12 シークレット検出件数 / M-13 ライセンス違反件数

要件定義の後に追加した指標（カテゴリは「セキュリティ」）。どちらも Trivy の SARIF から読む。

### 走査した対象の申告

SARIF の成果物に、メタデータ `{"scanners": ["vuln", "secret"]}` のように**走査した対象**を添える
（Trivy の `--scanners` と同じ書き方。`vuln` / `misconfig` → M-06、`secret` → M-12、`license` → M-13）。

- 申告があれば、検出を指標に振り分ける。シークレット（ルールの tags に `secret`、または gitleaks などの
  シークレット専用ツール）は M-12、ライセンス（tags に `license`）は M-13、それ以外は M-06
- 値を与えるのは**申告した対象の指標だけ**。ライセンスだけを走査した SARIF で M-06 を「0 件」として
  合格にしないため。申告していない対象の検出は捨てる
- 申告が無い SARIF は、すべてを M-06 として読む（M-12 / M-13 には値を与えない）。
  シークレットの分離を知らない送り手のシークレットが、判定から黙って消えないようにするため
- 未知の値（`vulnerabilities` など）は形式不正（ERROR）にする。書き間違いで指標が 0 件にならないため

### M-12 定義

```
シークレット検出件数 = 検出されたシークレットの件数（ルール ID とファイルの組み合わせで名寄せ）
```

コミットされた鍵やトークンは、履歴に残った時点で漏えいとみなす。M-07 のように新規だけを数えることはせず、
**検出されたものすべて**を数える。誤検出は、合格ラインの `exclusions` でファイルごと外す。
深刻度はすべて Critical。違反の内容には、ツールが伏せ字にした一致だけを残し、値そのものは持たない。

| 項目 | キー | 既定値 |
| --- | --- | --- |
| 合格ライン | `max_secrets` | 0 件 |

### M-13 定義

```
ライセンス違反件数 = 分類が forbidden のパッケージ数
```

Trivy のライセンスの分類（緩い順に unencumbered / permissive / notice / reciprocal / restricted / forbidden、
分からなければ unknown）で判定する。数える単位は**パッケージ**。

**1 つのパッケージに複数のライセンスが並ぶ場合は、選べる（OR）とみなし、最も緩いものを採る。**
logback（EPL-2.0 または LGPL-2.1）や jakarta.*（EPL-2.0 または GPL-2.0 + Classpath 例外）のような
デュアルライセンスを厳しいほうで数えると、ほとんどの Java のアプリが不合格になる。
このため収集ランナーはライセンスの走査を**深刻度で絞らずに**行う（MIT などの緩いライセンスも見えないと、
緩いほうを選べない）。unknown は、同じパッケージに分類の分かるライセンスがあればそちらを採る。

| 項目 | キー | 既定値 |
| --- | --- | --- |
| 合格ライン | `max_forbidden` | 0 パッケージ |
| restricted の上限 | `max_restricted` | 無し（件数では落とさず WARN）。GPL などを使えない配布形態なら 0 を設定する |
| 分類不明の上限 | `max_unknown` | 無し（件数では落とさず WARN） |

判定の優先順位:

1. forbidden が `max_forbidden` を超えた、または restricted / unknown が上限（設定したときだけ）を超えた → FAIL
2. restricted / unknown のパッケージがある → WARN（利用形態で可否が変わるため、既定では落とさない）
3. それ以外 → PASS

違反として残すのは、forbidden / restricted / unknown になったパッケージの、その分類のライセンスだけ
（走査は全パッケージを報告するため、全件を残すと違反でない行が大量に積まれる）。fingerprint は
`パッケージ|ライセンス`。

### 既定値と境界条件

M-12 / M-13 は 合格ライン（`*.gate.yml`）の `metrics.secrets` / `metrics.licenses` で設定する。**既定では無効**
（M-10 / M-11 と同じ理由）。

| 条件 | 扱い |
| --- | --- |
| `scanners` に `secret`（`license`）を申告した SARIF が無い | M-12（M-13）は ERROR |
| 申告どおりに走査して検出 0 件 | M-12 / M-13 とも PASS |

## 付録 A: 導入手順

対象リポジトリは既にベースラインが整っているため、
段階的なしきい値の引き上げ（ラチェット方式）は採用せず、
**本仕様の絶対値しきい値を当初から適用する**。

| 段階 | 期間の目安 | 内容 |
| --- | --- | --- |
| 1. 計測パイプライン整備 | 1〜2 週間 | 収集ランナーに対象の計測プロファイルを追加し、合格ライン（`collector/targets/*.gate.yml`）を追加して、成果物が quality-gate に届く状態にする（対象リポジトリは変更しない。[収集ランナーで計測する](../operations/collector.md)） |
| 2. 確認運用 | 1〜2 週間 | 絶対値しきい値で判定する。しきい値と実測値の関係、計測の安定性（特に性能指標の変動）を確認する |
| 3. 本番運用 | 以降 | 判定結果を是正とリリース判定の根拠として使う |

段階 2 は「しきい値を緩めるための期間」ではなく、
**計測そのものが信頼できるかを確認するための期間**である。
ここで確認すべきは主に次の 3 点。

- 性能指標の 3 回実行の変動係数が 20% 以内に収まっているか（M-03 境界条件）
- `exclusions` の設定により意図せず広い範囲が計測対象外になっていないか（0.2 節）
- ERROR（成果物の未提出・形式不正）が発生していないか

### 新規リポジトリを追加する場合

対象リポジトリを追加する際は、登録前に 1 度計測してベースラインを確認する。
既定のしきい値から大きく乖離している場合は、そのリポジトリに限り
達成可能な水準からしきい値を設定し、改善計画とともに段階的に引き上げる。

達成不可能なしきい値を掲げると、不合格が常態化して誰も見なくなり、
ゲート全体が機能しなくなるためである。

## 付録 B: 指標間の関係

指標は独立ではなく、相互に補完・検証しあう関係にある。
この関係を理解して運用することで、個々の数値を追うより高い効果が得られる。

- **M-01（カバレッジ）と M-02（ミューテーション）** — カバレッジが高くミューテーションスコアが
  低い場合、「コードを通しているがアサーションしていない」テストの存在を示す。
  カバレッジ単独では検出できない。なお M-02 は backend のみであるため、
  frontend についてはこの相互検証が働かない点に留意する
- **M-07（複雑度）と M-01（カバレッジ）** — 複雑度の高い関数はカバレッジを上げにくい。
  M-07 の違反が続く場合、M-01 の改善も停滞する
- **M-10（テスト成功率）と M-01（カバレッジ）** — 失敗したテストがあってもカバレッジは出る。
  カバレッジの値は、テストが通っている（M-10 が合格）ことを前提に読む
- **M-11（スキップ）と M-10（テスト成功率）** — 落ちるテストをスキップすると M-10 は 100% に戻る。
  M-10 の改善と M-11 の増加が同じ Run で起きていたら、直したのではなく黙らせた可能性がある
- **M-10（テスト成功率）と M-08（互換性）** — テストが 100% 成功していても、
  API が破壊的に変更されていれば既存のクライアントは壊れる。テストは変更後の API に合わせて書き直されるため、
  互換性は M-08 で見る
- **M-03（性能）と M-06（脆弱性）** — 依存ライブラリの更新は脆弱性を解消する一方で
  性能特性を変えることがある。両指標を同一 Run で見ることで副作用を検知できる
