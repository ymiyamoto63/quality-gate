# quality-gate 設計判断と未決事項

本書は、quality-gate の構成を決めている主要な設計判断（DD-xx）とその理由、
および運用しながら決める未決事項（Q-xx）をまとめる。
各判断の具体的な仕様は [要件定義書](01-requirements.md) と各設計書に記す。

---

## 1. 設計判断

### 基本方針

| # | 項目 | 判断 | 理由 |
| --- | --- | --- | --- |
| DD-1 | 利用形態 | **社内専用・単一テナント**。インターネットには公開しない | 対象は社内のリポジトリで、利用者も社内の少人数に限られる。マルチテナントと課金は要件外 |
| DD-2 | 対象リポジトリの構成 | **モノレポ**（`backend/` + `frontend/`）を 1 リポジトリ単位で扱う。複数のリポジトリを束ねる上位概念（「プロダクト」など）は持たない | backend と frontend の結果が 1 つの Run にまとまり、両者にまたがる指標（M-09 API の互換性など）を扱いやすい |
| DD-3 | 判定結果の扱い | **可視化に徹し、PR のマージをブロックしない** | 合格ラインの妥当性が実績で確かめられていない段階でブロックすると、しきい値の一時緩和やチェックの回避が常態化し、ゲートが形骸化する。判定と合否は本番同等に動かし、合否は「情報」として示す |
| DD-4 | 技術スタック | **Spring Boot 4（Java 25 LTS・Maven）+ Vue 3**。SPA は Spring Boot に同梱して同一オリジンで配信し、API の型は openapi-typescript + openapi-fetch で生成する。成果物はローカルファイルシステムに保存する | 同一オリジンにすると CORS が不要で、認証を HttpOnly のセッション Cookie で完結できる。この規模ではオブジェクトストレージは過剰。詳細は [04 技術スタック](04-tech-stack.md) |
| DD-5 | quality-gate 自身の品質 | **quality-gate 自身は計測対象にせず、Pull Request の CI（`ci.yml`）で確かめる**。結合テスト・生成物の同期検証・アクセシビリティ検査（axe-core の critical / serious 0 件）・脆弱性スキャン（修正版のある重大・高 0 件）に失敗したらマージしない | 少人数で使う社内ツールで、性能指標（到達率 50 req/s の負荷試験）は実際の使われ方とかけ離れている。セルフホストランナーは収集ランナー専用で（DD-11）、自身の計測で占有すると性能計測の条件が崩れる。自身の指標を画面で見たくなったら、収集ランナーの対象に登録する |

### 計測

| # | 項目 | 判断 | 理由 |
| --- | --- | --- | --- |
| DD-6 | 計測と判定の分担 | **quality-gate リポジトリの「収集ランナー」が対象リポジトリを取得して計測し、Ingest API に送る。バックエンドは取り込みと判定だけを行い、テストやスキャンを実行しない**。対象リポジトリには設定ファイル・ワークフロー・計測用の依存関係を置かない。Ingest API の送り手は収集ランナーだけ | バックエンドに Docker・ビルドツールチェーン・対象の認証情報を持ち込まずに済む。計測方法と合格ラインを quality-gate 側で一元管理でき、対象のチームに計測用の保守を求めない。代わりに、対象のビルド構成が変わったときの追従は quality-gate の運用者が担う（[01](01-requirements.md) R-15）。構成は [収集ランナー方式](../architecture/collector-runner.md) |
| DD-7 | 計測のきっかけ | **収集ランナーの手動実行**（対象とブランチ・コミット・タグ・PR を指定する） | 計測したい時点（リリース前・PR の確認など）は人が決める。判定から外したいもの（生成コードなど）や一時的に許容するものは、合格ライン（DD-13）の `exclusions`・指標の `enabled`・しきい値で扱い、理由はコミットに残す |
| DD-8 | PR の計測とスキップの申告 | **PR の計測では PIT と負荷試験を実行せず、スキップを申告する**。申告できる指標は合格ラインの `execution.skippable_metrics` に限り、それ以外の申告と申告のない未提出は `ERROR` とする。スキップを含む Run は部分計測として表示する | PIT と負荷試験は時間がかかり、PR の確認を待たせる。一方、自由にスキップできると fail-closed（測れていないものを合格にしない）が骨抜きになるため、申告制と許容リストで両立させる（[01](01-requirements.md) 6.4） |
| DD-9 | コンポーネント | **計測プロファイル（`BACKEND_DIR` / `FRONTEND_DIR`）だけで決める**。判定と表示には成果物に付いたコンポーネント名を使う | 計測を分けているのは計測プロファイルだけで、定義を他に持つとずれる余地が生まれる |
| DD-10 | GitHub 連携 | **バックエンドは GitHub API を呼ばない**（ログインの OAuth だけ）。比較元・タグ・ファイルの移動は、収集ランナーが clone した履歴から求めて送る（`git merge-base` / `git tag --points-at` / `git diff -M`・`git log -M`） | 収集ランナーは対象の全履歴を clone しているため、同じ情報を git で求められる。バックエンドに GitHub App の秘密鍵を置かずに済み、GitHub の障害で判定やリリース判定が止まらない。代わりに、タグを付ける前に計測したコミットはタグで引けない（タグを付けて計測し直すか、コミット SHA で指定する）。ファイルの移動は、比較元からの差分と first-parent 1,000 コミット分までを追う |
| DD-11 | 性能計測の条件 | **到達率 50 req/s を負荷条件として固定し、その下で p95 ≤ 500ms・エラー率 ≤ 0.1% を判定する。計測は他のジョブと同居しない専有のセルフホストランナーで行い、絶対値のしきい値で判定する** | スループットを結果として測ると、合否が負荷のかけ方で変わる。共有の実行環境ではノイズで値が揺れ、絶対値で判定できない。50 req/s は初期値で、導入初回の計測で妥当性を確かめる |
| DD-12 | ミューテーションテストの対象 | **PIT を使い、backend だけを対象にする**。frontend は M-01 ブランチカバレッジで担保する | PIT は JVM 専用。業務ロジックはバックエンドに寄っている。frontend の M-02 は測りようがないため `NOT_APPLICABLE` とし、部分計測の理由にしない |

### 判定

| # | 項目 | 判断 | 理由 |
| --- | --- | --- | --- |
| DD-13 | 合格ラインの置き場所 | **quality-gate リポジトリの `collector/targets/<owner>__<name>.gate.yml` だけ**。収集ランナーが Run ごとに `quality-gate-config` として送り、quality-gate はその内容で判定する。画面（S-06）は表示だけ。`*.gate.yml` が無ければ収集ランナーは送信の前に止まる | 置き場所を 1 か所にすると、判定に使った合格ラインと管理している合格ラインがずれない。変更はプルリクエストでレビューし、理由と実施者は Git の履歴に残る |
| DD-14 | しきい値の適用 | **絶対値のしきい値を当初から適用する**（段階的に引き上げるラチェット方式は採らない） | 対象リポジトリはベースラインが整っており、マージもブロックしない（DD-3）。導入初期は計測そのものが信頼できるかを確かめる期間と位置づける（[02](02-metrics-spec.md) 付録 A） |
| DD-15 | 判定の実行方式 | **取り込みの確定（`finalize`）と再評価の中で、その場で判定して結果を返す**。判定に失敗した Run は「処理失敗」（`FAILED`）として残し、管理者が再評価で直す。保持期間の削除などの日次バッチは `@Scheduled` で動かし、失敗しても翌日に再実行される | 判定は保存済みの成果物を読んで DB に書くだけで、数秒で終わる。非同期の仕組みを挟まないため、収集ランナーは送信の応答で結果を知ることができ、単一プロセス構成のまま運用できる |
| DD-16 | リリース判定 | **タグかコミットを指定し、そのコミットで判定済みの Run から結論（リリース可 / 注意あり / 不可 / 判定できない）を出す**。同じコミットの最新の完全計測を使い、近くのコミットでは代用しない。部分計測で不合格が無ければ「判定できない」。判定し直さず、Run の判定時の結果をそのまま使う。指標ごとに説明と基準の根拠を示し、根拠の強さを「外部基準 / 業界の目安 / チーム判断」で明示する。CSV は 1 行 1 指標で、出力を監査ログに残す。PDF はブラウザの印刷 | 近くのコミットの結果は別のコードの結果になる。測っていない指標を合格とみなさない。見るたびに結論が変わると証跡にならない。経営陣や開発初心者にも読めるよう、チームで決めた値を外部の基準と同じ口調で書かない。前回リリースとの比較・承認の仕組み・総合点は持たない |
| DD-17 | リリース判定のための計測 | **タグを指定して計測でき、比較元は前のタグにする。PIT と負荷試験は PR 以外のすべての計測で実行する**。quality-gate は比較元コミットで判定済みの Run を比較対象 Run に優先して使う | リリースブランチやタグの計測を完全計測にし、リリース判定が「判定できない」にならないようにする。新規の違反・破壊的変更・スキップの増加を、前回のリリースからの変更全体で数える。手動の計測は順不同で、同じブランチで直前に計測した Run がリリースより新しいことがあるため、比較元のコミットを優先する |

### 認証と認可

| # | 項目 | 判断 | 理由 |
| --- | --- | --- | --- |
| DD-18 | ログイン | **GitHub OAuth**（個人アカウント / GitHub Free）。単一の GitHub App の user-to-server 認可フローを使い、ログインの可否は quality-gate 内の**許可リスト**で制御する | Organization を持たないため、組織のメンバーシップをログインの条件にできない。GitHub アカウントを持つ誰でも OAuth 自体は完了できるため、許可リストが実質的な入口の制御になる |
| DD-19 | ロール | **Admin / Viewer の 2 ロール**。利用者が増えたら、Developer / Maintainer を加えた 4 ロールへ拡張する | 対象 1 リポジトリ・利用者数名の規模では 2 ロールで足りる。ロールの追加が権限定義の追加だけで済むように実装する |
| DD-20 | Ingest Token | **収集ランナー用の 1 つを、バックエンドの環境変数 `QG_INGEST_TOKEN` と収集ランナーの Actions Secret `QG_INGEST_TOKEN` に置く**。交換は、新旧をカンマ区切りで並べて設定し、収集ランナーを切り替えてから古い値を消す | 送り手は収集ランナーだけで、トークンは同じ Actions Secrets に置かれる。リポジトリごとに分けても守りは強くならない。無効化は環境変数の値を変えて行う |

## 2. 未決事項

優先度「高」の未決事項は無い。

### Q-1. ミューテーションテストの実行時間をどこまで許容するか【優先度: 中】

PIT は相応の時間を要する（全量では単体テストの数十倍）。収集ランナーでは対象の CI の実行時間に影響しないため、
論点は「セルフホストランナーをどれだけ占有してよいか」になる。

現在は、PR 以外の計測（ブランチ・コミット・タグ）で全量を実行し（DD-17。like-chatgpt で約 1 分）、
PR の計測では M-02 のスキップを申告する（DD-8）。ランナーの占有が問題になったら見直す。

### Q-2. 不合格時の是正プロセスをどう定めるか【優先度: 中】

マージをブロックしないため（DD-3）、**不合格が放置されない運用ルール**が別に要る。
アプリの機能ではなく運用の取り決めだが、これを欠くと [リスク R-7](01-requirements.md#13-リスクと対策)
のとおり「可視化しただけで何も改善しない」状態になる。

決めること:

- 不合格を検知してから是正までの目標期間（例: Critical 脆弱性は 3 営業日以内）
- 不合格の指標をレビューする場（既存の定例に組み込めるか）
- マージブロック（スコープ外）へ移る判断基準と時期の目安

### Q-3. 成果物の保持期間とストレージ【優先度: 低】

保持期間の既定は「Run メタデータ・指標値 2 年 / 元成果物 90 日 / 監査ログ 2 年」で、管理画面（S-09）から変更できる。

- 監査・リリース判定の観点で、より長期の保持が要るか
- 保存先はローカルファイルシステム（バインドマウント。[04](04-tech-stack.md) 5.2）。必要な空き容量（初期 10GB 程度）を確保できるか

### Q-4. デプロイ先と運用体制【優先度: 低】

- オンプレミスか、プライベートクラウド（AWS / Azure / GCP）か
- 運用担当（監視・バックアップ・アップデート）はどのチームか

対象 1 リポジトリ・利用者数名の規模であれば、**Docker Compose による単一ホスト構成**
（PostgreSQL 1 コンテナ + アプリ 1 コンテナ）で足りる。

### Q-5. マージブロックへ進む場合の GitHub プラン【優先度: 低】

マージをブロックしないため（DD-3）現時点で対応は不要だが、将来必須チェック化する場合、
**GitHub Free ではプライベートリポジトリの保護ブランチを使えない**（GitHub Pro 以上が必要）。
