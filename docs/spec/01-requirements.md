## 1. 背景と目的

### 1.1 背景

ソフトウェアの品質は「テストを書いている」「脆弱性スキャンを回している」といった
*活動の有無* では語れるが、*水準* を数値で語れていないことが多い。
個々のツール（JaCoCo、Vitest、Trivy、k6、axe-core など）は導入済みでも、
結果は CI のログやジョブごとの成果物に散在し、次のような状態に陥りやすい。

- 品質の現在地がチーム内で共有されていない（各自が別のツールの別の画面を見ている）
- 「良くなっているのか悪くなっているのか」の推移が追えない
- 合格ラインが暗黙知で、人によって判断が違う
- カバレッジは見ているが、ミューテーションスコア・複雑度・アクセシビリティは誰も見ていない

### 1.2 目的

quality-gate は、指定したリポジトリについて以下を実現する。

1. **定量化** — 6 カテゴリの品質指標を、定義の揺れなく同一の基準で数値化する
2. **判定** — 明示された合格ラインに対して 合格 / 不合格 を機械的に判定する
3. **可視化** — 現在地と推移をダッシュボードで一望できるようにする
4. **リリース判断** — リリースしてよいかを、指標ごとの合否と根拠を添えて 1 画面で示し、証跡を残す

### 1.3 ゴール（成功の定義）

| # | ゴール | 測り方 |
| --- | --- | --- |
| G-1 | 対象リポジトリの 6 カテゴリ全指標が、計測を実行するたびに数値として記録される | 直近 30 日の計測成功率 95% 以上 |
| G-2 | 誰でも 1 画面で「今の合否」と「30 日の推移」が分かる | ダッシュボード到達から把握まで 3 クリック以内 |
| G-3 | 合格ラインの定義が版として管理され、変更履歴が追える | `collector/targets/*.gate.yml` を Git で管理し、内容が変わるたびに版を作る |
| G-4 | リリース判定会議で、タグを指定するだけで結論と根拠を示せる | タグの計測から判定の表示・CSV の出力まで追加の作業なし |

### 1.4 非ゴール（このアプリがやらないこと）

- **バックエンドでのテストやスキャンの実行** — 実行は収集ランナーが担い、バックエンドは取り込みと判定だけを行う（3 章）
- **マージのブロック** — 可視化に徹し、PR のマージ制御は行わない
- **品質問題の自動修正** — 検出と提示までを担当し、修正は開発者が行う
- **汎用 BI ツール化** — 品質指標に用途を限定し、任意のメトリクス投入基盤にはしない

## 2. スコープ

### 2.1 計測対象リポジトリの前提

| 項目 | 前提 |
| --- | --- |
| バックエンド | Java / Spring Boot（Maven） |
| フロントエンド | Vue 3 SPA（TypeScript、npm + Vitest） |
| 単体・結合テスト | JUnit 5、Testcontainers、Vitest |
| リポジトリホスティング | GitHub（収集ランナーは quality-gate リポジトリの GitHub Actions で動く） |
| リポジトリ構成 | **モノレポ**（`backend/`、`frontend/`）。対象は **1 リポジトリ** |
| GitHub アカウント種別 | 個人アカウント（GitHub Free）。Organization は使用しない |
| リポジトリの公開設定 | プライベート |

対象が単一のモノレポであるため、backend と frontend の計測結果は 1 つの Run に
まとまる。API の互換性（M-08）のように両者にまたがる指標を扱ううえで都合がよく、
複数リポジトリの Run を束ねる上位概念（「プロダクト」等）は不要である。

計測ツール（カバレッジ、ミューテーションテスト、負荷試験、脆弱性スキャン、複雑度解析、
API の差分検出、アクセシビリティ検査）は、収集ランナーが版を固定して持ち込む（3 章）。
対象リポジトリにツールや設定を追加する必要はない。**テストそのものは対象リポジトリのもの**を実行する。
収集ランナーはセルフホストランナーで動くため、GitHub Actions の無料枠（プライベートリポジトリで月 2,000 分）を消費しない。

### 2.2 スコープ内

- 計測（収集ランナー）と、計測結果の受け取り・保管・正規化
- 合格ライン（しきい値）の定義・版管理
- 合否判定と、判定根拠（個別違反）の保持
- ダッシュボード・トレンド・詳細ドリルダウン・リリース判定の提供
- 認証・認可、監査ログ

### 2.3 スコープ外（将来検討）

- PR の必須チェック化によるマージブロック
- 複数組織を収容するマルチテナント / 課金
- GitHub 以外のホスティング（GitLab、Bitbucket）対応
- 手動アクセシビリティ検査結果の取り込み

> 将来拡張としてスコープ外に置いた項目も、データモデルと API は拡張可能な形で設計する（8 章）。

## 3. 全体方針

### 3.1 計測の実行方式：収集ランナーと取り込み型のバックエンド

計測は **quality-gate 側の「収集ランナー」** が行い、バックエンドは送られた成果物を取り込んで判定する（[03](03-design-decisions.md) DD-6）。
対象リポジトリには設定ファイル・ワークフロー・計測用の依存関係を置かない。

```
 対象リポジトリ (private) ──clone（GitHub App の読み取り権限）──┐
                                                                  ▼
 quality-gate リポジトリの GitHub Actions（専有のセルフホストランナー）
   fetch（取得。比較元・タグ・ファイルの移動を求める）
   → measure（計測。コンテナの中で動かし、認証情報を渡さない）
   → submit（Ingest API へ送信）
                                                                  │ HTTPS / Ingest Token
                                                                  ▼
 quality-gate バックエンド（取り込み → 正規化 → 判定 → 可視化）
```

| 項目 | 内容 |
| --- | --- |
| きっかけ | 手動実行（対象とブランチ・コミット・タグ・PR を指定する） |
| 計測ツール | 収集ランナーが版を固定する（JaCoCo / PIT / PMD / ESLint / k6 / Trivy / oasdiff / axe-core）。テストは対象のものを実行する |
| 合格ライン | quality-gate リポジトリの `collector/targets/<owner>__<name>.gate.yml` を Run ごとに送り、その内容で判定する |
| 対象ごとの情報 | 計測プロファイル（`collector/targets/<owner>__<name>.env`。ビルドの場所、Java の版、テスト結果の場所など） |

この方式を採る理由:

- バックエンドに Docker・ビルドツールチェーン・対象リポジトリの認証情報を持ち込まずに済む。
  それらは収集ランナーのマシンにだけ必要になり、収集ランナーは性能計測と同じ専有のセルフホストランナーで直列に動かす（DD-11）
- 計測方法と合格ラインを quality-gate 側で一元管理でき、対象リポジトリのチームに計測用の保守を求めない

代償として次の制約を受け入れる。これらは要件として明示的に扱う。

| 制約 | 対処 |
| --- | --- |
| 計測条件（マシンスペック等）が変わると値が比べられない | 性能の成果物には計測メタデータの提出を必須化し、計測環境が変わった Run は系列を分ける（FR-03-3 / FR-08-2） |
| 成果物が届かないことがある | 申告のない未提出は「不合格（fail-closed）」として扱う。意図的なスキップは申告制とし、ERROR と区別する（6.4） |
| 提出値の真正性を完全には保証できない | 送り手を収集ランナーに絞り、Ingest Token を持つのは収集ランナーだけにする |
| 対象のビルド構成が変わると計測が追従できない | 未提出は ERROR として表に出る。計測プロファイルを更新して追従する（R-13） |

収集ランナーの構成は [収集ランナー方式](../architecture/collector-runner.md) を参照。

### 3.2 運用方針：可視化に徹する

**PR のマージをブロックしない**（DD-3）。合格ラインの妥当性が実績で検証されていない段階でブロックを始めると、
しきい値の一時緩和やチェックのスキップが常態化し、ゲート自体が形骸化するためである。
判定ロジックと合否そのものは本番同等に動かし、合否は「情報」として提示する。
必須チェック化によるマージブロックはスコープ外（2.3）とし、必要になった時点で検討する。

## 4. 利用者とユースケース

### 4.1 ロールと権限

対象が 1 リポジトリ・利用者が数名の規模であるため、ロールを 2 種に絞る。

| ロール | 想定者 | 権限 |
| --- | --- | --- |
| Viewer | 参照のみの関係者（PO、QA など） | ダッシュボード・Run 詳細・トレンド・リリース判定の閲覧と CSV の出力 |
| Admin | 開発者・基盤管理者 | 全操作（リポジトリ登録、Run の再評価、ユーザー管理、監査ログ閲覧） |

#### 将来の拡張（利用者増加時）

利用者が増え、判断を一人で完結させるべきでなくなった時点で、
次の 4 ロール構成へ拡張する。ロールの追加が画面と権限定義の追加のみで済むように実装する。

| ロール | 権限 |
| --- | --- |
| Viewer | 閲覧のみ |
| Developer | Viewer + Run の再評価 |
| Maintainer | Developer + リポジトリ登録 |
| Admin | Maintainer + ユーザー/ロール管理、監査ログ閲覧 |

認証に GitHub（個人アカウント）を用いるため、**Organization のメンバーシップや Team を
ロールのマッピング元にできない**。そのため、ロールは quality-gate 内で個別に付与する（FR-10-6）。

### 4.2 主要ユースケース

| UC | 利用者 | シナリオ |
| --- | --- | --- |
| UC-01 | Admin | リポジトリを登録し、収集ランナーの計測プロファイルと合格ラインを追加する |
| UC-02 | Admin | 収集ランナーでブランチ・コミット・タグを指定して計測を実行すると、判定結果が生成される |
| UC-03 | Admin | 自分の PR を計測し、Run 詳細で不合格の原因（どの関数、どの CVE、どのページ）を特定する |
| UC-04 | 全員 | 朝の定例でダッシュボードを開き、全リポジトリの合否と 30 日推移を確認する |
| UC-05 | Admin | 合格ラインを引き上げる（例: カバレッジ 75% → 80%）。`*.gate.yml` をプルリクエストで変更し、マージ後の計測から反映される |
| UC-06 | 全員 | リリース判定会議のために、タグかコミットを指定して、その時点の全指標の合否と結論（リリースしてよいか）を 1 画面で確認し、CSV を証跡として残す |

## 5. 機能要件

凡例: **必須** = 実装必須 / **推奨** = 可能なら実装する

### 5.1 リポジトリ・設定管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-01-1 | GitHub リポジトリを識別子（`owner/repo`）で登録・一覧・無効化できる。登録していないリポジトリ、無効化したリポジトリの計測は受け付けない | 必須 |
| FR-01-2 | 「バックエンド」「フロントエンド」等のコンポーネント単位で指標を扱える。コンポーネントは計測プロファイル（`BACKEND_DIR` / `FRONTEND_DIR`）で決まり、成果物に付いた名前で表示する | 必須 |
| FR-01-3 | 監視対象ブランチ（既定: `main`）を設定できる | 必須 |
| FR-02-1 | 合格ライン等の設定をファイルから取り込む（Configuration as Code。quality-gate リポジトリの `collector/targets/<owner>__<name>.gate.yml`） | 必須 |
| FR-02-2 | 設定ファイルをスキーマ検証し、不正な場合は判定せず、行番号とキー名つきで理由を提示する。未知のキーも不正とする | 必須 |
| FR-02-3 | 設定は版として保存され、各 Run は「どの版の設定で判定されたか」を保持する（判定の再現性） | 必須 |

### 5.2 計測と取り込み

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-03-1 | Ingest API で Run を開始し、複数の成果物ファイルを添付し、確定（finalize）できる。確定するとその場で判定し、結果を返す | 必須 |
| FR-03-2 | Run には コミット SHA、ブランチ、PR 番号、実行者、CI 実行 URL、計測日時を付与する。比較元のコミットと、計測したコミットを指すタグも付与できる | 必須 |
| FR-03-3 | 性能計測の成果物には 計測環境（環境名、ランナー、CPU/メモリ、データ量）を必須メタデータとして付与する | 必須 |
| FR-03-4 | 同一コミット SHA に対する再送信は、既存 Run を上書きせず新しい試行（attempt）として記録する | 必須 |
| FR-03-5 | 取り込み失敗（形式不正、サイズ超過、トークン不正）は理由を構造化して返し、収集ランナーのログで原因が分かる | 必須 |
| FR-03-6 | 1 ファイルあたり 50MB、1 Run あたり 200MB を上限とし、超過時は明示的にエラーとする | 必須 |
| FR-03-7 | Run 作成時に、実行しなかった指標を `skippedMetrics`（指標 ID と理由）として申告できる | 必須 |
| FR-03-8 | 収集ランナーを提供する。対象リポジトリを変更せずに、指定したブランチ・コミット・タグ・PR を取得・計測して Ingest API に送る。PIT と負荷試験は PR 以外の計測で実行する | 必須 |

### 5.3 正規化と判定

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-04-1 | ツール固有フォーマットを内部の正規化モデルへ変換するアダプタ層を持ち、アダプタは指標と疎結合に追加できる | 必須 |
| FR-04-2 | 対応フォーマットは [02-metrics-spec.md](02-metrics-spec.md) に定義したものとし、SARIF 2.1.0 を静的解析系の第一形式とする | 必須 |
| FR-04-3 | 複数ツールが同一の問題を報告した場合、指標ごとに定めたキーで重複排除する | 必須 |
| FR-05-1 | 指標ごとに PASS / WARN / FAIL / SKIP / ERROR / NOT_APPLICABLE を判定する（6.2） | 必須 |
| FR-05-2 | Run 全体の判定を、指標判定の集約ルール（6.3）に従って決定する | 必須 |
| FR-05-3 | 判定結果には、そのしきい値・実測値・差分（前回比）・判定根拠となる個別違反へのリンクを含む | 必須 |
| FR-05-4 | 新規の関数・破壊的変更・スキップの増加のように比較元を要する指標のため、比較元のコミット SHA（収集ランナーが求めて送る）を Run に記録する | 必須 |
| FR-05-5 | 管理者が Run を再評価でき、成果物を再送信せずに、保存済みの成果物とその Run とともに送られた設定で判定し直せる | 必須 |
| FR-05-6 | 申告されたスキップは `SKIP` とし、`execution.skippable_metrics` に含まれない指標のスキップ申告は `ERROR` とする | 必須 |
| FR-05-7 | `SKIP` を含む Run を**部分計測**として記録し、完全計測と区別する（6.3.1） | 必須 |

### 5.4 可視化とリリース判定

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-06-1 | ダッシュボードで全リポジトリの最新判定（合否、最終計測日時）を一覧表示する。カテゴリ別の状態は Run 詳細（FR-07-1）で見る | 必須 |
| FR-06-2 | 最終計測日時を表示する | 必須 |
| FR-06-3 | 最後に**完全計測**が行われた Run を常時表示する | 必須 |
| FR-06-4 | 部分計測の Run は、未計測の指標名と申告された理由を Run 詳細に併記する | 必須 |
| FR-07-1 | Run 詳細で、6 カテゴリ × 各指標の実測値・しきい値・判定を表形式で表示する | 必須 |
| FR-07-2 | 各指標から個別違反（脆弱性、複雑度超過関数、失敗したテスト、a11y 違反）の一覧へドリルダウンできる | 必須 |
| FR-07-3 | 個別違反から、対象リポジトリの該当ファイル・行への GitHub リンクを開ける | 必須 |
| FR-07-4 | 比較対象 Run との比較で「新規に発生した違反」「解消された違反」を区別して表示する。移動しただけのファイルの違反は新規にしない | 必須 |
| FR-07-5 | 取り込んだ元成果物をダウンロードできる（保持期間内） | 推奨 |
| FR-08-1 | 指標ごとの時系列トレンドグラフ（既定 30 日、最大 2 年）を表示する | 必須 |
| FR-08-2 | 性能指標のトレンドは、計測環境が異なる Run を別系列として描画する | 必須 |
| FR-08-3 | トレンド上にしきい値のラインを重畳表示する | 必須 |
| FR-08-4 | `SKIP` の指標はトレンド上で**欠測**として扱い、0 として描画しない | 必須 |
| FR-08-5 | タグかコミット SHA を指定して、そのコミットで判定済みの Run から、リリースの可否（リリース可 / 注意あり / 不可 / 判定できない）と全指標の合否を 1 画面（S-09）に表示する。使うのは最新の完全計測。未計測、または部分計測で不合格が無ければ「判定できない」とする。近くのコミットの Run では代用しない。タグは、そのタグを付けて計測した Run からコミットを探す | 必須 |
| FR-08-6 | リリース判定では、指標ごとに「何を見るか」「基準の根拠」「基準を満たさないと何が起きるか」を、開発に詳しくない人にも分かる言葉で示す。根拠には種類（外部基準 / 業界の目安 / チーム判断）を付ける | 必須 |
| FR-08-7 | リリース判定を CSV（1 行 1 指標。判定の前提・出力日時・出力者を各行に含む）で出力できる。印刷して PDF にもできる。出力は監査ログに残す | 必須 |
| FR-08-8 | リリース判定には比較元のコミット（新規の違反・破壊的変更・スキップの増加を数える起点）を示す。タグで計測したときの比較元は前のタグとする | 必須 |

### 5.5 定期処理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-09-1 | 保持期間を超えた成果物・Run・監査ログを毎日自動削除する。確定されないまま 24 時間たった Run は終端（ABANDONED）にする | 必須 |

### 5.6 共通機能

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-10-1 | GitHub アカウントによる OAuth ログインで認証する（GitHub App の user-to-server 認可フローを利用） | 必須 |

## 6. 品質指標と判定仕様（概要）

各指標の厳密な定義・入力フォーマット・計算式・境界条件は
**[02-metrics-spec.md](02-metrics-spec.md)** に定義する。本章は概要のみ示す。

### 6.1 指標一覧

| ID | カテゴリ | 指標 | 合格ライン | 主な入力 |
| --- | --- | --- | --- | --- |
| M-01 | 機能テスト | ブランチカバレッジ | 75% 以上（backend / frontend 各々） | JaCoCo XML、Vitest lcov |
| M-02 | 機能テスト | ミューテーションスコア | 60% 以上（**backend のみ**） | PIT XML |
| M-03 | 性能テスト | 応答時間 p95 | 500ms 以内 | k6 summary JSON |
| M-04 | 性能テスト | スループット | 到達率 50 req/s を**負荷条件として固定**（[M-03](02-metrics-spec.md) 参照） | k6 summary JSON |
| M-05 | 性能テスト | エラー率（副指標） | 0.1% 以下 | k6 summary JSON |
| M-06 | セキュリティ | 重大・高 脆弱性件数 | 0 件 | SARIF（Trivy） |
| M-07 | コード構造 | 循環的複雑度 15 超の新規関数数 | 0 件 | PMD XML / ESLint JSON |
| M-08 | 契約・互換性 | OpenAPI 破壊的変更件数 | 0 件 | oasdiff JSON |
| M-09 | 使いやすさ | アクセシビリティ重大違反件数 | 0 件（impact: critical / serious） | axe-core JSON |

| M-13 | セキュリティ | ライセンス違反件数（既定は無効） | forbidden 0 件（restricted・分類不明は WARN） | SARIF（Trivy のライセンスの走査） |

### 6.2 指標単位の判定ステータス

| ステータス | 意味 |
| --- | --- |
| PASS | 実測値が合格ラインを満たす |
| WARN | 合格ラインは満たすが、注意水準（指標ごとに定義）に該当 |
| FAIL | 実測値が合格ラインを満たさない |
| SKIP | 計測していない。次のいずれか。(a) 設定で `enabled: false` としている (b) 収集ランナーが**スキップを申告**した（6.4） |
| ERROR | 提出されるはずの成果物が未提出、または形式不正で値を確定できない |
| NOT_APPLICABLE | ツールの制約により、そのコンポーネントでは**測りようがない**（対象外）。M-02 の frontend（PIT は JVM 専用）など |

`SKIP` と `ERROR` の区別は本システムの根幹にあたる。
**「意図して測らなかった」と「測ったつもりが届いていない」は別物**であり、
後者を見逃すと計測の破綻に気づけない。区別の方法は 6.4 に定める。

### 6.3 Run 全体の集約ルール

```
FAIL が 1 つ以上          → Run = FAIL
ERROR が 1 つ以上          → Run = FAIL   （fail-closed）
上記なし かつ WARN が 1 つ以上 → Run = PASS_WITH_WARNINGS
上記いずれもなし            → Run = PASS
SKIP / NOT_APPLICABLE は集約に影響しない（ただし件数を UI に明示）
```

`ERROR → FAIL` は **fail-closed**（計測できていないものを合格扱いしない）とする。
判定から外したい指標は、設定で `enabled: false` にする。

### 6.3.1 完全計測と部分計測

`SKIP` を 1 つ以上含む Run は **部分計測（PARTIAL）** として記録し、
全指標を判定できた Run（**完全計測**）と区別する。
`NOT_APPLICABLE` は部分計測の理由にしない。測りようのないものを積み残しに数えると、
どの Run も完全計測にならず、部分計測の警告が意味を失うためである。

部分計測の Run が PASS でも、それは「測った範囲では合格」を意味するに過ぎない。
そのため次を必須とする。

- Run 詳細に「部分計測（未計測 N 件）」を明示し、未計測の指標名と理由を併記する
- ダッシュボードには最新 Run とは別に「**最後の完全計測**」を常に表示する
- トレンドグラフ上、スキップした指標の点は 0 ではなく**欠測（線を繋がない）**として描画する
- リリース判定は部分計測で不合格が無ければ「判定できない」とする（FR-08-5）

### 6.4 スキップの申告と、その濫用を防ぐ仕組み

収集ランナーは PR の計測で PIT と負荷試験を実行しない。quality-gate はそれを ERROR と区別できなければならない。
一方で、自由にスキップを申告できると fail-closed の原則が骨抜きになる。両立のため次の 4 点を定める。

1. **スキップは明示的に申告する** — Run 作成時に、実行しなかった指標を `skippedMetrics` として申告する（7.1）。
   申告のない指標の成果物が届かなかった場合は `ERROR` とする
2. **スキップを許容する指標は設定で限定する** — 合格ラインの `execution.skippable_metrics` に列挙した指標だけがスキップ可能。
   列挙されていない指標のスキップ申告は `ERROR` として扱う（「脆弱性スキャンをスキップした」といった申告は通らない）
3. **部分計測であることを隠さない** — 6.3.1 のとおり、部分計測の Run は完全計測と明確に区別して表示する
4. **最後の完全計測を常に見せる** — 最後に完全計測が行われた日時をダッシュボードとリポジトリ詳細に常に表示する（FR-06-3）

### 6.5 設定ファイル（`collector/targets/<owner>__<name>.gate.yml`）の例

```yaml
version: 1

execution:
  # スキップを申告できる指標。ここに無い指標のスキップ申告は ERROR とする
  skippable_metrics: [mutation_score, performance]

exclusions:                       # 全指標共通の計測除外
  - "**/generated/**"
  - "**/*.config.ts"
  - "backend/**/dto/**"

metrics:
  branch_coverage:
    enabled: true
    threshold: 75                 # %。コンポーネントごとに判定する
    warn_below: 80                # これ未満は注意（WARN）
  mutation_score:
    enabled: true
    threshold: 60
    components: [backend]         # PIT を用いるため Java のみ。frontend は対象外
  performance:
    enabled: true
    p95_ms: 500
    arrival_rate_rps: 50          # 負荷条件（到達率）。この負荷下で p95 / エラー率を判定する
    error_rate_pct: 0.1
    scenarios: ["login", "search", "order-create"]
  vulnerabilities:
    enabled: true
    max_critical: 0
    max_high: 0
  cyclomatic_complexity:
    enabled: true
    max_complexity: 15
    warn_from: 11
  api_contract:
    enabled: true
    breaking_changes: 0
  test_results:
    enabled: true
  accessibility:
    enabled: true
    standard: wcag22aa
    max_critical: 0               # axe impact: critical + serious
    pages: ["/", "/login", "/orders", "/orders/new", "/settings"]
```

## 7. 外部インタフェース

### 7.1 Ingest API（収集ランナー → quality-gate）

認証は `Authorization: Bearer <ingest-token>`。トークンは収集ランナー用の 1 つで、書き込み専用。

| メソッド | パス | 用途 |
| --- | --- | --- |
| POST | `/api/v1/runs` | Run を開始し、メタデータを登録して `runId` を返す |
| POST | `/api/v1/runs/{runId}/artifacts` | 成果物をアップロード（`type` でフォーマットを指定、multipart） |
| POST | `/api/v1/runs/{runId}/finalize` | 取り込み完了を宣言し、その場で正規化・判定して結果を返す |

Run 開始時のメタデータ:

```json
{
  "repository": "example-org/example-app",
  "commitSha": "a1b2c3d4e5f6...",
  "baseCommitSha": "9f8e7d6c5b4a...",
  "branch": "feature/order-api",
  "pullRequestNumber": 1234,
  "triggeredBy": "collector",
  "ciRunUrl": "https://github.com/example-org/quality-gate/actions/runs/123456",
  "measuredAt": "2026-09-21T02:10:00Z",
  "tags": [],
  "skippedMetrics": [
    { "metricId": "M-02", "reason": "PR の計測では PIT を実行しない" },
    { "metricId": "M-03", "reason": "PR の計測では k6 を実行しない" },
    { "metricId": "M-04", "reason": "PR の計測では k6 を実行しない" },
    { "metricId": "M-05", "reason": "PR の計測では k6 を実行しない" }
  ]
}
```

`skippedMetrics` は省略可能で、省略時は「すべての指標を計測した」
ことを意味する。申告された指標が `execution.skippable_metrics` に含まれない場合、
その指標は `SKIP` ではなく `ERROR` となる（FR-05-6）。

性能成果物の添付時に必須となる追加メタデータ:

```json
{
  "environment": {
    "name": "perf-staging",
    "runner": "self-hosted-perf-01",
    "cpu": "8 vCPU",
    "memory": "16 GiB",
    "datasetProfile": "orders-1M",
    "loadModel": "constant-arrival-rate",
    "warmupSeconds": 60,
    "durationSeconds": 300
  }
}
```

quality-gate 自身は計測しない（DD-5）。自身の Pull Request では `.github/workflows/ci.yml` が
ユニットテスト・結合テスト・生成物の同期検証・アクセシビリティ検査・脆弱性スキャンを GitHub ホストランナーで実行する。

### 7.2 参照 API（UI → quality-gate）

GitHub OAuth ログイン後のセッションで認証する REST API。
リポジトリ一覧、Run 一覧・詳細、指標時系列、Finding 一覧、リリース判定を提供する。
仕様は springdoc により OpenAPI として自動生成し、`api/openapi.yml` として管理する。

### 7.3 GitHub 連携

**単一の GitHub App** を登録し、ユーザーログインと収集ランナーによる対象の読み取りの双方をこれで賄う。
OAuth App を別に用意する必要はない（GitHub App は user-to-server 認可フローを持つ）。
バックエンドは GitHub API を呼ばない（DD-10）。

| 用途 | 方式 | 権限 |
| --- | --- | --- |
| ユーザーログイン（FR-10-1） | GitHub App の user-to-server 認可フロー | ユーザー識別（`read:user`相当）のみ |
| 収集ランナーによる対象の clone | GitHub App の Contents: Read。対象リポジトリにインストールし、ジョブごとに 1 時間有効のインストールトークンを発行する | 読み取りのみ |
| 比較元（`baseCommitSha`）・タグ・ファイルの移動 | 収集ランナーが clone した履歴から求めて送る（`git merge-base` / `git tag --points-at` / `git diff -M`） | — |

GitHub App の権限は上記に限定する。書き込み権限とワークフローの起動権限は付与しない。
App の秘密鍵は quality-gate リポジトリの Actions Secrets に置き、収集ランナーの取得ジョブだけが使う（バックエンドには置かない）。

GitHub App の登録・インストールは**個人アカウント（GitHub Free）で追加費用なく可能**である。
App を private として登録すれば、所有アカウント自身のリポジトリにのみインストールできる。

> **認可上の注意**: Organization を使用しないため、「組織のメンバーであること」を
> ログインの条件にできない。GitHub アカウントを持つ任意のユーザーが OAuth フロー自体は
> 完了できてしまうため、**quality-gate 側の許可リスト（FR-10-4）が実質的な入口の
> アクセス制御となる**。この許可リストは省略できない。

## 8. データモデル（主要エンティティ）

| エンティティ | 説明 | 主な属性 |
| --- | --- | --- |
| `Repository` | 計測対象リポジトリ | owner, name, defaultBranch, enabled |
| `GateConfig` | 合格ライン等の設定。内容が変わるたびに版を作る | repositoryId, version, contentHash, rawYaml, parsed |
| `Run` | 1 回の計測・判定の単位 | repositoryId, commitSha, baseCommitSha, branch, prNumber, tags, attempt, status, verdict, completeness, gateConfigId, baselineRunId, measuredAt |
| `Artifact` | 取り込んだ元成果物 | runId, type, filename, sizeBytes, storageKey, sha256, metadata |
| `Measurement` | 指標ごとの実測値と判定 | runId, componentName, metricId, variant, value, threshold, status, previousValue |
| `Finding` | 個別違反（脆弱性 / 複雑度超過関数 / 失敗テスト / a11y 違反） | runId, metricId, fingerprint, state, severity, title, filePath, line, detail(JSON) |
| `User` | 利用者と権限 | githubLogin, role, status |
| `AuditLog` | 監査ログ（追記のみ） | actor, action, targetType, targetId, before, after, occurredAt |

**`Finding.fingerprint`** は違反を Run をまたいで同定するためのキーであり、
「新規発生 / 継続 / 解消」の判定に用いる。
指標ごとの fingerprint 定義は [02-metrics-spec.md](02-metrics-spec.md) に記載する。
詳細なテーブル定義は [06-database-design.md](06-database-design.md) を参照。

## 10. 非機能要件

### 10.1 性能

| 項目 | 目標 |
| --- | --- |
| ダッシュボード初期表示 | p95 1.0 秒以内（リポジトリ 50 件、Run 10 万件想定） |
| Run 詳細表示 | p95 1.5 秒以内 |
| トレンド API（30 日 / 1 指標） | p95 800ms 以内 |
| 確定（finalize）から判定結果の応答まで | 中央値 10 秒以内、p95 60 秒以内 |

これらの目標は自動の負荷試験では検証しない（quality-gate 自身の性能は計測しない。DD-5）。

### 10.2 規模想定

| 項目 | 初期 | 3 年後 |
| --- | --- | --- |
| 対象リポジトリ数 | 1 | 5 |
| 1 日あたり Run 数 | 10〜30 | 100 |
| 累積 Run 数 | 1 万（1 年） | 10 万 |
| 成果物ストレージ | 10 GB | 50 GB |
| 同時利用ユーザー数 | 数名 | 20 |

初期規模は小さく、性能・可用性の要求は緩い。この規模では
**PostgreSQL 1 台 + アプリ 1 プロセスの Docker Compose 構成で十分**であり、
水平スケール、メッセージキュー、キャッシュ層はいずれも不要である。
データモデルと API は将来のリポジトリ追加に耐える形にしておくが、
**インフラを先回りして複雑にはしない**。

### 10.3 可用性・信頼性

- 稼働率 99.5%（社内業務時間帯基準）。計画停止は事前告知の上で業務時間外に実施
- quality-gate の障害が対象リポジトリの開発を止めないこと（対象リポジトリの CI は quality-gate に依存しない）
- 同一コミットへの再送信は新しい試行（attempt）として記録し、過去の Run を上書きしない
- データベースは日次バックアップ、RPO 24 時間 / RTO 4 時間

### 10.4 セキュリティ

- 通信はすべて TLS 1.2 以上
- Ingest Token・IdP クライアントシークレットは環境変数（または Secrets）で渡し、平文でログ出力しない
- GitHub App の権限は 7.3 の最小限に限定する
- 取り込んだ成果物にはソースコード断片・環境情報が含まれうるため、閲覧は許可リストのユーザーに限る
- アップロードファイルはサイズ上限・形式の検証・XML 外部実体参照（XXE）無効化を徹底する
- 計測中の対象のコード（テストなど）はコンテナの中で動かし、認証情報を渡さない
- 依存ライブラリの脆弱性は quality-gate 自身の CI（Pull Request ごと）で検査する

### 10.5 運用・可観測性

- ヘルスチェック（`/actuator/health`）、メトリクス（Micrometer → Prometheus）を提供
- 構造化ログ（JSON）に相関 ID（runId、requestId）を付与
- 主要アラート: 取り込み失敗率の上昇、判定の処理失敗（`FAILED`）、日次バッチ（保持期間の削除）の失敗、ストレージ逼迫
- データ保持: Run メタデータ・指標値 2 年 / 元成果物 90 日 / 監査ログ 2 年（いずれも設定可能）

### 10.6 アクセシビリティ

quality-gate 自身が WCAG 2.2 Level AA に適合する。具体的には、
キーボードのみで全機能を操作でき、フォーカスが常に可視で、
グラフは表形式の代替表現を併せ持ち、axe-core の critical / serious 違反が 0 件であること。

### 10.7 保守性

- quality-gate 自身は quality-gate で計測しない（DD-5）。代わりに Pull Request の CI で、テスト・生成物の同期検証・アクセシビリティ検査・脆弱性スキャンに合格する
- 新しい指標・新しいツールフォーマットの追加が、アダプタ実装の追加のみで完結する構造とする

### 11.2 モジュール構成（バックエンド）

主要なモジュールは次のとおり。全パッケージと依存規則は [05](05-architecture.md) 1 章を参照。

```
quality-gate/
├ backend/
│  ├ ingest/        取り込み API、トークン認証、成果物保管
│  ├ pipeline/      設定解決 → 正規化 → 判定の流れ（確定と再評価から呼ぶ）
│  ├ adapter/       ツール別パーサ（jacoco, lcov, pit, k6, sarif, pmd, eslint, junit, oasdiff, axe）
│  ├ normalize/     正規化モデルへの変換、重複排除、fingerprint 生成、ファイルの移動の対応
│  ├ evaluate/      しきい値適用、指標判定、Run 集約、差分（新規/解消）算出
│  ├ config/        設定ファイルの検証・版管理
│  ├ query/         ダッシュボード・トレンド向け参照 API（読み取り最適化）
│  ├ release/       リリース判定と CSV
│  ├ admin/         管理系の操作 API（利用者・リポジトリ・再評価・監査ログ）
│  ├ maintenance/   日次バッチ（保持期間の削除・滞留した Run の後始末）
│  └ platform/      監査ログ、ArtifactStore（ストレージ抽象）、共通例外
├ frontend/         Vue 3 SPA
└ collector/        収集ランナー（計測スクリプト・計測プロファイル・合格ライン・ツールの版）
```

設計上の要点:

- **アダプタ層の独立** — ツールの追加・差し替えが `adapter/` の追加のみで完結する。
  正規化モデルはツール中立であり、ツール固有の概念を上位層に漏らさない
- **判定の再現性** — Run は「取り込んだ実測値」と「適用した設定版」を保持するため、
  再評価はいつでも決定的に再実行できる
- **成果物の受領と判定の分離** — 成果物のアップロードでは保存だけを行い、
  正規化・判定は finalize でまとめて行う。判定は数秒で終わるため、その場で行い結果を返す

## 12. 制約・前提

| # | 内容 |
| --- | --- |
| C-1 | 計測ツールの実行は収集ランナー（セルフホストランナー）が行う。収集ランナーは GitHub App の読み取り権限で対象をクローンする。バックエンドはコードをクローンしない |
| C-2 | 計測ツールは収集ランナーが版を固定して持ち込むため、対象リポジトリ側での導入は不要。ただし収集ランナーが扱える対象の構成（Maven + npm / Vitest）に限られる |
| C-3 | 性能計測は、他ジョブと同居しない専有の実行環境で行う（確保済み） |
| C-4 | ミューテーションテストは PIT を用いるため **backend（Java）のみ**が対象。frontend は M-01 カバレッジで担保する |
| C-5 | ミューテーションテストと負荷試験は実行時間が長いため、PR の計測では実行しない（ブランチ・コミット・タグの計測では全量を実行する） |
| C-6 | 自動アクセシビリティ検査は WCAG 違反の一部しか検出できない。「重大 0 件」は適合の十分条件ではない |
| C-7 | 単一テナント（社内専用）構成。インターネット公開は行わない |
| C-8 | GitHub は個人アカウント（Free）を使用する。Organization を持たないため、ログイン可否は quality-gate 内の許可リストで制御する（FR-10-4） |
| C-9 | 収集ランナーは専有のセルフホストランナーで直列に動く。ランナーが 1 台のため、計測は同時には動かない |
| C-10 | GitHub Free ではプライベートリポジトリの保護ブランチが利用できない。将来マージブロックへ進む場合は GitHub Pro 以上への変更が必要（[03](03-design-decisions.md) Q-5） |
| C-11 | マージブロックを行わない。不合格の是正は運用ルールに依存する |
| C-12 | SPA は Spring Boot に同梱して同一オリジンで配信する。フロントエンドのみを独立してデプロイすることはしない |

## 13. リスクと対策

本章はプロダクト・運用上のリスクを扱う。
技術選定に伴うリスク（PIT の Java 25 対応、生成物の同期漏れ など）は
[04-tech-stack.md](04-tech-stack.md) 9 章に分けて記載する。

| # | リスク | 影響 | 対策 |
| --- | --- | --- | --- |
| R-1 | 性能計測値が実行環境のノイズで変動し、合否が安定しない | ゲートが信用されなくなる | 専有環境 + ウォームアップ除外 + 3 回実行の中央値採用（M-03） |
| R-2 | 既存コードの水準が低く、初日から全リポジトリが不合格になる | 導入が頓挫する | 対象リポジトリは既にベースラインが整っているため、絶対値しきい値を当初から適用する。新規リポジトリを追加する際は、登録前にベースラインを計測し、乖離があればしきい値を個別設定する |
| R-3 | PIT と負荷試験の実行時間で計測が長時間化する | 開発速度の低下 | PR の計測では実行せず、ブランチ・コミット・タグの計測で全量を実行する（DD-17） |
| R-4 | 新規 CVE 公開により、コード変更なしで不合格に転じる | 突然の不合格に混乱 | 計測し直したときに判定が変わる。修正版が無い間は合格ライン（`*.gate.yml`）の変更として扱い、理由をコミットに残す |
| R-5 | ツールの severity 表記がばらつき「High」の定義が揺れる | 判定の信頼性低下 | CVSS スコアへの正規化マッピングを明文化する（M-06） |
| R-6 | 合格ラインの緩和が乱発され、実質的に無効なゲートになる | 形骸化 | 合格ラインは Git で管理し、変更はプルリクエストを通す（DD-13） |
| R-7 | 可視化のみで是正されない | 品質が改善しない | 週次で不合格リポジトリをレビューする運用を定める。リリース判定で不合格の指標を明示する |
| R-8 | 許可リストの設定漏れにより、意図しない GitHub ユーザーがログインできてしまう | 情報漏洩 | 既定を「拒否」とし、許可リストに存在しないユーザーは認証成功後も一律拒否する。追加操作は監査ログに記録する |
| R-9 | スキップが常態化し、M-02 と M-03〜05 が事実上測られなくなる | 指標の形骸化 | スキップを申告制とし、部分計測を完全計測と区別して表示する。最後の完全計測を常に表示する。スキップ可能な指標は設定で限定する（6.4）。リリース判定は完全計測を求める |
| R-10 | frontend のミューテーションスコアを計測しないため、Vue 側のテストの実効性が検証されない | フロント側のテスト品質が見えない | frontend は M-01 ブランチカバレッジで担保し、必要に応じて Stryker の導入を検討する |
| R-11 | 「新規関数」の同定がリファクタリング（移動・リネーム）で誤検知する | 開発者の不信 | git の rename 検出を用いてファイルの移動を追跡する（[02](02-metrics-spec.md) 0.4） |
| R-12 | 収集ランナーがセルフホストランナーでしか動かないため、ランナーの停止中は計測が止まる | 計測の途絶 | 計測は手動実行のため、実行したときにジョブが始まらないことで気づける。復旧後に計測し直す |
| R-13 | 対象リポジトリのビルド構成が変わり、収集ランナーの計測方法が追従できなくなる | 指標が ERROR になる | 未提出は fail-closed で ERROR として表に出る。計測プロファイルを更新して追従する。保守の担い手が対象のチームから quality-gate の運用者に移ることを前提とする |

## 15. 受け入れ基準

本要件の達成は次をもって確認する。

| # | 基準 |
| --- | --- |
| A-1 | 収集ランナーが成果物を送信して確定すると、応答で判定結果が返り、Run 詳細で 6 カテゴリの判定が確認できる |
| A-2 | 各指標について、合格ラインをまたぐ値を人為的に作り、PASS / FAIL が仕様どおり切り替わることを確認できる |
| A-3 | 成果物を未提出にした場合、既定設定で当該指標が ERROR となり Run 全体が FAIL になる |
| A-4 | 同一 Run を再評価すると、同じ設定版の下で同じ判定結果が再現される |
| A-5 | quality-gate 自身の Pull Request の CI（`ci.yml`）が成功する |
| A-6 | quality-gate の主要画面について、axe-core の critical / serious 違反が 0 件である |
| A-7 | 監査対象操作がすべて監査ログに記録され、Admin が検索・確認できる |
| A-8 | PIT / k6 をスキップして送信した Run（収集ランナーの PR の計測）が、ERROR ではなく `SKIP` として記録され、部分計測と表示される |
| A-9 | `execution.skippable_metrics` に含まれない指標のスキップを申告すると `ERROR` となり、Run が FAIL になる |
| A-10 | 最後の完全計測の日時がダッシュボードに表示される |
| A-11 | タグを指定して計測すると、リリース判定でそのタグから結論と全指標の合否が表示され、CSV を出力できる |

## 16. 用語定義

| 用語 | 定義 |
| --- | --- |
| Run | 1 つのコミットに対する 1 回の計測・判定の単位 |
| 収集ランナー | quality-gate リポジトリの GitHub Actions で動き、対象リポジトリを取得・計測して Ingest API に送る仕組み |
| 計測プロファイル | 対象ごとの計測方法（`collector/targets/<owner>__<name>.env`） |
| 合格ライン | 対象ごとの指標としきい値の集合（`collector/targets/<owner>__<name>.gate.yml`）。ゲート（Gate）とも呼ぶ |
| Finding | 判定の根拠となる個別の違反（脆弱性 1 件、複雑度超過関数 1 つ、失敗したテスト 1 件 など） |
| fingerprint | Finding を Run をまたいで同一と見なすためのキー。新規 / 継続 / 解消の判定に用いる |
| 比較元 | 新規の違反・破壊的変更・スキップの増加を数える起点のコミット（`baseCommitSha`） |
| 比較対象 Run | 前回比と違反の新規 / 継続 / 解消の起点にする過去の Run（比較元のコミットの Run、無ければ同じブランチの直前の Run） |
| 完全計測 / 部分計測 | 全指標を判定できた Run / `SKIP` を含む Run |
| ベースライン | 導入時点の実測値。しきい値の妥当性確認と、新規リポジトリ追加時の判断に用いる |
| fail-closed | 計測できなかった場合に「合格」ではなく「不合格」と扱う方針 |
