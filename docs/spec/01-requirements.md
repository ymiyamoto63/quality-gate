## 1. 目的

**指定したリポジトリの品質を定量的に測定し、リリース前の品質を判断する。**

個々の品質ツール（JaCoCo、Vitest、Trivy、k6、axe-core など）の結果は CI のログや成果物に散らばり、
合格ラインは暗黙知になりやすい。quality-gate は次の 4 つを行う。

1. **定量化** — 6 カテゴリの品質指標を、同じ定義で数値化する
2. **判定** — 明示した合格ラインに対して、合格 / 不合格を機械的に判定する
3. **可視化** — 現在地と推移を画面で示す
4. **リリース判断** — タグかコミットを指定すると、リリースしてよいかを指標ごとの合否と根拠を添えて 1 画面で示し、証跡（CSV）を残す

### 1.1 ゴール

| # | ゴール | 測り方 |
| --- | --- | --- |
| G-1 | 計測を実行するたびに、6 カテゴリの全指標が数値として記録される | 直近 30 日の計測成功率 95% 以上 |
| G-2 | 誰でも 1 画面で「今の合否」と「30 日の推移」が分かる | ダッシュボードから 3 クリック以内 |
| G-3 | 合格ラインの変更履歴が追える | `collector/targets/*.gate.yml` を Git で管理する |
| G-4 | リリース判定会議で、タグを指定するだけで結論と根拠を示せる | タグの計測から判定の表示・CSV の出力まで追加の作業なし |

### 1.2 やらないこと

- **バックエンドでのテストやスキャンの実行** — 実行は収集ランナーが担い、バックエンドは取り込みと判定だけを行う
- **マージのブロック** — 可視化に徹し、PR のマージは制御しない（DD-3）
- **品質問題の自動修正**
- **汎用のメトリクス基盤化** — 品質指標に用途を限る

## 2. スコープ

### 2.1 計測対象リポジトリの前提

技術スタックは固定する。これ以外の構成は計測できない。

| 項目 | 前提 |
| --- | --- |
| バックエンド | Java / Spring Boot（Maven）、JUnit 5 |
| フロントエンド | Vue 3 SPA（TypeScript、npm + Vitest） |
| リポジトリ構成 | **モノレポ**（`backend/`、`frontend/`）。backend と frontend の結果は 1 つの Run にまとまる |
| ホスティング | GitHub（個人アカウント・GitHub Free。プライベートリポジトリ） |

計測ツールは収集ランナーが版を固定して持ち込む。対象リポジトリにツールや設定を追加する必要はない。
テストそのものは対象リポジトリのものを実行する。

### 2.2 スコープ外（将来検討）

- PR の必須チェック化によるマージブロック
- マルチテナント
- GitHub 以外のホスティング
- 手動アクセシビリティ検査結果の取り込み
- frontend のミューテーションテスト（Stryker など）

## 3. 全体方針：収集ランナーと取り込み型のバックエンド

計測は **quality-gate 側の「収集ランナー」** が行い、バックエンドは送られた成果物を取り込んで判定する（DD-6）。
対象リポジトリには何も置かない。

```
 対象リポジトリ (private) ──clone（GitHub App の読み取り権限）──┐
                                                                  ▼
 quality-gate リポジトリの GitHub Actions（専有のセルフホストランナー）
   fetch（取得。比較元・タグを求める）
   → measure（計測。コンテナの中で動かし、認証情報を渡さない）
   → submit（Ingest API へ送信）
                                                                  │ HTTPS / Ingest Token
                                                                  ▼
 quality-gate バックエンド（取り込み → 正規化 → 判定 → 可視化）
```

**リポジトリの指定。** 計測するリポジトリは、収集ランナーの手動実行（`collect.yml`）で `owner/name` を指定する。
対象ごとに quality-gate リポジトリの `collector/targets/` に次のファイルを置く。これが対象の登録を兼ねる。

| ファイル | 内容 |
| --- | --- |
| `<owner>__<name>.env` | 計測プロファイル（どう測るか。ビルドの場所、Java の版、既定ブランチ など） |
| `<owner>__<name>.gate.yml` | 合格ライン（何を合格とするか） |
| `<owner>__<name>.k6.js` | 負荷試験のシナリオ（性能を測る場合） |

バックエンドは初めて計測が届いたときにリポジトリを登録する。画面での登録操作は無い。

| 制約 | 対処 |
| --- | --- |
| 計測条件（マシンスペック等）が変わると値が比べられない | 性能の成果物には計測環境のメタデータを必須とし、環境が変われば系列を分ける |
| 成果物が届かないことがある | 申告のない未提出は不合格（fail-closed）。意図的なスキップは申告制とし、ERROR と区別する（6.4） |
| 対象のビルド構成が変わると計測が追従できない | 未提出は ERROR として表に出る。計測プロファイルを更新して追従する |

## 4. 利用者とユースケース

### 4.1 ロール

| ロール | 想定者 | 権限 |
| --- | --- | --- |
| Viewer | 参照のみの関係者（PO、QA など） | 全画面の閲覧と CSV の出力 |
| Admin | 開発者・運用者 | Viewer に加えて、Run の再評価、利用者とロールの管理、監査ログの閲覧 |

ログインは GitHub アカウントで行い、ロールは quality-gate 内で個別に付与する（GitHub の組織情報には依存しない）。

### 4.2 ユースケース

| UC | 利用者 | シナリオ |
| --- | --- | --- |
| UC-01 | Admin | `collector/targets/` に計測プロファイルと合格ラインを追加し、対象を計測できるようにする |
| UC-02 | Admin | 収集ランナーでブランチ・コミット・タグ・PR を指定して計測すると、判定結果が生成される |
| UC-03 | Admin | PR を計測し、Run 詳細で不合格の原因（どの関数、どの CVE、どのページ）を特定する |
| UC-04 | 全員 | ダッシュボードで全リポジトリの合否と推移を確認する |
| UC-05 | Admin | 合格ラインを変える（例: カバレッジ 75% → 80%）。`*.gate.yml` をプルリクエストで変更し、マージ後の計測から反映される |
| UC-06 | 全員 | リリース判定会議で、タグかコミットを指定して結論と全指標の合否を確認し、CSV を証跡として残す |

## 5. 機能要件

### 5.1 対象と合格ライン

| ID | 要件 |
| --- | --- |
| FR-01-1 | 計測対象は計測プロファイル（`collector/targets/<owner>__<name>.env`）で決める。バックエンドは初めて計測が届いたリポジトリを登録する |
| FR-01-2 | 「バックエンド」「フロントエンド」のコンポーネント単位で指標を扱う。コンポーネントは計測プロファイル（`BACKEND_DIR` / `FRONTEND_DIR`）で決まる |
| FR-01-3 | 既定ブランチは計測プロファイルの `DEFAULT_BRANCH` とし、トレンドの既定の系列に使う |
| FR-02-1 | 合格ラインはファイルで管理する（`collector/targets/<owner>__<name>.gate.yml`）。収集ランナーが Run ごとに送り、その内容で判定する |
| FR-02-2 | 合格ラインをスキーマ検証し、不正なら判定せず、行番号とキー名つきで理由を示す。未知のキーも不正とする |
| FR-02-3 | Run は判定に使った合格ラインを成果物として Run と同じ期間保持し、送った quality-gate リポジトリのコミットを記録する（判定の再現性）。版の履歴は Git で見る |

### 5.2 計測と取り込み

| ID | 要件 |
| --- | --- |
| FR-03-1 | 収集ランナーを提供する。対象リポジトリを変更せずに、指定したブランチ・コミット・タグ・PR を取得・計測して Ingest API に送る。PIT と負荷試験は PR 以外の計測で実行する |
| FR-03-2 | Ingest API で Run を開始し、成果物を添付し、確定（finalize）できる。確定するとその場で判定し、結果を返す |
| FR-03-3 | Run にはコミット SHA、ブランチ、PR 番号、実行者、CI 実行 URL、計測日時、比較元のコミット、コミットを指すタグを付ける |
| FR-03-4 | 性能の成果物には計測環境（環境名、ランナー、CPU / メモリ、データ量）を必須とする |
| FR-03-5 | 同じコミットへの再送信は既存の Run を上書きせず、新しい試行（attempt）として記録する |
| FR-03-6 | 取り込みの失敗（形式不正、サイズ超過、トークン不正）は理由を構造化して返す。上限は 1 ファイル 50MB、1 Run 200MB |
| FR-03-7 | 実行しなかった指標を `skippedMetrics`（指標 ID と理由）として申告できる |

### 5.3 正規化と判定

| ID | 要件 |
| --- | --- |
| FR-04-1 | ツール固有の形式を内部の正規化モデルへ変換するアダプタ層を持つ。対応形式は [02](02-metrics-spec.md) に定める |
| FR-04-2 | 複数ツールが同じ問題を報告した場合、指標ごとに定めたキー（fingerprint）で重複を除く |
| FR-05-1 | 指標ごとに PASS / WARN / FAIL / SKIP / ERROR / NOT_APPLICABLE を判定し、Run 全体を集約ルール（6.3）で決める |
| FR-05-2 | 判定結果には、しきい値・実測値・前回比・根拠となる個別違反を含む |
| FR-05-3 | 比較元を要する指標（破壊的変更、スキップの増加）と、違反の新規 / 解消の算出のため、比較元のコミットを Run に記録する |
| FR-05-4 | 管理者は、成果物を送り直さずに Run を再評価できる（保存済みの成果物と、その Run とともに送られた合格ラインで判定し直す） |
| FR-05-5 | 申告されたスキップは `SKIP`、`execution.skippable_metrics` に無い指標のスキップ申告は `ERROR` とする。`SKIP` を含む Run は部分計測として完全計測と区別する |

### 5.4 可視化とリリース判定

| ID | 要件 |
| --- | --- |
| FR-06-1 | ダッシュボードで全リポジトリの最新の判定・最終計測日時・最後の完全計測の日時を示す |
| FR-07-1 | Run 詳細で、6 カテゴリ × 各指標の実測値・しきい値・判定を表で示す。部分計測では未計測の指標と理由を併記する |
| FR-07-2 | 各指標から個別違反（脆弱性、複雑度超過関数、失敗したテスト、a11y 違反）の一覧へ進め、対象リポジトリの該当ファイル・行の GitHub リンクを開ける |
| FR-07-3 | 比較対象 Run と比べて、違反が新規 / 継続 / 解消のどれかを示す |
| FR-07-4 | 取り込んだ元成果物をダウンロードできる（保持期間内） |
| FR-08-1 | 指標ごとのトレンドグラフ（既定 30 日、最大 2 年）を示す。しきい値の線を重ね、`SKIP` は 0 ではなく欠測とする。性能は計測環境ごとに系列を分ける |
| FR-08-2 | タグかコミットを指定して、そのコミットで判定済みの Run から、リリースの可否（リリース可 / 注意あり / 不可 / 判定できない）と全指標の合否を 1 画面に示す。使うのは同じコミットの最新の完全計測で、近くのコミットでは代用しない。未計測、または部分計測で不合格が無ければ「判定できない」 |
| FR-08-3 | リリース判定では、指標ごとに「何を見るか」「基準の根拠」「満たさないと何が起きるか」を、開発に詳しくない人にも分かる言葉で示す。根拠には種類（外部基準 / 業界の目安 / チーム判断）を付ける |
| FR-08-4 | リリース判定を CSV（1 行 1 指標。判定の前提・出力日時・出力者を各行に含む）で出力でき、印刷して PDF にもできる。出力は監査ログに残す |
| FR-08-5 | リリース判定には比較元のコミットを示す。タグで計測したときの比較元は前のタグとする |

### 5.5 共通機能

| ID | 要件 |
| --- | --- |
| FR-09-1 | 保持期間を超えたデータを毎日削除する（Run と指標値 2 年、元成果物 90 日、監査ログ 2 年。環境変数で変更できる）。合格ラインの成果物は Run と同じ期間残す。確定されないまま 24 時間たった Run は終端（ABANDONED）にする |
| FR-10-1 | GitHub アカウントでログインする（GitHub App の user-to-server 認可フロー） |
| FR-10-2 | ロール（4.1）に基づく認可を画面と API の双方で強制する |
| FR-10-3 | Ingest API は収集ランナー用の Ingest Token（1 つ）で認証し、書き込み専用とする |
| FR-10-4 | ログインできる GitHub ユーザーを許可リストで管理する。リストに無いユーザーは認証に成功しても拒否する。初回ログインのユーザーを Admin とし、以降は Admin が許可リストに追加する |
| FR-11-1 | 許可リストとロールの変更、再評価の依頼、リリース判定の CSV 出力を監査ログに記録する。監査ログは追記のみとする |
| FR-12-1 | 参照系の REST API の OpenAPI 仕様を `api/openapi.yml` として公開する |

## 6. 品質指標と判定（概要）

厳密な定義は [02-metrics-spec.md](02-metrics-spec.md) に定める。

### 6.1 指標

| ID | カテゴリ | 指標 | 既定の合格ライン | 主な入力 |
| --- | --- | --- | --- | --- |
| M-01 | 機能テスト | ブランチカバレッジ | 75% 以上（backend / frontend 各々） | JaCoCo XML、lcov |
| M-02 | 機能テスト | ミューテーションスコア | 60% 以上（**backend のみ**） | PIT XML |
| M-03 | 性能テスト | 応答時間 p95 | 500ms 以内（到達率 50 req/s を負荷条件として固定） | k6 summary JSON |
| M-04 | 性能テスト | エラー率 | 0.1% 以下 | k6 summary JSON |
| M-05 | セキュリティ | 重大・高 脆弱性件数 | 0 件 | SARIF（Trivy） |
| M-06 | コード構造 | 循環的複雑度 15 超の関数数 | 0 件 | PMD XML / ESLint JSON |
| M-07 | 契約・互換性 | OpenAPI 破壊的変更件数 | 0 件 | oasdiff JSON |
| M-08 | 使いやすさ | アクセシビリティ重大違反件数 | 0 件（critical / serious） | axe-core JSON |
| M-09 | 機能テスト | テスト成功率 | 100% | JUnit XML |
| M-10 | 機能テスト | スキップされたテスト数 | 比較対象 Run から増やさない | JUnit XML |
| M-11 | セキュリティ | シークレット検出件数 | 0 件 | SARIF（Trivy） |
| M-12 | セキュリティ | ライセンス違反件数 | forbidden 0 件（restricted・分類不明は WARN） | SARIF（Trivy） |

M-11 / M-12 は合格ラインで有効にしたときだけ判定する（設定ファイルの無い Run の既定値では無効）。

### 6.2 指標単位の判定

| ステータス | 意味 |
| --- | --- |
| PASS | 合格ラインを満たす |
| WARN | 合格ラインは満たすが、注意水準に当たる |
| FAIL | 合格ラインを満たさない |
| SKIP | 計測していない（合格ラインで無効にした、または収集ランナーがスキップを申告した） |
| ERROR | 提出されるはずの成果物が未提出、または形式不正で値を確定できない |
| NOT_APPLICABLE | ツールの制約で、そのコンポーネントでは測りようがない（M-02 の frontend など） |

**「意図して測らなかった（SKIP）」と「測ったつもりが届いていない（ERROR）」を区別する**ことが本システムの根幹である。

### 6.3 Run 全体の集約

```
FAIL または ERROR が 1 つ以上 → Run = FAIL（fail-closed）
上記なし かつ WARN が 1 つ以上 → Run = PASS_WITH_WARNINGS
上記いずれもなし              → Run = PASS
SKIP / NOT_APPLICABLE は集約に影響しない
```

`SKIP` を 1 つ以上含む Run は **部分計測**、含まない Run は **完全計測** とする。
部分計測の PASS は「測った範囲では合格」にすぎないため、Run 詳細に未計測の指標を明示し、
ダッシュボードに最後の完全計測を常に表示し、リリース判定は完全計測を求める。

### 6.4 スキップの申告

収集ランナーは PR の計測で PIT と負荷試験を実行しない。fail-closed を骨抜きにしないため、次のように限定する。

1. スキップは Run 作成時に `skippedMetrics` で明示的に申告する。申告のない未提出は `ERROR`
2. スキップできる指標は合格ラインの `execution.skippable_metrics` に列挙したものだけ。それ以外の申告は `ERROR`
3. 部分計測であることを隠さない（6.3）

### 6.5 合格ラインの例（`collector/targets/<owner>__<name>.gate.yml`）

```yaml
version: 1

execution:
  skippable_metrics: [mutation_score, performance]   # PR の計測で申告できるスキップ

exclusions:                       # 全指標共通の計測除外
  - "**/generated/**"

metrics:
  branch_coverage:
    threshold: 75
    warn_below: 80
  mutation_score:
    threshold: 60
    components: [backend]
  performance:
    p95_ms: 500
    arrival_rate_rps: 50
    error_rate_pct: 0.1
    scenarios: ["login", "search"]
  vulnerabilities:
    max_critical: 0
    max_high: 0
  cyclomatic_complexity:
    max_complexity: 15
    warn_from: 11
  api_contract:
    breaking_changes: 0
  test_results:
    min_success_rate: 100
  accessibility:
    standard: wcag22aa
    max_critical: 0
    pages: ["/", "/login"]
```

| # | 画面 | 主な内容 | 利用ロール |

| S-01 | ダッシュボード | 全リポジトリの最新の判定、最終計測日時、最後の完全計測 | 全員 |
| S-02 | リポジトリ詳細 | 最新の判定、直近の Run、トレンド・設定・リリース判定への入口 | 全員 |

| S-04 | 違反一覧 | 個別違反（深刻度 / 新規・継続で絞り込み）、GitHub への直リンク | 全員 |
| S-05 | トレンド | 指標の推移。性能は計測環境ごとの系列 | 全員 |
| S-06 | 設定 | 直近の Run に送られた合格ラインと検証結果（表示のみ） | 全員 |
| S-07 | 管理 | 許可リスト、ロール、監査ログ | Admin |
| S-08 | リリース判定 | 結論と全指標の合否、各指標の説明と根拠、CSV の出力・印刷 | 全員 |

quality-gate 自身も WCAG 2.2 AA を満たす（axe-core の critical / serious 0 件、キーボードで全操作、色だけで合否を伝えない、グラフに表の代替）。

## 9. 非機能要件

| 項目 | 要件 |
| --- | --- |
| 規模 | 対象リポジトリ 1〜5、Run は 1 日 10〜100、利用者は数名〜20。**PostgreSQL 1 台 + アプリ 1 プロセス**（Docker Compose）で足り、キュー・キャッシュ・水平スケールは持たない |
| 性能の目安 | ダッシュボード p95 1.0 秒、Run 詳細 p95 1.5 秒、確定から判定結果の応答まで p95 60 秒（自動では検証しない） |
| 可用性 | quality-gate の障害が対象リポジトリの開発を止めない。DB は日次バックアップ |
| セキュリティ | 通信は TLS。Ingest Token と GitHub のクライアントシークレットは環境変数で渡し、ログに出さない。成果物の閲覧は許可リストの利用者に限る。アップロードはサイズ上限と形式検証を行い、XML の外部実体参照を無効にする。計測中の対象のコードはコンテナの中で動かし、認証情報を渡さない |
| 運用 | `/actuator/health`、Prometheus のメトリクス、相関 ID（runId、requestId）付きの JSON ログ |
| 保守性 | 指標やツール形式の追加がアダプタと判定器の追加で完結する。quality-gate 自身の品質は PR の CI（`ci.yml`）で確かめる（DD-5） |

## 10. 制約

| # | 内容 |
| --- | --- |
| C-1 | 計測は収集ランナー（専有のセルフホストランナー、1 台で直列）が行う。バックエンドはコードを取得しない |
| C-2 | 収集ランナーが扱える対象の構成（Maven + npm / Vitest のモノレポ）に限る |
| C-3 | ミューテーションテストは PIT を使うため backend のみ。frontend は M-01 で担保する |
| C-4 | 自動のアクセシビリティ検査は WCAG 違反の一部しか検出できない。「重大 0 件」は適合の十分条件ではない |
| C-5 | 社内専用・単一テナント。GitHub は個人アカウント（Free）のため、ログインの可否は許可リストで制御する |

## 11. リスクと対策

| # | リスク | 対策 |
| --- | --- | --- |
| R-1 | 性能の値が実行環境のノイズで揺れ、合否が安定しない | 専有環境、ウォームアップの除外、3 回実行の中央値（M-03） |
| R-2 | PIT と負荷試験で計測が長くなる | PR の計測では実行せず、ブランチ・コミット・タグの計測で実行する（DD-8） |
| R-3 | 新しい CVE の公開で、コード変更なしに不合格になる | 計測し直すと判定が変わる。修正版が無い間は合格ラインの変更として扱い、理由をコミットに残す |
| R-4 | 合格ラインの緩和が乱発され、ゲートが形骸化する | 合格ラインは Git で管理し、変更はプルリクエストを通す（DD-13） |
| R-5 | スキップが常態化し、M-02 と M-03 / M-04 が測られなくなる | 申告制と許容リスト、部分計測の明示、最後の完全計測の表示、リリース判定は完全計測を求める |
| R-6 | 許可リストの設定漏れで、意図しないユーザーがログインする | 既定を拒否とし、許可リストに無いユーザーは一律拒否する。変更は監査ログに残す |
| R-7 | 既存コードに複雑度 15 超の関数が多く、M-06 が不合格のままになる | 許容する関数は合格ラインの `exclusions` で外し、理由をコミットに残す |
| R-8 | 対象のビルド構成が変わり、収集ランナーが追従できない | 未提出は ERROR として表に出る。計測プロファイルを更新する |

## 12. 受け入れ基準

| # | 基準 |
| --- | --- |
| A-1 | 収集ランナーが成果物を送って確定すると、応答で判定結果が返り、Run 詳細で 6 カテゴリの判定を確認できる |
| A-2 | 各指標について、合格ラインをまたぐ値で PASS / FAIL が仕様どおり切り替わる |
| A-3 | 成果物を未提出にすると、その指標が ERROR になり Run 全体が FAIL になる |
| A-4 | 同じ Run を再評価すると、同じ判定結果が再現される |
| A-5 | PR の計測（PIT と k6 をスキップ）が ERROR ではなく SKIP として記録され、部分計測と表示される。許容していない指標のスキップ申告は ERROR になる |
| A-6 | タグを指定して計測すると、リリース判定でそのタグから結論と全指標の合否を表示でき、CSV を出力できる |
| A-7 | quality-gate 自身の PR の CI（`ci.yml`）が成功し、主要画面の axe-core の critical / serious 違反が 0 件である |

## 13. 用語

| 用語 | 定義 |
| --- | --- |
| Run | 1 つのコミットに対する 1 回の計測・判定 |
| 収集ランナー | quality-gate リポジトリの GitHub Actions で動き、対象リポジトリを取得・計測して Ingest API に送る仕組み |
| 計測プロファイル | 対象ごとの計測方法（`collector/targets/<owner>__<name>.env`） |
| 合格ライン | 対象ごとの指標としきい値の集合（`collector/targets/<owner>__<name>.gate.yml`） |
| Finding | 判定の根拠となる個別の違反（脆弱性 1 件、複雑度超過関数 1 つ など） |
| fingerprint | Finding を Run をまたいで同一と見なすキー。新規 / 継続 / 解消の判定に使う |
| 比較元 | 破壊的変更・スキップの増加を数える起点のコミット（`baseCommitSha`） |
| 比較対象 Run | 前回比と違反の新規 / 継続 / 解消の起点にする過去の Run（比較元のコミットの Run、無ければ同じブランチの直前の Run） |
| 完全計測 / 部分計測 | 全指標を判定できた Run / `SKIP` を含む Run |
| fail-closed | 計測できなかったものを合格ではなく不合格と扱う方針 |
